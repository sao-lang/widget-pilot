## 0. 先建立整体认知

M04 是**服务，不是库**：它有独立进程（control-plane :8000 + orchestrator worker）、建表（PG 五张业务表）、
暴露 REST + SSE。它把 M03 库级的不变量（状态迁移、租约、幂等、hash 链）接到真实
Postgres / Redis 上，并在此之上加了 M03 没有的东西——账号、JWT、租户隔离、审计账本。

关键结构特征：**每个依赖都是「Protocol + 双实现」**。UserStore / SessionStore / EventWindow /
CheckpointStore 都有内存实现（无 Docker 跑测试）与 PG/Redis 实现（生产）。读懂这一点，
就理解了为什么能在没有基础设施时跑全量单测，以及生产装配集中在哪。

**最重要的一句**：修复前 orchestrator 是 27 行心跳壳、真实适配器只在测试里实例化；修复后
生产进程真的驱动 `agent_core.run()` —— checkpoint 落 PG、state 字节落 Redis、审计落 PG、
任务走 Redis Streams。**"能力存在"和"能力接进生产"是两件事**，本轮补的就是后者。

规模：`services/control_plane/` 约 2200 行（含 migrations）+ `services/orchestrator/` 约 970 行
（adapters 495 / dispatcher 337 / deps 278 / worker 136）；M04 相关测试 13 文件约 1713 行。
**不要按文件名字母序读**，按下面 6 个阶段。

```
阶段 1  入口与装配         api/main.py → api/server.py → api/guard.py
   ↓
阶段 2  领域服务（心脏） ★  sessions/service.py → accounts/service.py
   ↓
阶段 3  存储适配           accounts|sessions/stores.py → pg_stores.py → audit/pg_ledger.py
   ↓
阶段 4  基础设施落库        orchestrator/adapters.py（五个 M03 Protocol 的 PG/Redis 实现）
   ↓
阶段 5  生产编排回路 ★★     orchestrator/deps.py → dispatcher.py → worker.py（能力接进生产）
   ↓
阶段 6  测试即文档          tests/unit/test_m04_* → tests/integration/test_m04_*
```

> 类型契约（`packages/agent_core/types.py` / `packages/contracts/enums.py`）不列入顺序——
> **当字典用**，遇到 `State` / `AgentEvent` / 某枚举值时再回查。

## 1. 阶段 1 · 入口与装配

| 文件 | 行数 | 读什么 |
|---|---|---|
| `api/main.py` | 82 | 生产装配全景：环境门禁（JWT_SECRET / DATABASE_URL 缺失即拒绝启动）→ 原始 DATABASE_URL 透传给各存储（统一经 `db.sync_dsn` 转 pg8000）→ 注入 PG 用户/会话存储、Redis 事件源、**真实附件服务（S3+PG+守卫）**、**PgAuditLedger**、**RedisTaskQueue 入队回调** → 挂 healthz/readyz |

`X-Accel-Buffering: no`；帧格式 `id: {seq}\nevent: {kind}\ndata: {json}\n\n`，末尾心跳注释帧。
当前是**有限流**（发完存量事件即关闭，客户端凭最后 seq 续连）；长连接异步订阅待 M15 联调。

## 2. 阶段 2 · 领域服务（全模块心脏，逐行读）

### 2.1 `sessions/service.py`（357 行）—— 状态机唯一执行点

所有状态迁移集中在此，铁律：**先租户校验 → 判前态是否合法 → 捕获前态 → 写新态 →
乐观锁提交 → 写审计**。三个私有方法看懂了，公开方法全是同一模式：

| 私有方法 | 职责 |
|---|---|
| `_assert_owner(user_id, row)` | 调 TenantGuard；拒绝时写 DENY 审计（payload 仅尝试者 id）再抛 403 |
| `_commit(row, expected_state)` | 带乐观锁的写回；存储层冲突（ValueError）折叠为领域 ConflictError（409） |
| `_audit(row, action, decision)` | 状态迁移写只追加审计账本（M04 产生，M11 汇总） |

公开迁移方法：`create` / `submit_message` / `mark_awaiting_input` / `answer_clarification` /
`interrupt` / `resume` / `cancel` / `complete` / `fail`。终态集合 `_TERMINAL_STATES` 与
挂起态集合 `_HANG_STATES` 是两个 frozenset，别散落裸枚举比较。

**关键设计**：`reason_code` 不落 Session 主记录（按 §6.1 字段归属，过程数据走事件流），
但 `mark_awaiting_input` 会把它写进审计的 decision 字段（SPEC_MISSING vs ask_user 可区分）。
`interrupt` 幂等（A6）：已挂起态直接返回，不重复写 checkpoint。

> **接线注意**：`mark_awaiting_input` 内部有 `_assert_owner`，所以 dispatcher 回写挂起态时
> **必须传真实 user_id**（从任务载荷取，见阶段 5）；传空串会抛 ForbiddenError——这是
> 本轮 review 修掉的第一个 Blocker。

### 2.2 `accounts/service.py`（175 行）—— JWT 双令牌

`register` 只存 argon2 hash；`login` 失败路径统一（不区分账号不存在/密码错误，防枚举）。
JWT claims 带 `sub` / `role` / `type` / `exp`，access 15min + refresh 7d。

**refresh 安全约束**（本轮修复点）：refresh 时用户必须仍存在，角色取 **DB 最新值**
而非 token claims——否则用户被删/降权后仍能凭旧 role 换发越权令牌。

### 2.3 `sse.py`（105 行）、`audit/ledger.py`（164 行）与 `audit/pg_ledger.py`（202 行）

- `sse.py`：`EventWindow` Protocol + 两个实现——`SSEWindow`（内存测试）/ `RedisEventSource`
  （生产，包装 `RedisEventBus.window`）。`since(last_event_id, session_id)` 按 seq 过滤（I5）。
- `audit/ledger.py`：内存账本，hash 链 `chain_hash = sha256(prev + 规范化全字段)`，
  **整行证据字段入链**（不只 payload），篡改 action/user_id 也能被 `chain_valid` 检出。
- `audit/pg_ledger.py`：**生产 PG 账本（本轮新增）**，与内存版同接口。hash 链算法复用
  `ledger._canonical_body`（**唯一规范化点**，写入与重算共用）。`append` 用
  `pg_advisory_xact_lock` 串行化「读链尾→算 hash→写行」——不加锁的并发 append 会断链
  （本轮 review B4：8 线程 20 次 append 曾实测 `chain_valid=False`）。修后 6 用例全绿（含并发）。

| 文件 | 行数 | 读什么 |

## 4. 阶段 4 · 基础设施落库（`orchestrator/adapters.py`，495 行）

这是 M03 五个库级 Protocol 的真实落板，**五个类相互独立，按需查，不必通读**：

| 类 | 职责 | 对应不变量 |
|---|---|---|
| `PgCheckpointStore` | checkpoint 表读写；save 新 rev 行**继承前一 rev 的租约列**（B2 修复点） | I1 / I2 |
| `PgLeaseProvider` | 原子抢锁 `UPDATE ... WHERE lease_until < now()`；抢不到抛 `HUMAN_REQUIRED`（与 M03 协议的非空 `Lease` 返回对齐）；heartbeat 引用 LEASE_TTL_S 常量 | I3 |
| `RedisIdempotencyStore` | SETNX 原子占位，命中复用 result_ref；bytes→str 单点解码 | I4 |
| `RedisEventBus` | XADD 写流 / XRANGE 续传 / XTRIM 窗口；`make_event_decoder` 工厂 | I5 |
| `RedisEventSource` | 见 `sse.py`（此处经 `bus.window` 回调接入生产 SSE） | — |

**关键修复点**：租约是 **run 级**而非 rev 级。`save()` 若不带租约列，持锁 worker 每写一个
checkpoint 就会丢锁、被另一 worker 抢占（双 worker 并发）。这是拷贝集成测试才能发现的缺陷。

> 注意：这些适配器**本身不知道谁调用它们**。阶段 4 只是"造好了能力"，真正让它们在
> 生产被驱动的是阶段 5 的 dispatcher/worker——这是本轮修复的核心分工。

## 5. 阶段 5 · 生产编排回路（★★ 本轮新增，重点读）

修复前 `worker.py` 是 27 行心跳壳、这三个能力只在集成测试里被实例化；修复后生产进程真的
驱动 agent loop。**按 `deps → dispatcher → worker` 顺序读**，这是整条回路的骨架。

### 5.1 `deps.py`（278 行）—— 生产依赖装配

| 类/函数 | 行号 | 读什么 |
|---|---|---|
| `RedisObjectStore` | :47 | checkpoint state 字节的通用存储（put 返回 `#sha256:` ref / get 校验）；大对象落 Redis，元数据行仍落 PG |
| `ProdCheckpointStore` | :105 | 包装 `PgCheckpointStore` + 对象存储，**补齐 M03 `save_checkpoint`/`chain_valid` 依赖的 `objects`/`states`/`rows` 便利属性**（:126/:131）；这是"适配器直接喂给 run()"的关键——否则 `run.py:54,66` 会 AttributeError |
| `RealClock` | :180 | 生产时钟（单测用 FakeClock） |
| `_EnvModelGateway` | :188 | **真实模型接线**：`complete()`（:207）→ `model_provider.complete()` → `httpx.post` 真实端点；无 fake |
| `build_deps` | :241 | 一次性装配全部真实依赖；缺 `MODEL_*` 即 fail-fast（:259-266），**禁止静默降级 fake** |

测不了见 `docs/modules/M04-模型依赖与测试缺口标注.md`。

### 5.2 `dispatcher.py`（337 行）—— 队列消费与状态回写

| 类/方法 | 行号 | 读什么 |
|---|---|---|
| `RedisTaskQueue` | :85 | Streams 队列：`enqueue`(:120) / `consume`(:132) / `_reclaim`(:161) / `ack`(:195) / `dead_letter`(:205) / `replay_expired`(:221) |
| `_reclaim` | :161 | XAUTOCLAIM 认领超时 PEL → 递增重试计数 → **重新入队（计数持久化在 wire）+ ACK 旧消息** → 返回空让 `>` 读新消息。计数用无下划线 `retries` 字段（:36），否则每轮从 0 重置、死信永不触发（review B2） |
| `Dispatcher._write_back` | :255 | 终态映射：DONE→complete（**空 bundle_ref 转 fail，不假绿**，:263-273）/ FAILED\|HANDOFF→fail / 挂起→mark_awaiting_input（**用任务里的真实 user_id**，:259） |
| `process_one` | :289 | 取一条 → `run()` → 回写；**仅成功后 ACK**（:317-320），失败留 PEL，重试超 `_MAX_RETRY=3` 写死信 |

**review 三问速记**：① 任务带 `user_id`（否则挂起回写 403）② 失败不 ACK（否则丢任务）③
重试计数随 Stream 持久化（否则死信失效）。这三条各对应一个曾真实复现的 Blocker。

### 5.3 `worker.py`（136 行）—— 主循环 + 恢复扫描 + 心跳

- `scan_expired_tasks`（:42）：扫过期租约 → `find_by_run_id` 反查真实 session_id/user_id →
  构造完整恢复任务（**不是空 session_id**，否则跨实例接管失败）。
- `main`（:78）：`build_deps`(:94) → `Dispatcher`(:97) → 循环消费；单任务失败只记日志不崩主循环
  （:110-114）；每 10s 刷心跳文件供 Docker HEALTHCHECK；每 30s 恢复扫描。
- 心跳曾与消费耦合导致长模型调用期间被误判不健康——现已用 try/except 解耦。

## 7. 一条主线贯穿（自检用）

读完后用 `POST /api/sessions/{id}/messages` 这条链路自检，能讲清每跳落在哪个文件、失败返回什么码:

```
① POST /messages            → server.py:post_message()                    失败 400/403
② 鉴权（解码 JWT）          → current_user() → UserRow                    失败 401
③ 租户校验                  → session svc:_assert_owner → guard.py        失败 403 + DENY 审计
④ 状态迁移 DRAFT→RUNNING    → session svc:submit_message()                乐观锁前态 + 审计
⑤ 乐观锁落库                → pg_stores.py:update()                        WHERE state=前态，0 行→409
⑥ 任务入队 ★                → task_enqueuer → RedisTaskQueue.enqueue()    （新）携带 session/user/run
⑦ worker 消费 ★             → dispatcher.process_one() → run()            （新）真实 agent loop
⑧ checkpoint 落库 ★         → deps.ProdCheckpointStore → PG 行 + Redis 字节（新）rev 单调/hash 链
⑨ 终态回写 ★                → dispatcher._write_back → session svc       （新）DONE→COMPLETED 等
⑩ SSE 扇出                  → adapters.RedisEventBus → GET /events → SSE 帧
```

**前 5 步是修复前就有的服务能力，⑥–⑨ 是本轮补的"接进生产"**。防护点：③ 越权（A1）、
⑤ 乐观锁（S2）、⑦ 失败不 ACK+重试计数（review B2）、⑧ 租约继承（B2）、⑨ 空产物不假绿（B6）。
