# M04 · 代码阅读指南

> 面向第一次接手 `services/control_plane` + `services/orchestrator/adapters.py` 的开发者。
> 目标：用最短路径建立骨架认知，再按需要深入。本指南是**阅读顺序建议**，不新增任何设计决策；
> 权威规格见 `docs/modules/M04-账号会话与编排域.md`，行为判据见 `tests/`。
> 姊妹篇：`docs/M03-代码阅读指南.md`（M04 是 M03 纯内核的**服务化与持久化承载方**）。

## 0. 先建立整体认知

M04 是**服务，不是库**：它有独立进程（control-plane :8000）、建表（PG 五张业务表）、
暴露 REST + SSE。它把 M03 库级的不变量（状态迁移、租约、幂等、hash 链）接到真实
Postgres / Redis 上，并在此之上加了 M03 没有的东西——账号、JWT、租户隔离、审计账本。

关键结构特征：**每个依赖都是「Protocol + 双实现」**。UserStore / SessionStore /
EventWindow 都有内存实现（无 Docker 跑测试）与 PG/Redis 实现（生产）。读懂这一点，
就理解了为什么这个项目能在没有基础设施时跑全量单测，以及生产装配集中在哪。

规模：`services/control_plane/` 约 1800 行（含 migrations）+ `orchestrator/adapters.py`
402 行；测试 7 个文件约 1020 行。**不要按文件名字母序读**，按下面 5 个阶段。

```
阶段 1  入口与装配       api/main.py → api/server.py → api/guard.py
   ↓
阶段 2  领域服务（心脏） ★  sessions/service.py → accounts/service.py
   ↓
阶段 3  存储适配         accounts|sessions/stores.py → pg_stores.py
   ↓
阶段 4  基础设施落库      orchestrator/adapters.py
   ↓
阶段 5  测试即文档        tests/unit/test_m04_api.py → tests/integration/test_m04_infra.py
```

> 类型契约（`packages/agent_core/types.py` 967 行 / `packages/contracts/enums.py` 121 行）
> 不列入顺序——**当字典用**，遇到 `State` / `AgentEvent` / 某枚举值时再回查。

## 1. 阶段 1 · 入口与装配

| 文件 | 行数 | 读什么 |
|---|---|---|
| `api/main.py` | 69 | 生产装配全景：环境门禁（JWT_SECRET / DATABASE_URL 缺失即拒绝启动）→ asyncpg DSN 转 psycopg → 注入 PG 存储 + Redis 事件源 → 挂 healthz/readyz |
| `api/server.py` | 351 | 系统对外暴露什么：13 条 REST 路由（含 auth refresh 与 SSE）+ `current_user` 鉴权依赖；所有异常到 HTTP 状态码的映射都在此 |
| `api/guard.py` | 30 | 只有 10 行逻辑——`assert_owner`：归属不等抛 ForbiddenError，固定文案不泄漏资源是否存在。**全模块越权防护的单一闸门** |

**关注点**：`create_app()` 是依赖注入点——测试传内存实现，生产传 PG/Redis 实现。
`current_user` 是闭包（在 create_app 内定义一次），拆 token → 还原 UserRow → 查不到用户 401。

**SSE 端点**（`server.py:stream_events`）：`GET /api/sessions/{id}/events`，先租户校验，
再按 `Last-Event-ID` 从事件源拉增量。响应头 `text/event-stream` + `no-cache` +
`X-Accel-Buffering: no`；帧格式 `id: {seq}\nevent: {kind}\ndata: {json}\n\n`，末尾心跳注释帧。
当前是**有限流**（发完存量事件即关闭，客户端凭最后 seq 续连）；长连接异步订阅待 M15 联调。

## 2. 阶段 2 · 领域服务（全模块心脏，逐行读）

### 2.1 `sessions/service.py`（258 行）—— 状态机唯一执行点

所有状态迁移集中在此，铁律：**先租户校验 → 判前态是否合法 → 捕获前态 → 写新态 →
乐观锁提交 → 写审计**。三个私有方法看懂了，公开方法全是同一模式：

| 私有方法 | 职责 |
|---|---|
| `_assert_owner(user_id, row)` | 调 TenantGuard；拒绝时写 DENY 审计（payload 仅尝试者 id）再抛 403 |
| `_commit(row, expected_state)` | 带乐观锁的写回；存储层冲突（ValueError）折叠为领域 ConflictError（409） |
| `_audit(row, action, decision)` | 状态迁移写只追加审计账本（M04 产生，M11 汇总） |

公开迁移方法：`create` / `submit_message` / `mark_awaiting_input` / `answer_clarification` /
`interrupt` / `resume` / `cancel` / `complete` / `fail`。终态集合 `_TERMINAL_STATES` 与
挂起态集合 `_HANG_STATES` 是两个 frozenset，别散落裸枚举比较。

**关键设计**：`reason_code` 不落 Session 主记录（按 §6.1 字段归属，过程数据走事件流），
但 `mark_awaiting_input` 会把它写进审计的 decision 字段（SPEC_MISSING vs ask_user 可区分）。
`interrupt` 幂等（A6）：已挂起态直接返回，不重复写 checkpoint。

### 2.2 `accounts/service.py`（175 行）—— JWT 双令牌

`register` 只存 argon2 hash；`login` 失败路径统一（不区分账号不存在/密码错误，防枚举）。
JWT claims 带 `sub` / `role` / `type` / `exp`，access 15min + refresh 7d。

**refresh 安全约束**（本轮修复点）：refresh 时用户必须仍存在，角色取 **DB 最新值**
而非 token claims——否则用户被删/降权后仍能凭旧 role 换发越权令牌。

### 2.3 `sse.py`（105 行）与 `audit/ledger.py`（142 行）—— 各扫一遍

- `sse.py`：`EventWindow` Protocol + 两个实现——`SSEWindow`（内存测试）/ `RedisEventSource`
  （生产，包装 `RedisEventBus.window`）。`since(last_event_id, session_id)` 按 seq 过滤（I5）。
- `audit/ledger.py`：hash 链 `chain_hash = sha256(prev + 规范化全字段)`，
  **整行证据字段入链**（不只 payload），篡改 action/user_id 也能被 `chain_valid` 检出。

## 3. 阶段 3 · 存储适配（双实现可插拔）

| 文件 | 行数 | 读什么 |
|---|---|---|
| `accounts/stores.py` | 78 | `UserStore` Protocol + `InMemoryUserStore`（email 小写归一、双索引） |
| `sessions/stores.py` | 105 | `SessionStore` Protocol + `InMemorySessionStore`；`get()` 返回**副本**（对齐 PG fetchone 语义，乐观锁依赖此点） |
| `accounts/pg_stores.py` | 95 | PG 实现；email UNIQUE 冲突映射为 DuplicateEmailError（409） |
| `sessions/pg_stores.py` | 155 | PG 实现；`update(expected_state)` 加 `WHERE state = %s`，0 行命中抛 ValueError（被 service 折叠为 409） |

**关注点**：乐观锁是 S2 修复引入的——并发两请求同时迁移同一会话，`WHERE state=前态`
保证只有一个 UPDATE 命中。内存实现用 `current.state is not expected_state` 模拟同等语义。

## 4. 阶段 4 · 基础设施落库（`orchestrator/adapters.py`，402 行）

这是 M03 五个库级 Protocol 的真实落板，**五个类相互独立，按需查，不必通读**：

| 类 | 职责 | 对应不变量 |
|---|---|---|
| `PgCheckpointStore` | checkpoint 表读写；save 新 rev 行**继承前一 rev 的租约列**（B2 修复点） | I1 / I2 |
| `PgLeaseProvider` | 原子抢锁 `UPDATE ... WHERE lease_until < now()`；heartbeat 引用 LEASE_TTL_S 常量 | I3 |
| `RedisIdempotencyStore` | SETNX 原子占位，命中复用 result_ref；bytes→str 单点解码 | I4 |
| `RedisEventBus` | XADD 写流 / XRANGE 续传 / XTRIM 窗口；`make_event_decoder` 工厂 | I5 |
| `RedisEventSource` | 见 `sse.py`（此处经 `bus.window` 回调接入生产 SSE） | — |

**关键修复点**：租约是 **run 级**而非 rev 级。`save()` 若不带租约列，持锁 worker 每写一个
checkpoint 就会丢锁、被另一 worker 抢占（双 worker 并发）。这是拷贝集成测试才能发现的缺陷。

## 6. 一条主线贯穿（自检用）

读完后用 `POST /api/sessions/{id}/messages` 这条链路自检，能讲清每跳落在哪个文件、失败返回什么码：

```
① POST /messages          → server.py:post_message()
② 鉴权（解码 JWT）        → current_user() → UserRow       失败 401
③ 租户校验                → session svc:_assert_owner() → guard.py   失败 403 + DENY 审计
④ 状态迁移 DRAFT→RUNNING  → session svc:submit_message()  乐观锁前态 + 审计
⑤ 乐观锁落库              → pg_stores.py:update()          WHERE state=前态，0 行→409
⑥ 事件扇出                → adapters.py:Redis Streams → GET /events → SSE 帧
```

**这六步里嵌着本轮修复的防护点**：③ 租户校验（B1 越权）、⑤ 乐观锁（S2 并发）、
④ 之后的租约继承（adapters.py:save，B2 双 worker）、refresh 的 DB role（B3 旧令牌）。

## 8. 两条实用捷径

- **20 分钟抓主干**：阶段 1（`main.py` + `server.py` 路由表）→ 阶段 2.1（`sessions/service.py`
  三个私有方法 + 一个公开方法）→ 第 6 节主线自检。
- **讲清「M04 与 M03 的边界」**：M03 定义纯函数与库级算法（可脱库单测），M04 负责把它
  们接到真实 PG 表、REST/SSE 接口、权限校验与审计上。**边界最易混淆**：`decide()` / `lease.py`
  的算法在 M03，把算法接到 `checkpoint` 表、让 worker 跑起来的编排在 M04。

## 9. 如何验证你读懂了

```bash
# 全量测试（166 条：unit + 真实集成，无 Docker 时集成 skip）
.venv/Scripts/python.exe -m pytest -q

# 代码风格 / 类型
.venv/Scripts/python.exe -m ruff check services/control_plane services/orchestrator/adapters.py
npx pyright services/control_plane services/orchestrator/adapters.py
```

能独立回答下面三个问题，就算真正读懂了 M04：

1. 用户 B 用自己的 token 能 cancel 用户 A 的会话吗？系统在哪一层、用什么机制挡住？
2. worker 持锁期间写了一个 checkpoint，另一个 worker 能抢到锁吗？租约存在哪张表、哪一列？
3. 两个请求同时把同一会话从 RUNNING 打断，会不会出现两次 checkpoint_rev+1？乐观锁在哪一层生效？

## 10. 已知边界（阅读时不必困惑）

- **审计落内存账本**：`AuditLedger` 目前是内存实现，DENY/迁移审计在内存生效；生产容器
  的 `audit_event` 表尚未接入（PG 审计适配器待补）。看到表空不要以为审计没写。
- **SSE 有限流**：发完存量事件+心跳即关闭，靠 Last-Event-ID 续连；长连接异步订阅待 M15。
- **R11 偏好代理端点**依赖 M07 生成服务，跨模块，不在本模块代码内。
