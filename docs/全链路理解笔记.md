## M03 agent_core 内核（2026-11-19，★ 深度级，上）

- ★ **链路位置**：不是 14 步里单独一步，而是贯穿 ⑦→⑭ 的**手写 harness 执行底座**（X1）。承载 ⑦ 生成回路的显式 agent loop、⑭ 按 seq 的 SSE 事件流，以及跨任务恢复（kill 后续跑 / 跨天回来）。零 Agent 框架（D-5）的载体——把框架黑盒里的不变量显式化为可单测代码。
- ★ **上游给什么 / 下游要什么**：上游 M04 注入 `Deps`（7 个 Protocol：model gateway / checkpoint / lease / idempotency / object store / event bus / clock / tracer）+ 用户输入 `Input`；下游产出终态 `State`（含 `bundle_ref`/`evidence`）、版本化 checkpoint、连续 seq 的事件流、幂等副作用记录，供 M04 推 SSE、M08 校验、M17 回放、M18 追踪消费。**M03 是库不是服务**：无进程、无端口、不建表。
- ★ **设计取舍（为什么这么做）**：见下方「G3 追问 · 为什么抢租约」。一句话主线——用「纯函数 decide + 副作用收口在 loop」把唯一不可信变量（模型输出）隔离在 `CALL_MODEL` 分支，用「checkpoint + 租约 + 幂等」三件套手写 durable execution，替代 Temporal。
- **输入 / 输出 / 关键接口**：
  - 入口 `run(session_id, run_id, user_input: Input|str, deps: Deps) -> State`（`loop/run.py:96`）
  - 核心 `decide(state) -> Decision`（`loop/decide.py`，纯函数，9 分支）
  - 恢复三件套 `save_checkpoint` / `lease.acquire|heartbeat|release|scan_expired` / `idempotency.get_or_reserve`
  - 类型词汇表 `SpecState`（15 显式字段，`extra="forbid"`）/ `Decision`（9 kind，NamedTuple）/ `State` / `Terminal`
- **代码关键位置（G2）**：① 入口 `packages/agent_core/loop/run.py:96` `run()`；② 核心逻辑 `packages/agent_core/loop/decide.py:87` 判定树（全库最重要）；③ 状态机 = 9 个 `DecisionKind` 分支 + `SpecState.signal` 可信结论槽位。5 站必读主线：types.SpecState → injection → **decide** → run → 恢复三件套。
- **挂 M03 的哪个机制**：M03 自身就是其他模块挂载的机制集合——`decide` 分支（各业务模块声明自己属哪个 kind）、`Deps` 里的 Port（基础设施注入点）、hook（每 super-step 落盘/发事件/计量/续租的固定动作）。下游模块不得改 `decide()` 语义。
- **状态机与前态→后态**：`RUNNING --AWAIT_INPUT/ASK_USER--> AWAITING_INPUT`（挂起不占计算资源）`--RESUME_FROM_CLARIFICATION--> RUNNING`；`--DONE/HANDOFF/FAILED--> 终态`（写终态快照，不再被恢复扫描命中）。回边 `REPAIR` 不新增 Run，计数由 `repair.feedback` 负责。
- **失败路径 → ReasonCode → 前端显示什么**：预算四维触顶 → `BUDGET_EXHAUSTED` → cost 事件 + 错误态；迭代 `MAX_ITER=12` → `RETRY_EXHAUSTED` → 终态 FAILED；自纠正超 `MAX_REPAIR=2` / 澄清超 `MAX_CLARIFY=2` → `HANDOFF` + `CLARIFICATION_LIMIT` → 转人工；`ASK_USER` → `ask_user` 事件推问题卡；`AWAIT_INPUT` → `interrupted` 事件透出 `reason_code`（如 `SPEC_MISSING`）。

### G3 追问 · 为什么 `run()` 一进来就抢租约（T19 / I6 / I11）

1. **抢的是"谁在推进这个 run"的主权，不是普通互斥锁。** M03 是零框架手写 harness，没有 Temporal 兜底，必须自己保证同一 `runId` 同一时刻只有一个 worker 在跑（I6 单持锁者）。T19 的判据就是：两个 worker 并发 `acquire`，**恰好 1 个成功**。抢到才敢往下写 checkpoint、发事件、调模型——这些都是有副作用的动作。

2. **为什么必须是"带 TTL + 心跳的租约"，而不是进程内锁？** 因为 worker 会被 kill（跨天恢复、故障注入 T21）。进程内锁随进程消失，却把 run 卡在"锁已随进程没了、但没人知道该谁接手"的半截状态。租约带过期时间（`TTL=30s`，影子校准值），worker 每个 super-step `heartbeat()` 续租；一旦 worker 崩溃，心跳停止、租约自然到期，恢复扫描 `scan_expired` 就能捞出 `lease_until < now AND terminal IS NULL` 的 run，让新实例用 `UPDATE ... WHERE lease_until < now()` **原子接管**。**锁必须能自动失效，否则 worker 一死锁就永远解不开——这是"崩溃可接管"的关键。**

3. **为什么配合 checkpoint 的 rev 链和幂等表？** 租约只保证"同一时刻一个人跑"；崩溃后换人跑，新 worker `load` 出的状态可能落后于最后已落盘的 super-step。所以 `_persist` 用 `rev = max(state.rev, latest_rev+1)` 防撞主键 `(run_id, rev)`，副作用用 `idem_key = session_id + step + payload_hash` 防重复。**租约 + checkpoint + 幂等 = 恢复三件套，缺一个都做不到 T25「产物条数 = 1」。**

4. **为什么终态的 run 不再被接管？** `scan_expired` 带 `terminal IS NULL` 条件（I11），终态 run 即使租约过期也不接管，避免重复交付。所以 `finally: lease.release()` 是"正常结束立即让出持锁权"，而不是傻等 TTL 过期。

5. **为什么有两种调用形态？** `run()` 用**对象式** `lease.heartbeat()/release()`（绑定了 run_id/owner，无参调用，贴合 §11.3 原文）；恢复扫描调度用**模块级** `scan_expired(now)`（面向全部 run，不针对单个）。契约约定两者并存（`injection.py:144/162`）。run.py 里两种形态都续租：`lease.heartbeat()` + `deps.lease_provider.heartbeat(run_id, owner)`。
