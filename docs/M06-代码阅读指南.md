## 0. 先建立整体认知

M06 是**请求进模型之前的同步判定门禁**，不是服务、不建表、不持有 provider 凭证。
它把设计文档承诺的"确定性门禁高于模型自律"落成一条同步短事务：
**L1 越界短路 → 安全护栏（注入/PII 真值校验/敏感词/预算）→ 语义层（描述/role/规格）→ 四级意图级联**，
命中/不足即短路返回，放行产 `ValidationResult` 交 M07。技能预取、need_skill 请求链已整套删除，
规程正文由模型经 `LOAD_CAPABILITY` 按需加载（五项闸门在 loop 内执行，不在本链）。

三个关键结构特征，读懂就理解了全模块：

1. **一切皆 Protocol + 双实现**。L2 `Embedder` / L3 `IntentClassifier` / L4 `IntentGateway`（`ports.py`）
   都有默认零依赖实现（可离线跑）和真实模型注入口（M20/M07 提供）。所有 Store（guard_hit / audit /
   两张日志 intent_route / capability_audit）都是 Protocol + 可插拔接口，内存实现仅存 tests/support/，
   生产注入 PG。这就是为什么没有真实模型也能跑全量单测。
2. **纯判定函数 + 事件 payload 出口**。`validate_chain()` 不写数据库、不发网络，只返回结论并
   通过 `event_sink` 回调产 guard/notice/routing/skill/plan/error 事件（§4.2）。副作用（落库、推 SSE）
   由调用方负责。
3. **拒绝类零模型调用是硬红线**（I14 / A1 / A24）。`OUT_OF_SCOPE` / 注入 / PII / 预算命中
   都在任何模型端口构造之前短路——代码里的顺序不是排版偏好，是安全保证。

规模：`services/guardrails/` 2076 行（21 个 .py）+ `orchestrator/validate_chain.py` 382 行；
测试 19 个文件（unit + integration）。**不要按文件名字母序读**，按下面 5 个阶段。

```

   ↓
阶段 2  纯判定层（心脏） ★    input_guard.py → rule_registry.py+patterns/ → semantic.py → grid_resolver.py → spec_conflicts.py
   ↓
阶段 3  四级级联与接线点 ★    ports.py → intent_cascade.py → semantic_router.py → intent_classifier.py
   ↓
阶段 4  留证与装配            guard_hit.py → audit.py → telemetry.py → capability_guard.py ★
                            → change_gate.py → validate_chain.py（两处）
   ↓
阶段 5  REST 端点 + 测试       api/main.py → tests/unit/test_m06_*.py
```

## 2. 阶段 2 · 纯判定层（心脏，逐行读）

### 2.1 `input_guard.py`（ADR-005 后约 90 行）—— 五类护栏的唯一入口

`check_input(description, extracted_texts, intent, budget, sensitive_detector=None)` 把注入 / PII 真值校验 / 分类敏感词 / 意图白名单 / 预算
五类判定串起来，命中即返回 `GuardResult(passed=False, hits=[...])`；PII 命中后再过 `validators.py` 真值校验，敏感词走 `sensitive.py` 的 Aho-Corasick 分类词库（涉政词库外置）。
**关键**：它扫描的是"描述 + 附件 extracted 文本 + 归一化意图"，绝不碰附件 original 原文（§6.5）。

### 2.2 `rule_registry.py`（77 行）+ `patterns/`（68 行）—— 规则表的实现

`PatternRule` 静态注册 + `scan()` 纯函数；`_mask()` 按 rule_id 分治——手机号/身份证数字全掩码，
邮箱保留域名掩码本地部分（`PII_EMAIL` 的 excerpt 不留原文）。三个 patterns 文件是正则词表本身，
扫一眼即可，不必背。

### 2.3 `semantic.py`（151 行）—— 语义层四步

`validate_semantic()` 依次查：① 描述充分性（长度 + `_has_required_slots()` 的宿主锚点/开放特征词表，ADR-004 去类型化）→
② 附件 role 明确性（不猜不默认）→ ③ `resolve_grid()` 三级规格 → ④ 冲突矩阵前置提示。
**每一步失败都给具体建议**（`suggestions` 非空），不静默放行。

> **澄清态参数 `grid_confirmed`（B1 修复，2026-11-21）**：用户答过规格询问后，重入队带
> `clarification_reply=1`，`validate_chain` 据此传 `grid_confirmed=True` 跳过 step2 描述充分性——
> 否则用户仅答"4x4"会二次被拒、clarify_count 2 次后卡死。跳过的是长度/槽位判定，
> **注入/PII/越界扫描照常执行**（安全不降级）；原始需求由 `original_description` 保留送进模型。

### 2.4 `grid_resolver.py`（124 行）+ `spec_conflicts.py`（30 行）—— 规格三级来源

`resolve_grid()` 三级：selector → 描述线索词表 → 缺省询问（`SPEC_MISSING` + `suggest_grid`）。
**绝不推断**：无 grid 也无线索时 `grid=None / grid_source=None`，
只给建议（`_detect_conflict_features()` 从描述抽所有冲突特征过滤候选，preferred_grids 合法项置顶）。
用户经 `/clarifications` 回答后由装配层传 `clarified_grid`，溯源 `grid_source=clarified`。

## 3. 阶段 3 · 四级级联与接线点（重点，先看 `ports.py`）

### 3.1 `ports.py`（83 行）—— 五个 Protocol 就是接线契约

三个模型端口：`Embedder`（L2 向量化+相似度）/ `IntentClassifier`（L3 分类）/ `IntentGateway`（L4 兜底裁定）；
两个日志写入口：`IntentRouteLogStorePort` / `CapabilityAuditLogStorePort`（PG 与测试替身共用）。
全部 `runtime_checkable`。**M20/M07 后续就位时照此实现并注入即可，不需要改级联判定逻辑。**
默认模型实现在 `semantic_router.DefaultEmbedder` / `intent_classifier.RuleBasedClassifier` / `StructuredFallback`；
日志的内存替身在 `tests/support/guardrails.py`，生产注入 PG。

### 3.2 `intent_cascade.py`（248 行）—— 级联编排的唯一执行点

`classify_intent()` 的骨架：

```
L1 词表（_l1_rule_intent，正向优先防误判；ADR-004 后按语义族联合条件，不按 widget 类型）→ 命中即返回，零模型调用
  ↓ 未命中
L2 _try_route()（阈值 0.75）→ 命中且非 OUT_OF_SCOPE 即裁定
  ↓ 端点异常/低置信
L3 _try_classify()（token ≤512，可解析性校验）→ 可解析即裁定
  ↓ 端点异常/不可解析/输出 OUT_OF_SCOPE
L4 gateway.resolve()（注入端口）→ 白名单方向裁定；异常回落 StructuredFallback
```

**两个必读细节**：
- `_try_route/_try_classify` 吞掉端点异常并给 `fallback_reason`（`L2_EMBEDDER_UNAVAILABLE` /
  `L3_CLASSIFIER_UNAVAILABLE` / `L3_OUTPUT_UNPARSEABLE` / `L4_*`），经 `on_fallback` 回调告警——
  **绝不静默跳过判定放行**。
- L2/L3/L4 即使返回 `OUT_OF_SCOPE` 也不采纳（拒绝类只出自 L1），回落放行方向兜底。

### 3.3 `semantic_router.py`（123 行）/ `intent_classifier.py`（46 行）—— 默认实现

`DefaultEmbedder` 用**共享 bigram 词表**定长向量（不是各文本独立词表按位置对齐——那会导致
任意两文本相似度恒 1.0 的假绿）；`RuleBasedClassifier` 恒返回"不可解析"以触发升级；
`StructuredFallback` 不调模型、结构化归类 WIDGET_GENERATION。

## 5. 一条主线贯穿（自检用）

把 `services/orchestrator/validate_chain.py::validate_chain()` 从头到尾读一遍，你会经过：

1. **入参边界**：grid 字符串 → `GridSpec` 枚举（非法 → CONTRACT_MISMATCH 拒绝，不挂起，零模型；M1 修复）
2. **输入快照**：`build_snapshot()` → sha256 → `evidenceRef` → 写 SNAPSHOT 审计（§6.1）
3. **step0 越界短路**：`is_out_of_scope(description)` → L1 命中即留 guard_hit + 推 guard/error 事件，**零模型**
4. **step7-10 安全护栏**：`check_input()` → 注入/PII 真值校验/敏感词/预算命中即短路（**先于语义层**，防 reason_code 失真）
5. **step2-6 语义层**：`validate_semantic()` → 不足/冲突/规格缺失 → 推 notice + 具体建议
6. **step11 四级级联**：`classify_intent(embedder=, classifier=, gateway=, on_fallback=)` → 写 IntentRouteLog
7. **routing 事件**：model_tier / threshold_hit / intent_normalized / route_layer / fallback_reason
8. **放行**：`ValidationResult(ok=True, ..., evidence_ref=ref, ...)` 交 M07（无 recipe_ids 字段）
   **注**：能力加载的五项闸门不在本链，而在 loop 内（capability_guard_adapter → capability_guard），
   L1/L2 请求审计写 `capability_audit_log`。

> 读完后自问：为什么第 3、4 步必须在第 5 步之前？（答案：拒绝类零模型 + 注入描述不含控件槽位
> 会先被语义层误拦——这不是代码排版问题，是安全顺序不变量。）

## 9. 已知边界（阅读时不必困惑）

- **内存实现只在 tests/，生产注入 PG**：源码只保留 PG/Redis 真实实现与 Protocol；内存/Fake 统一在 `tests/support/`，
  测试显式注入。生产注入 PG 版（迁移 0005 建 intent_route + capability_audit_log / 0007 建 guard_hit /
  0008 no-op 占位 / 0009 drop 预取表），guard_hit PG 失败保守拒绝，缺配置 fail-fast，不降级内存。
- **不实作模型端口**：默认实现是零依赖兜底，真实能力由 M20/M07 按 `ports.py` 注入（见模型缺口标注 §1）。
- **不持有 provider 凭证**：护栏进程无网络边到模型端点，凭证在 M20/M07 侧。
- **已接生产入口（2026-11-21）**：`guardrail_adapter.build_validator` 把 `validate_chain` 注入 dispatcher，
  run() 前过校验；PG 留证失败保守拒绝（不降级内存）。
- **不跑 CI 门禁**：`change_gate.py` 只是钩子；A16 的 CI 触发归 M10/CI 基建（缺口标注 §2.3）。

> **跨模块接线义务已双向标注**：所有"他模块需配合 M06"的义务都写进了对应模块设计文档的
