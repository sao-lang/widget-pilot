## 0. 读前GPS

M08 回答一个问题：**如何让一段不可信的 LLM 生成代码在受控环境里跑一遍，并且拿到的"通过"结论是无法伪造、无法抵赖的**。

一次性 Docker 沙箱解决的是「信任边界」问题：生成代码可能死循环、可能外联偷数据、可能 `rm -rf`、可能读宿主文件、可能冒充能力调用成功。把这些风险放到一个**用完即毁、断网、非 root、限额、只读根、被 seccomp 挡住危险 syscall、15 秒强杀**的容器里，即便完全失控也逃不出来、也留不下来。宿主机只收一份结构化 JSON 报告，再用 Python 侧**独立复核**，绝不只信容器自报的 success。

三层结构要分清：

- **宿主机协调层（Python）**：`entry.py` 组装 payload、拉起 Docker、收报告、跑四类断言、写证据、下结论；`ports.py` 提供 S3 证据端口与 Docker CLI 执行器；其余小文件各管一段纯逻辑。
- **容器内 JS（runner.js）**：esbuild 把 TSX 编译成 IIFE，jsdom 挂载渲染，注入 device mock 与 bridge 桩，收集交互/能力/设备调用，最后把结构化报告写到 stdout。
- **镜像配置层（seccomp.json / Dockerfile / package.json）**：决定容器"能做什么、不能做什么"，是安全边界的物理落地。

关键函数（顺着这条链读）：

- `validate_and_test`（entry.py:289）——A→B→C 三段门禁汇总总入口，沙箱不可用走降级且**绝不判通过**。
- `run_sandbox`（entry.py:112）——固定顺序 编译→渲染→尺寸→运行时→能力→交互→设备→证据。
- `_docker_command`（entry.py:88）——安全参数一次性拼齐。
- `on_sandbox_unavailable`（entry.py:375）——M11 触发的降级入口，只诊断不通过。
- `installDeviceMock`（runner.js:123）——容器内设备 API 限流/Doze/调用序列上报。
- `renderAndAssert`（runner.js:260）——jsdom 挂载、交互点击、DOM 序列化。
- `evaluate_bridge_events`（bridge_stub.py:31）——Python 侧独立复核能力调用，防容器自报成功。
- `write_evidence` / `verify_evidence_refs`（evidence.py:17/64）——所有证据带 sha256，回读校验防篡改（A17）。

核心不变量（后面每一处代码都在守这些）：

1. **隔离**：`--network none` + `--cap-drop ALL` + `--user 10001:10001` + cgroups 限额 + seccomp + `--read-only` + 15s 硬超时强杀；**不挂 docker.sock 给容器内 runner**（挂了等于把宿主机 root 交给容器，容器逃逸只需一句话）。
2. **四类断言**：尺寸（size）、无运行时错误（runtime）、能力走 bridge（capability）、交互行为（interaction）；外加 ADR-010 的设备 API 调用序列门禁。
3. **证据带 hash**：写对象返回 `key#sha256:...` 引用，读回必须重新算 hash 比对，缺证据或 hash 不符不得判 PASSED。
4. **沙箱不可用绝不判通过**：Docker 缺失/镜像缺失/超时/报告空/不可解析 → 一律 `SANDBOX_UNAVAILABLE` 降级，写降级记录，passed=False。
5. **真 Chrome png 降级不伪造**：jsdom 只有 DOM 无布局，像素截图交给宿主机 headless Chrome；没有 Chrome 或渲染失败返回 `None`，只有 html 结构证据、png_ref=None，**绝不伪造 png**，也不阻断主校验。
6. **fail-closed**：形状错误、字段缺失、异常路径一律朝"失败/不可用"收敛，不朝"通过"收敛。

一句话记忆：**容器里跑、宿主机判、证据带 hash、门全 fail-closed、降级不通过、无 Chrome 不造假**。

## 11. 镜像配置逐项讲解（安全边界的物理落地）

### 11.1 seccomp.json 逐行讲解（36 行）

seccomp（secure computing mode）过滤系统调用：默认放行，显式拒绝一组高危 syscall。这是容器逃逸的最后一道内核级防线。

- **第 1 行** `{` — JSON 根对象开始。

- **第 2 行** `"defaultAction": "SCMP_ACT_ALLOW",` — **默认放行**所有 syscall，只对下面列出的做例外。这是一种"黑名单"策略：好处是兼容性（Node/esbuild 需要的 syscall 不需要逐个列），代价是未列出的新 syscall 默认放行。不这么写（`SCMP_ACT_ERRNO` 默认拒绝且规则为空）：容器连读写文件都做不了，runner 直接崩。

- **第 3 行** `"archMap": [],` — 架构映射留空，使用 Docker 默认（按主机架构应用规则）。

- **第 4 行** `"syscalls": [` — 开始规则数组。

- **第 5-6 行** `{` / `"names": [` — 第一条规则，开始 syscall 名列表。

- **第 7-9 行** `"ptrace",` / `"process_vm_readv",` / `"process_vm_writev",` — 进程内存读写类：`ptrace` 可附加并控制其它进程、读写其内存；`process_vm_*` 跨进程读写内存。放行等于允许容器窥探/篡改宿主或其它容器进程。

- **第 10 行** `"bpf",` — BPF 字节码加载，可用于内核态探针/网络过滤，是逃逸与隐蔽持久化的常用手段。

- **第 11 行** `"userfaultfd",` — 用户态缺页处理，曾多次被用于内核漏洞提权。

- **第 12-14 行** `"mount",` / `"umount",` / `"umount2",` — 挂载/卸载文件系统。放行可挂载宿主目录（配合逃逸）或绕过只读根。

- **第 15-16 行** `"setns",` / `"unshare",` — 命名空间操作：`setns` 可加入宿主或其它容器的 namespace（经典逃逸路径），`unshare` 可创建新 namespace 绕隔离。

- **第 17 行** `"reboot",` — 重启系统。放行可让容器重启宿主。

- **第 18 行** `"kexec_load",` — 加载新内核替换当前内核。放行等于完全控制系统。

- **第 19 行** `"open_by_handle_at",` — 通过文件句柄直接打开文件，可绕过路径权限检查读宿主文件（容器逃逸常见技俩）。

- **第 20-23 行** `"init_module",` / `"finit_module",` / `"delete_module",` / `"create_module",` — 内核模块加载/删除。放行等于可以在内核态执行任意代码，彻底打破隔离。

- **第 24-25 行** `"iopl",` / `"ioperm",` — I/O 端口权限设置，可访问硬件端口（x86 特权操作）。

- **第 26 行** `"chroot",` — 改变根目录。放行可配合其它手段构造逃逸。

- **第 27 行** `"pivot_root",` — 切换根文件系统（容器运行时自己用，但容器内进程不应调用）。

- **第 28 行** `"personality",` — 设置进程执行域（历史上用于绕过 seccomp/ASLR 类攻击）。

- **第 29 行** `"acct",` — 开启进程记账，可写文件到宿主路径。

- **第 30 行** `"quotactl",` — 磁盘配额控制，内核接口，attack surface 大。

- **第 31 行** `]` — syscall 名列表结束。

- **第 32 行** `"action": "SCMP_ACT_ERRNO",` — 命中这些 syscall 时返回错误（而不是杀进程）。选 ERRNO 而非 KILL：让生成代码拿到一个普通错误（与 entry.py/executor.py 的 fail-closed 一致），而不是把整个 runner 打死导致报告丢失。

- **第 33 行** `"errnoRet": 1,` — 返回的 errno 值（1 = EPERM，操作不允许）。错误信息明确"权限不足"，便于诊断。

## 12. 证据引用与结论对象的权威定义（`output_ports.py` 逐行讲解）

> 定位：前面 §1–§11 反复出现 `key#sha256:hash`、`EvidenceRefs(...)`、`ValidateResult(...)`，但只讲"调用"，没讲"定义在哪"。本章补齐 hash 链的格式源头与共享 DTO 契约。以下全部来自 `services/guardrails/output_ports.py`（192 行），逐行对照源码。

### 12.1 为什么权威定义在 output_ports，而不是 ports.py / evidence.py

- `ports.py:21` 只是一行 `from services.guardrails.output_ports import make_object_ref, parse_object_ref` —— 它是**消费方**，不是定义方。§2 讲 ports.py 时这行 import 出现过，容易被误当成格式来源；doc:807 曾据此把 `#sha256:` 的来源错指到 `ports.py:21`，现已纠正为本章的 `output_ports.py:36` 与 `:182-184`。
- `evidence.py:11` 同样是 `from services.guardrails.output_ports import EvidenceRefs, canonical_json`，也是消费方。
- 模块 docstring **第 1–6 行**：`:1` "M08 出护栏 / 契约校验 / 沙箱共享端口与结论对象（新端口协议，不改 M06 ports.py）" — 三个服务（guardrails / sandbox_runner / control_plane）共享的结论对象定义在这里，避免各写一份漂移；`:3-5` 三条纪律——结论对象 frozen 可逐字段比较（I13）、引用必带 hash 且读取方必校验（A17）、端口用 Protocol 且生产实现由 sandbox_runner 注入、测试替身只许出现在 `tests/support/`；`:6` docstring 结束。
- 结论：**格式契约单点定义在 `output_ports.py`**，sandbox_runner 只调用。将来改分隔符、改摘要算法、改字段，只动这一个文件，不会出现"format 漂移"时无人知道改哪里。

### 12.2 第 36 行：`_REF_SEPARATOR = "#sha256:"`

- **第 36 行** `_REF_SEPARATOR = "#sha256:"` — 全链证据引用的**唯一分隔符常量**。引用格式 `{key}#sha256:{64 位 hex}` 由它定义，而不是分散在每个 `put()` 里拼字符串。
- 模块 docstring 第 3–4 行已声明这条契约："证据引用统一为 `{key}#sha256:{hex}`，读取方必须校验 hash（A17）"。第 36 行是把这句自然语言落成可执行常量。
- 它是**私有常量**（下划线开头），不在 `__all__`（`:19-34`）里。外部代码应使用 `make_object_ref` / `parse_object_ref`，不要直接引用它。

### 12.3 第 172–179 行：`sha256_hex` 与 `canonical_json` —— hash 可复现的根因

- **第 172 行** `def sha256_hex(data: bytes) -> str:` — 摘要函数签名：输入字节，输出 64 位小写 hex 字符串。
- **第 173 行** docstring "字节摘要（sha256 hex），证据与 spec_hash 共用。" — 点明两个用途：证据引用里的 hash，以及 `contract_check.py:39-40` 的 `compute_spec_hash` 里的 spec_hash。
- **第 174 行** `return hashlib.sha256(data).hexdigest()` — 标准库 sha256，`hexdigest()` 出十六进制。没有自定义、没有加盐，同一份字节永远得到同一 hash —— 这是"结论对象可逐字段比较、重复测试一致（I13）"的基础。
- **第 177 行** `def canonical_json(value: JsonValue | object) -> str:` — 稳定序列化函数。
- **第 178 行** docstring "稳定序列化：键排序、无多余空白、UTF-8 原样输出。" — 三个承诺对应下一行的三个参数。
- **第 179 行** `return json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` — 三个参数逐个讲：
  - `sort_keys=True`：字典键排序，所以 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 结果相同 —— `contract_check.py:39` 的 docstring "spec_hash = sha256(canonical_json(spec))，与字段顺序无关"正是由此保证。
  - `separators=(",", ":")`：去掉默认 `", "` / `": "` 中的空格，避免同一对象因空白差异得到不同 hash。
  - `ensure_ascii=False`：中文等非 ASCII 字符按 UTF-8 原样输出，不转义成 `\uXXXX`；否则同一中文字符串在"转义/不转义"两种写法下 hash 不同。
- 这三个参数合起来，才是 §0 不变量 3"证据带 hash"以及 `entry.py:311-314` 缓存键可复现的技术根因；前面只是"一句话带过"，这里给出完整定义。
- 调用点（全 `services/` grep）：`evidence.py:33,47`（报告/逐例落证）、`entry.py:163`（payload 注入 stdin）、`entry.py:313`（缓存键中 manifest_draft 的 hash）、`contract_check.py:40`、`output_guard.py:265,268`。把这些摘要拼成引用的是下面的 `make_object_ref`。

### 12.4 第 182–192 行：`make_object_ref` / `parse_object_ref` —— 生成与 fail-closed 解析

- **第 182 行** `def make_object_ref(key: str, data: bytes) -> str:` — 生成带 hash 引用的唯一入口。
- **第 183 行** docstring "生成带 hash 的对象引用。"
- **第 184 行** `return f"{key}{_REF_SEPARATOR}{sha256_hex(data)}"` — 把 key、第 36 行分隔符、第 174 行摘要拼成 `{key}#sha256:{hex}`。**格式只在这里拼**，所以 `ports.py:261 build_object_ref` 直接委托它，不重复实现。
- **第 187 行** `def parse_object_ref(ref: str) -> tuple[str, str]:` — 解析入口，返回 `(key, expected_hash)`。
- **第 188 行** docstring "拆分引用为 (key, expected_hash)；格式非法 fail-closed。" — fail-closed 是关键词：非法引用必须抛错，不能静默返回空 key/hash。
- **第 189 行** `key, separator, digest = ref.partition(_REF_SEPARATOR)` — 用同一个常量切分。`partition` 只切第一个分隔符，key 里即便含 `#sha256:` 也不会错切到后面；找不到分隔符时 `separator` 为空串。
- **第 190 行** `if not separator or not key or len(digest) != 64:` — 三个校验：必须有分隔符、key 不能为空、digest 必须正好 64 字符（sha256 hex 长度）。任一不满足即非法。
- **第 191 行** `raise ValueError(f"invalid object ref: {ref[:80]}")` — 抛 ValueError（fail-closed）。只截取前 80 字符，避免把超长/恶意引用整段写进日志。
- **第 192 行** `return key, digest` — 合法引用返回二元组，交给调用方（如 `ports.py:136`）做 GET + 重算 hash 比对。
- 消费链：`ports.py:136` `S3EvidenceStore.get` 用它拆出 key 与期望 hash → `:141` 重算实际 hash → `:142-143` 不等则抛 `CONTRACT_MISMATCH`（A17 防篡改，§2 已逐行讲）。

### 12.5 第 97–111 行：`EvidenceRefs` 七字段逐行（含第六位后可省略第七位的原因）

- **第 97 行** `@dataclass(slots=True, frozen=True)` — 不可变 + 无 `__dict__`，对应 §0 "结论对象不可变、可逐字段比较（I13）"。
- **第 98 行** `class EvidenceRefs:` — 证据包引用集合，每一项都是 `key#sha256:{hex}`。
- **第 99–103 行** docstring：明确 `snapshot_ref` 是 DOM 序列化 html（结构证据），`snapshot_png_ref` 是 headless Chromium 真像素截图（R8/R13）；"后者末尾追加且默认 None，降级路径构造兼容"——这正是第 111 行默认值的用意。

- **第 106 行** `report_ref: str` — 报告 JSON 引用（check_report.json）。
- **第 107 行** `snapshot_ref: str | None` — DOM 序列化 html 引用；可空，快照失败时允许没有结构证据。
- **第 108 行** `case_refs: tuple[str, ...]` — 逐例明细引用元组（cases/*.json）；用 tuple 而非 list 保持不可变。
- **第 109 行** `compiled_ref: str` — 编译产物引用（compiled.js）。
- **第 110 行** `compiled_hash: str` — 编译产物 hash，与 `compiled_ref` 内 hash 对应，供缓存键/比对使用。
- **第 111 行** `snapshot_png_ref: str | None = None` — **第七个字段，末尾追加且默认 None**。这就是 doc:325 / doc:413 里 `EvidenceRefs("", "", None, (), "", "")` 六位位置参数仍然合法的原因：第六位之后可以省略第七位，取默认值 None。降级路径（`entry.py:264,365,402`）正是靠这个默认值在没有 Chrome 时构造证据包，不伪造 png。

### 12.7 与落证/回读的调用关系（hash 链闭环）

- `make_object_ref` 只在 `ports.py:261 build_object_ref` 被调用；`parse_object_ref` 在 `ports.py:136 get` 被调用。
- `S3EvidenceStore.put`（`ports.py:126-132`）用 `hashlib.sha256(payload).hexdigest()` 直接算 hash 放进 `ObjectRef`（`:132`），调用方（如 `compile.py:35-36`、`evidence.py:33/47`）再拼成 `#sha256:` 引用。
- `verify_evidence_refs`（`evidence.py:64-83`）逐项 `get` 触发 `:136-143` 的 hash 回读比对；`entry.py:269` 的 `passed = reason is None and evidence_ok` 正是这一环的结果。
- 因此 hash 链是：**`canonical_json` 稳定序列化 → `sha256_hex` 摘要 → `make_object_ref` 拼引用 → `get` 用 `parse_object_ref` 拆回 → 重算 hash 比对**。任何格式变化只需改 `output_ports.py` 一处。

- **第 163–169 行** `RepairCounterPort.count(self, run_id: str) -> int`：`:165` docstring "回边计数只读端口；实现由 M03/M07 注入，M08 不自行累加"；`:169` `...` 方法体省略。避免 M08 与调度层两处计数漂移。
- **设计要点**：`{key}#sha256:{hex}` 由 `_REF_SEPARATOR` 单点定义，`make_object_ref` / `parse_object_ref` 一对函数收口生成与解析，读取方端口强制校验；`EvidenceRefs` 用 `frozen` + 末尾追加可空字段，同时满足"不可篡改"与"降级兼容"。
