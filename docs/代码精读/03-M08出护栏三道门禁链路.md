## 0. 读前GPS

模型生成的 TSX 代码是**不可信数据**。在它被送进沙箱真正执行之前，系统必须先用确定性代码（零模型判定）把它过一遍又一遍地筛——这就是「三道门禁」。三道门是串联短路的：前一道不放行，后一道根本不会被执行，沙箱更不会被创建。

**为什么要三道门、而不是一道？**

- 一道门无法同时兼顾「结构合法」「意图/内容安全」「与规格一致」。三者失败的后果不同，混在一个函数里会让失败原因不可归因、不可修复。
- 三道门各自有独立的真相源：出护栏看 spec 与 AST，契约校验看 spec↔manifest↔AST 的交叉一致性，沙箱看真实运行结果。分层后每一层都可独立复算、独立留证。

**数据流（三个结论对象层层包裹）：**

- `ValidateResult` 是总汇总，内含 `output_guard: OutputGuardReport`、`contract_check: ContractCheckReport`、`sandbox_test: SandboxResult | None`。
- `SandboxResult` 内含 `evidence_refs: EvidenceRefs`（log / report / snapshot / case / compiled / snapshot_png 六类证据引用）。
- 所有证据引用统一为 `{key}#sha256:{hex}` 形态（`make_object_ref` 生成、`parse_object_ref` 校验）；报告里只留 hash 与节点类别，不留敏感词原文（ADR-005）。

**三道门分别拦什么：**

1. **第一道 · 出护栏（`check_output_guard`）**：六类判据——schema 合法性、能力白名单、AST 禁止内容（eval/外联/未知 import/系统 API）、PII、描述符合度、规格一致性。任一命中即 `hit=True`，短路，不进第二道。
2. **第二道 · 契约校验（`check_contract`）**：spec↔manifest↔代码三方比对——manifest 必填字段、能力集合双向差集、import 白名单、bridge 能力调用点、grid 一致、`spec_hash` 绑定。任一不等即 `passed=False`，短路，不建沙箱。
3. **第三道 · 沙箱（`run_sandbox`，在 entry.py 中）**：真实编译 + headless 运行 + 快照留证。前两道只是静态判定，这一道才是动态实证；沙箱不可用也绝不判通过（fail-closed 降级）。

**核心不变量（贯穿全部六个文件）：**

- **零模型判定**：六判据与三方比对全部是确定性代码，不调 LLM、不调外部服务（除只读源码引用）。不这么写，判定结果就不可复现，I13「重复测试一致」直接失效。
- **六判据**：schema / 能力白名单 / 禁止内容 / PII / 描述符合度 / 规格一致，缺一就会漏掉一类攻击面（如漏 PII 会把手机号带进产物，漏禁止内容会让 eval 绕过沙箱）。
- **spec_hash 绑定**：`spec_hash = sha256(canonical_json(spec))`，manifest 里必须写对。不这么写，spec 与 manifest 可各自漂移，校验就失去锚点。
- **fail-closed**：源码不可读、AST 解析失败、证据没写齐、留证表写失败——一律判失败/拒绝，绝不静默放行。不这么写，「无法校验」会被误当成「校验通过」。
- **命中不进沙箱**：出护栏 `hit=True` 或契约 `passed=False` 时，`validate_and_test` 直接 finalize，沙箱根本不启动。不这么写，恶意代码就会在沙箱里被真实执行。

**一句话记忆**：不可信代码先过「六判据出护栏 → spec↔manifest↔AST 三方比对 → 沙箱实跑」三道门，任一命中立即短路且绝不进沙箱，全程零模型、只留 hash 证据、任何异常都 fail-closed。

## 1. output_ports.py 逐行讲解（192 行）

这是 M08 的**端口与结论对象定义文件**：所有跨阶段传递的数据形状都在这里定死。它不改 M06 的 `ports.py`，而是另起一套「新端口协议」。核心设计是：结论对象全部 `frozen=True`（不可变）+ `slots=True`（省内存、防误加字段），保证结论一旦产出就不可被下游篡改——这是「校验结果不可伪造」的物理基础。

- **第 187-192 行** `def parse_object_ref(ref: str) -> tuple[str, str]:`

## 9. 两条护栏链的边界与并列关系（订正心智图接线）

旧版文档把 `guardrail_adapter.py` 画成"三道门的上游"，这是**链路关系表述错误**。真实情况是两条并列链：

- **输入侧（M06，进 LLM 前的门禁）**：`worker.py:172 build_validator` → `services/orchestrator/validate_chain.py:238 check_input` → 规则注册表 / 敏感词 / 危险调用 / 意图 / 预算五类短路（第 8 章）。`guardrail_adapter.py` 是这一侧的**装配模块**，产出 `ValidationResult` 交给 dispatcher。
- **输出侧（M08，进沙箱前的门禁）**：`entry.py:289 validate_and_test` → 出护栏 → 契约 → 沙箱（第 7 章）。

两者之间**没有"adapter 流转进三道门"的直接代码接线**：`check_input` 的结论经 dispatcher / M07 流程间接影响后续生成，而三道门入口是独立的 `validate_and_test`。并列关系的实质是：两条链都遵循**零模型、确定性、命中即短路、留证只留 hash、异常 fail-closed**；输入侧在模型调用前挡住不可信输入，输出侧在沙箱执行前挡住不可信产物，分别守住"进模型"与"进沙箱"两道边界。

端到端时序（真实调用现场）：

```
worker.py:172  build_validator（装配输入侧，guardrail_adapter.py）
        │
        ▼
validate_chain.py:238  check_input（第 8 章四件套 + 意图/预算短路）
        │  未命中才继续
        ▼
（M07 生成 TSX 产物）
        │
        ▼
entry.py:289  validate_and_test（第 7 章三道门）
        ├─ check_output_guard  hit → 短路，绝不建沙箱
        ├─ parse_tsx → check_contract  not passed → 短路，绝不建沙箱
        └─ run_sandbox（七阶段 + 证据写）/ 沙箱不可用 → 降级，绝不判通过
```

因此第 7 章的心智图（现第 10 章）底部"共用底座"处已把 `guardrail_adapter.py` 标注为**输入侧装配、非本链上游**；第 6 章开头与设计要点处也已同步订正。

## 11. 细节速记卡

| 记忆点 | 结论 | 不这么写会怎样 |
|---|---|---|
| 门禁顺序 | 出护栏 → 契约校验 → 沙箱，短路串行 | 前置失败仍继续执行，恶意代码进沙箱被真实执行 |
| 出护栏通行证 | `hit=False` 才进第二道门 | `hit` 与 `passed` 混用会误放命中代码 |
| 六判据 | schema/能力/AST禁内容/PII/描述符合/规格一致 | 缺一类漏一类攻击面（漏 PII 泄露隐私、漏禁内容 eval 绕过） |
| 零模型 | 全部确定性代码，无 LLM/外部服务 | 结果不可复现，I13 重复测试不一致 |
| AST 判定 | 状态机 token + 相邻位置，非全文正则 | 字符串/注释里的 `fetch` 被误判，或真实调用被漏判 |
| AST 缺失 | 记 violation（fail-closed） | "无法校验"被当成"校验通过"，无 AST 也放行 |
| spec_hash | `sha256(canonical_json(spec))`，manifest 必须写对 | spec 与 manifest 各自漂移，比对失去锚点 |
| 能力双向查 | spec_only 与 manifest_only 都要查 | 只查单向漏掉"manifest 偷偷多声明能力"的提权 |
| import 白名单 | 仅 `react`、`@widget/bridge` | 代码 import 任意外部模块，沙箱内任意加载 |
| 证据引用 | `{key}#sha256:{hex}`，读取方校验 hash | 引用对象被调包无法发现（违反 A17） |
| 报告留证 | 只留 hash 与规则名，不留敏感原文 | 报告本身成为 PII 泄露源（违反 ADR-005） |
| 结论不可变 | `frozen=True` + `slots=True` | 下游可篡改校验结论，伪造"已通过" |
| 沙箱通过条件 | 证据写齐才 `passed=True`（I10） | 日志/快照缺失仍报成功，留下不可复核的空通过 |
| 留证写失败 | 保守拒绝放行，不降级内存 | 无证据放行，事后无法审计 |
| bridge 调用识别 | 根是 bridge 绑定名 + 参数是合法能力值 | 普通函数被误算成能力调用，或伪装调用绕过 |
| 默认导出 | 必须为 `Widget` | 宿主找不到挂载组件，运行时白屏 |
| 装配层职责 | dispatcher 只暴露轻量 ValidatorFn，重依赖封装进闭包 | 确定性失败以异常抛出，dispatcher 不 ACK 无限重试 |
