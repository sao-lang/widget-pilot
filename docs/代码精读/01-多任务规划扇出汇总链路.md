## 0. 读前GPS

**这条链路解决什么**：一次对话里用户要多个控件（"做个时钟和日历"），系统要把它拆成 N 个子任务并发跑，最后**只发一条会话级 done**；而单控件请求必须零回归地走原来的 `run()` 直路，不进规划器；ADR-011 后子任务直接走 `run()` 单 agent 内核。

**文件分三层**（按调用顺序而非字母序读）：

- **数据契约层**：`ports.py`（所有 DTO 与端口 Protocol）、`states.py`（任务状态机）、`events.py`（统一 seq 域 + 类型化事件发射）。
- **规划层**：`planner.py`（零模型事实抽取 + 有界修复 + 零模型校验）、`fanout.py`（保守触发 + fan-out 结构）、`model_ports.py`（真模型端口适配器）。
- **编排层**：`dispatcher.py`（V1 门禁 → 规划接线 → 落库入队 → 子任务执行 → fan-in 裁决）。

**关键类/函数**：`extract_facts` / `validate_plan` / `plan` / `task_id_for`（planner）；`needs_planning` / `run_fanout_planning` / `FanoutResult.should_fanout`（fanout）；`GatewayPlanLLM` / `_parse_plan`（model_ports）；`fan_in` / `emit_fan_in`（coordinator）；`dispatcher._plan_and_fanout` / `_write_task_turn` / `_fan_in_if_complete` / `process_one`。

**五条核心不变量**（读具体行会反复撞见）：

1. **确定性门禁高于模型自律**：V1 在 `plan()` 之前，命中时模型调用次数 = 0；V2 校验有错就不落库、不扇出。模型永远不能自己决定"我通过了"。
2. **零模型判定**：`needs_planning()` 只回答"要不要调规划器"，N 的裁定、描述派生、附件分配全由真实 `PlanLLM` 完成；触发用的对象词表绝不参与裁定。
3. **uuid5 幂等**：`task_id = uuid5(parent_run_id, index)`，`task_turn.id = uuid5(task_id, turn_index)`——重规划、重投、并发都不重复落行。
4. **子任务独立 run_id**：`generation_task.run_id` 有 UNIQUE 约束，租约/checkpoint/cost_ledger 都按 run_id 隔离，必须一任务一 run。
5. **全终态才裁决**：子任务不各自写会话终态；必须全部终态后由 Coordinator 幂等裁决，发唯一会话级 done + 部分失败 notice，且只有 `RUNNING/AWAITING_INPUT` 会话可写终态。

**一句话记忆**：门禁先行、模型只下结论、id 全靠 uuid5、一任务一 run、全终态一条 done。

## 1. ports.py 逐行讲解（169 行）

全文件只有两类东西：`@dataclass(frozen=True)` 的不可变 DTO，和 `@runtime_checkable` 的 `Protocol` 端口。前者防数据中途被改，后者是契约声明（方法体 `...` 不是空实现，真实实现由 pg_stores/worker 装配）。这是整条链路的"词汇表"。

### 第 1-19 行：模块 docstring 与防环导入

- **第 1 行** ``"""purity-exempt-file: ADR-006/009/010 任务层真实端口协议（方法体 `...` 均为契约声明）。`` — 文件级豁免标记：本文件方法体全是 `...`， purity 静态检查会判空实现，打这个标记才能过检。不标的话 CI  purity 门禁直接红。
- **第 2 行** 空行（docstring 内分段）。
- **第 3 行** `生产实现由 pg_stores.py / worker.py 装配；测试注入的 Fake/Stub 只在 tests/support/。` — 划清生产/测试边界。不写死这条，Fake 就可能被误装配进生产，出现"测试桩在跑生产流量"的假实现。
- **第 4 行** `关键边界：Planner 是**真实模型端口**，生产缺端点 fail-fast，` — 这是全项目反复强调的红线：规划器端口必须接真模型。
- **第 5 行** `不得静默降级为规则规划器（ADR-006 §6.7）。角色层端口已于 ADR-011 移除。` — 承接上行：没有端点就快速失败，绝不悄悄用规则兜底。不这么写，就会出现"生产环境没配模型却像模像样产出计划"的幻觉实现，用户以为用了智能规划实际上是一堆 if/else。
- **第 6 行** `"""` — docstring 结束。
- **第 7 行** `from __future__ import annotations` — 延迟求值注解，注解以字符串保存，允许引用后面才定义的类型，降低 import 顺序耦合。
- **第 9 行** `from collections.abc import Sequence` — 给 `TaskStorePort.create_many` 的批量参数标注用。
- **第 10 行** `from dataclasses import dataclass` — `dataclass` 定义 DTO（ADR-011 后不再需要 `field`）。
- **第 11 行** `from typing import TYPE_CHECKING, Protocol, runtime_checkable` — `Protocol` 定义结构类型，`runtime_checkable` 让端口能 `isinstance` 检查，`TYPE_CHECKING` 用于下面防环。
- **第 13 行** `from packages.agent_core.types import JsonObject` — 上层核心类型：JSON 对象（角色层相关类型已移除）。
- **第 14 行** `from packages.contracts.enums import GridSpec` — grid 枚举（如 2x2/3x3），让 grid 取值可枚举、可比对。
- **第 16 行** `if TYPE_CHECKING:` — 这个分支只在静态类型检查时为真，运行时不执行。
- **第 17 行** `    # 仅类型检查期引用数据类（pg_stores 反向 import 本模块，运行时 import 会成环）。` — 解释防环原因：`pg_stores.py` 反向 import 本模块，若运行时也 import 回来就构成循环导入，`ImportError` 直接让服务起不来。

### `events.schema.json` 契约同步核对

- **第 7 行** `"required": ["seq", "sessionId", "runId", "ts", "kind", "phase", "payload", "traceId"]` — 事件顶层必填字段（与 §3 `TypedEventEmitter.emit` 形状一致）。
- **第 10 行** `"seq": { "type": "integer", "minimum": 0, "description": "每会话单调递增；续传/去重游标" }` — 对应 SSE 第 641 行的 `id`。
- **第 14-17 行** `"kind": { "enum": [18 种 ...] }` — 18 种事件类型枚举（ADR-011 后不再含角色层事件）。
- **第 18-20 行** `"phase": { "enum": ["DRAFT", "RUNNING", ..., "VALIDATING", ...] }` — 契约枚举含 VALIDATING，但发射侧 `events.py:76` 默认 `"RUNNING"`，全仓无代码把 phase 置为 VALIDATING（见 §17）。
- **第 44 行** `"taskId": { ... "done/error 带此字段=子任务级，不带=会话级（仅会话汇总可发）" }` — 解释 §11/§9 反复强调的"会话级 done 不带 taskId"：这是**契约层**的规定，不是实现细节。
- **第 45-46 行** `taskIndex / turn` — 两个归因字段；加上 `taskId` 共三个，与 §3 `emit` 的三个可选归因关键字参数（task_id/task_index/turn）一一对应，另加 `phase` 参数由 §9 第 734-739 行的 emitter 实际填入。

**本节结论**：消费侧闭环为 `emit → Redis Stream → events.since(Last-Event-ID) → SSE id/event/data`，seq 即续传游标；`tasks[]` 摘要把 §11 的 bundle_ref 暴露给前端，REST 端点把 §10/§14.3 的三链读出；契约的 18 种 kind 与 3 个归因字段与任务层事件形状一致，但 phase=VALIDATING 尚未落地。

## 19. 细节速记卡

- **V1 门禁在 `process_one` 第 767 行**，命中第 769 行直接 return 1——规划任务也先过门禁，`plan()` 第 209 行承诺"V1 命中时模型调用次数 = 0"。
- **`needs_planning()` 只回答"要不要调规划器"**；N 的裁定、描述派生、附件分配全由真 `PlanLLM` 完成，对象词表绝不参与裁定（用户否决纯规则规划）。
- **单控件零回归有两道闸**：`needs_planning=False`（fanout 第 46 行）和 `len(tasks)==1`（dispatcher 第 603 行），两处都返回 `False` 走 `run()` 直路；ADR-011 后子任务直接走 `run()` 单 agent 内核。
- **`task_id = uuid5(NAMESPACE_URL, "wp:task:{parent_run_id}:{index}")`**（planner 第 47 行）；随机 uuid4 会让重规划重复落行、fan-in 总数错。
- **子任务 run_id 必须独立 uuid4**（dispatcher 第 613 行）：`generation_task.run_id` 有 UNIQUE，且租约/checkpoint/cost_ledger 按 run_id 隔离。
- **入队带 `_FIELD_PLANNING: "0"`**（第 645 行）：否则子任务再次进入规划分支，递归扇出。
- **V2 幻觉附件 id → `CONTRACT_MISMATCH` → 硬拒绝 fail**（第 591-601 行）：不落 generation_task、不挂起等不存在的澄清。
- **`rationale` 含"依赖/先做完/之后再/depends on" → `CLARIFICATION_REQUIRED`**（planner 第 129 行）：v1 不支持 DAG，并行跑会让两个控件互相缺失。
- **`max_tasks` 双重夹逼 `[1,8]`**（planner 第 83 行）；brief / rationale / ambiguous_reason 统一截断 240 字。
- **修复最多 1 次**（`_REPAIR_ONCE`，planner 第 217 行）：有界防死循环；错误以结构化三元组回灌，让模型一次修完。
- **模型输出是唯一不可信变量**：`_parse_plan` 形状门禁（model_ports 第 61-76 行）+ `validate_plan` 语义门禁（白名单、grid 一致性、依赖检测），两层都 fail-closed。
- **两类端口缺失都是 fail-fast，绝不降级**：无 PlanLLM/TaskStore → RuntimeError（第 560 行）；无 seq allocator → RuntimeError（第 729 行）。
- **子任务绝不自己写会话终态**（第 839-841 行）：全部终态后由 Coordinator 唯一裁决并发唯一 done，否则第二个 `complete()` 撞 only-RUNNING 冲突进死信。
- **会话级 done 不带 taskId**，`results[]` 是 task_id→bundle 映射；**部分成功 = COMPLETED + notice**，不新增 PARTIAL 状态（coordinator 第 55、74、84 行）。
- **fan-in 幂等三道保险**：`fan_in` 的"数量 + 全终态"双条件（第 50 行）、会话状态门只放行 RUNNING/AWAITING_INPUT（第 727 行）、`emit_fan_in` 的 `not terminal` 提前返回（第 60 行）。
- **turn id = `uuid5(NAMESPACE_URL, "wp:turn:{task_id}:{turn_index}")`**（第 678 行），`turn_index` 由 `allocate_turn` 的 advisory 锁原子分配（第 662 行）——并发迭代既不丢轮也不重行。
