## 0. 读前GPS

**这两块各解决什么**：

- **记忆管理（X3）**：让系统"记住用户偏好并越用越准"——四类写入信号（explicit/clarification/adopted_artifact/correction）经零 LLM 领域规则，落进四层记忆（工作/情节/语义/程序），下一轮按高置信门禁与衰减排序注入 prompt。
- **上下文管理（X2）**：把合法输入装配成**可缓存、可省略、不可信数据隔离**的 prompt——六个固定槽位（系统契约 → L0 能力目录 → 规程软提示 → 检索 → 附件洞察 → 用户记忆 → 会话结论），有数据端口才装配对应槽，无端口即省略而非塞占位串。

**两块的边界**：记忆管理产出"数据"（`PreferencePort.hint_text` / `ProcedurePort.hint_text` / 检索候选 / 附件洞察），上下文管理消费这些数据并决定"放在 prompt 的哪一段、以什么形式"。四端口协议在 `services` 侧（M07）与 `packages/agent_core` 侧（M03）各有一份鸭子兼容镜像。

**七个文件分层**（按链路顺序读）：

- **领域层**：`types.py`（数据模型+常量）、`learning.py`（四操作/衰减/门禁纯函数）、`repro.py`（复现指纹）。
- **契约层**：`services/memory/ports.py`（Store + 四个装配端口）、`agent_core/context/ports.py`（M03 镜像）。
- **存储层**：`pg_stores.py`（偏好/事件/程序记忆真 PG）、`fact_summary_store.py`（事实摘要真 PG）。
- **适配层**：`adapters.py`（Store → 装配端口，执行门禁+衰减）、`preference_learning.py`（信号生产写入）。
- **装配层**：`context/slots.py`（六槽位）、`context/budget.py`（token 计数/压缩）。
- **接线层**：`worker.py`（注入真端口）、`dispatcher.py`（B1 preferred_grids / B2 全字段 / enricher）、`loop/run.py`（assemble 调用点）、`api/server.py`（偏好 REST）。

**贯穿全部链路的九条不变量**：

1. **I-M1 不存 PII / 附件原文 / 历史代码**——记忆只存白名单短字段。
2. **I-M2 记忆学习零 LLM**（`call_count == 0`）——四操作、衰减、排序全是纯代码。
3. **I-M3 低权重不覆盖高权重**——`decide_operation` 的 NOOP 分支只记事件不改偏好。
4. **I-M4 清除后 version+1 且事件保留**——失效只打 `superseded_at/revoked_at`，不删行。
5. **I-M5 有 preferred_grids 时建议首位**——通过 `high_confidence_grids` 注入校验链（B1）。
6. **I-M6 preference_version 进复现指纹**——十字段之一，改偏好即换指纹。
7. **I-M7 租户隔离**——所有读取按 user_id 锚定。
8. **I-P1/P2 程序记忆零 LLM、不改规程/prompt 前缀**——只做软提示。
9. **上下文槽序固定 + 数据槽无端口即省略**——保住 caching 前缀；检索片段恒标 `[不可信数据]` 并经注入过滤。

**诚实边界**（读到时不要困惑）：

- `RetrievalPort` / `AttachmentInsightPort` 真实实现由 M10 / M05 提供，**当前未注入**，对应槽自动省略。
- `correction`（0.7）纠偏信号依赖 M08 事件，当前未接线。
- 无真实模型端点时 PlanLLM fail-fast（角色层已由 ADR-011 移除，子任务直走单 agent `run()`）；L4 IntentGateway / 分档端点 / Responses wire 待 M20。
- `fact_summary` 是建议不是门禁：读失败省略段、写失败丢证据，都不阻断主链。

**一句话记忆**：领域规则零模型、存储 hash 链 + advisory、四端口有则装无则省、槽序固定保缓存、不可信数据当数据不当指令。

## 1. types.py 逐行讲解（166 行）

**为什么先读它**：这是整个 M07 记忆子系统的「宪法」——三层记忆（语义 / 情节 / 程序）的全部数据结构、全部权重常量、全部置信度和衰减阈值都定义在这一个文件里，且它**只定义结构，不依赖 PG / 不依赖任何服务**。后面 `learning.py` 的纯规则、`ports.py` 的端口签名、`pg_stores.py` 的落库实现，全都反过来 import 这里的类型和常量。读懂这一份，后面所有「为什么是 0.7」「为什么清除不删行」都能追根溯源。

### 第 1-8 行：模块 docstring

- **第 1 行** `"""M07 记忆领域模型（v1.6，ADR-002 D-9~D-14）。` — 一句话定位归属：M07 模块、版本 v1.6、对应决策记录 ADR-002 的 D-9 到 D-14 条目。把规格出处写在第一行，读者遇到任何反直觉设计都能按图索骥回 ADR 查证。
- **第 3-5 行** docstring 主体：`三层记忆 + 轻量程序记忆的纯数据结构：语义记忆 ``UserPreference``（每字段证据化）、` / `情节记忆 ``PreferenceEvent``（只追加、失效不删行）、程序记忆 ``UserProcedure``` / `（零 LLM 采纳计数）。本模块只定义结构，不依赖 PG / 任何服务，便于领域规则与存储解耦。` — 一口气交代三件核心事实：① 三层记忆各自的类名与语义（语义=带证据的偏好聚合、情节=只追加的事件流水、程序=纯计数）；② **「失效不删行」和「零 LLM」从模块头部就钉死**，这是后面 I-M4 和 I-P2 的总纲；③ 本模块**零外部依赖**（不 import PG、不 import service），所以领域规则（`learning.py`）和存储实现（`pg_stores.py`）可以各自独立演进、互不污染——这就是「领域与存储解耦」。
- **第 7 行** `类型约定：确定字段显式声明；JSON 边界用 ``JsonValue``；零裸 ``Any``。` — 类型纪律：确定的字段写确定类型，只有跨 JSON 序列化边界的值才用 `JsonValue` 兜底，且**全文件零裸 `Any`**。为什么禁裸 `Any`：一旦用 `Any`，类型检查器就放弃对该字段的全部校验，PII 原文、任意结构都能混进偏好值，I-M1（不存 PII / 原文）就失去静态防线的第一道闸。
- **第 8 行** `"""` — docstring 收尾。

### 第 9-15 行：imports

- **第 9 行** `from __future__ import annotations` — 延迟注解求值：让 `str | None`、`dict[...]` 这类注解在 Python 3.10 以下也不立即求值，同时支持类体内前向引用。记忆模型互相引用（如 `UserPreference` 的 `fields` 指向 `FieldEvidence`）时尤其需要。
- **第 11 行** `from dataclasses import dataclass, field` — `dataclass` 用于声明四个纯数据类；`field` 专为 `UserPreference.fields` 的可变默认值服务（见第 104 行）。
- **第 12 行** `from datetime import UTC, datetime` — `datetime` 供第 166 行取当前时刻；`UTC` 保证所有时间戳统一时区。为什么强制 UTC：证据时间戳要在 `effective_weight` 里做差算天数（learning.py 第 92 行），混用本地时区会算出错误的 `age_days`，直接搞错衰减档位。
- **第 13 行** `from enum import StrEnum` — 三个白名单枚举（`PreferenceField` / `PreferenceSource` / `PreferenceDecision`）都用它；`StrEnum` 成员既是枚举又是字符串，落库为字符串、比较时又是类型安全的枚举。
- **第 15 行** `from packages.agent_core.types import JsonValue` — 唯一的外部类型依赖：JSON 边界类型。全文件只有它跨包，印证了第 5 行「不依赖 PG / 任何服务」的承诺。

### 第 17-36 行：具名常量（禁魔法值）

- **第 17 行** `# --- 具名常量（禁魔法值）---------------------------------------------------` — 分区注释，明确下面全部是具名常量。为什么禁魔法值：0.7、30、180 这些数如果散落在规则代码里，改一处漏一处就会让「写入时用一套阈值、检索时用另一套阈值」，具名后所有模块 import 同一份，改一次全链路同步。
- **第 19 行** `PREFERENCE_VERSION_INITIAL: int = 1` — 偏好初始版本号，首次写入从 1 起。
  - **为什么是 1 而不是 0**：把 0 留给「无记录 / 未初始化」哨兵。这样 `PreferenceStorePort.get` 在无记录时也能返回 `version=1` 的空偏好（ports.py 第 32 行），调用方拿到任何真实偏好都能断言 `version >= 1`，不会出现「0 到底是空还是第一版」的歧义。版本号进复现指纹（I-M6），任一有效写入 `+1`（第 100 行注释）。
- **第 20 行** `"""用户偏好初始版本号（首次写入从 1 起）。"""` — 常量 docstring，说明取值语义。
- **第 21 行** `DECAY_RECENT_DAYS: int = 30` — 近期强化窗口 = 30 天。
  - **为什么是 30**：约一个月，是「用户最近仍然偏好这个」的合理时间尺度——一个月内更新过的偏好视为仍然新鲜、值得加权。窗口内证据权重乘 `DECAY_RECENT_FACTOR`（下一行）。
- **第 22 行** `"""近期强化窗口（天）：窗口内证据权重乘 ``DECAY_RECENT_FACTOR``。"""` — 说明该常量的用法。
- **第 23 行** `DECAY_RECENT_FACTOR: float = 1.5` — 近期强化系数 = 1.5（ADR-002 D-11）。
  - **为什么是 1.5 而不是 2 或 3**：要拉开近期证据的排序优先级，但不能放大到让单次近期信号压过多次高权重历史证据。1.5 是「温和强化」——既让近期条目上浮，又不至于让老证据永无出头之日；配合第 88 行「不裁剪到 1 以上」，排序只看相对值，1.5 足够形成区分度。
- **第 24 行** `"""近期强化系数（ADR-002 D-11）。"""` — docstring 指明规格出处。
- **第 25 行** `DECAY_STALE_DAYS: int = 180` — 陈旧窗口 = 180 天。
  - **为什么是 180**：约半年，与 `EVENT_TTL_DAYS`（第 29 行）取同一个尺度。超过半年的偏好大概率已过时，但**只降权不删除**——用户可能换了项目后又回来，删了就再也学不回来。
- **第 26 行** `"""陈旧窗口（天）：超过则证据权重乘 ``DECAY_STALE_FACTOR``，只降权不删除。"""` — **关键纪律**：明确「只降权不删除」，这是历史不删原则在衰减维度上的体现。
- **第 27 行** `DECAY_STALE_FACTOR: float = 0.3` — 陈旧降权系数 = 0.3（ADR-002 D-11）。
  - **为什么是 0.3 而不是 0**：0 等于删除（排序永远沉底、再也不会被选中），而 0.3 让陈旧证据保留微弱的入选机会——当所有新证据都不满足条件时，老证据仍可作兜底。降权幅度足够大（打到三成），保证它不会在正常场景里挤掉新证据。
- **第 28 行** `"""陈旧降权系数（ADR-002 D-11）。"""` — docstring。
- **第 29 行** `EVENT_TTL_DAYS: int = 180` — 情节记忆 TTL = 180 天。
  - **为什么是 180**：与陈旧窗口同为半年，语义一致——半年前的「谁在何时写了什么」审计价值衰减，但**到期只失效不删行**（第 30 行），因为事件流水是审计链（含 `row_hash` 防篡改，第 125 行），删行就断了哈希链、审计不可自洽。
- **第 30 行** `"""情节记忆 TTL（天）：到期失效不删行。"""` — docstring 钉死「不删行」，对应 I-M4。
- **第 31 行** `HIGH_CONFIDENCE_WEIGHT: float = 0.7` — 高置信门禁权重阈值 = 0.7（D-11）。
  - **为什么是 0.7**：对照 `SOURCE_WEIGHT`（第 65-70 行）——EXPLICIT=1.0、CLARIFICATION=0.8、CORRECTION=0.7 都 ≥0.7，能**仅凭权重**单独入选；ADOPTED_ARTIFACT=0.3 达不到，必须靠第 33 行的「证据数 ≥2」间接入选。0.7 这条线精准地把「用户亲口说的（显式/澄清/纠正）」和「系统推断的（采纳产物）」分成两档，正是 I-M3 / I-M1 的量化边界。
- **第 32 行** `"""高置信门禁权重阈值（D-11）：``weight >= 0.7`` 或 ``evidence_count >= 2``。"""` — docstring 点明「或」关系：权重和证据数是**两条独立通路**，满足其一即可，由第 59-62 行的 `is_high_confidence` 实现。
- **第 33 行** `HIGH_CONFIDENCE_EVIDENCE_COUNT: int = 2` — 高置信证据数阈值 = 2（D-11）。
  - **为什么是 2**：单条低权重证据可能是噪声（比如用户偶然采纳一次），两条则构成「重复出现」的最小证据。2 让采纳类（ADOPTED_ARTIFACT）信号需要至少两次才够格进记忆槽，避免一次性行为被当成稳定偏好。
- **第 34 行** `"""高置信门禁证据数阈值（D-11）。"""` — docstring。
- **第 35 行** `PROCEDURE_ADOPT_MIN: int = 2` — 程序记忆注入的最小采纳次数 = 2（D-14）。
  - **为什么是 2**：与证据数阈值同理——采纳一次可能是手滑，两次才说明用户真的反复用了这个 recipe/控件结构。达到 2 才作为「软提示」注入（I-P2：纯计数、零 LLM 判定），不足 2 则 `hint_text` 返回空串省略该槽（ports.py 第 156 行）。
- **第 36 行** `"""程序记忆注入的最小采纳次数（D-14）：``adopt_count >= 2`` 才作为软提示。"""` — docstring 绑定判定式与阈值。

### 第 39-44 行：`PreferenceField` 白名单枚举

- **第 39 行** `class PreferenceField(StrEnum):` — 可学习偏好字段枚举。
- **第 40 行** `"""可学习的偏好字段（白名单，防止学进 PII / 历史代码）。"""` — **I-M1 的核心防线**：明确这是白名单，作用就是「防止学进 PII / 历史代码」。为什么用白名单而非黑名单：黑名单永远列不全 PII 的变体（手机号、邮箱、人名、代码片段……），而白名单只允许三种与视觉偏好相关的结构化字段进入，其余一切信号在类型层就被挡在记忆之外——这是「不存 PII / 原文」最经济的静态保证。
- **第 42 行** `PALETTE = "palette"` — 配色偏好。
- **第 43 行** `PREFERRED_GRIDS = "preferred_grids"` — 偏好的网格布局。
- **第 44 行** `PREFERRED_WIDGET_TYPES = "preferred_widget_types"` — 偏好的控件类型。三值都是结构化短值，不是用户原话；即使这句话本身「原文」很长，能落库的也只有这三个字段的枚举/短列表值。

### 第 47-53 行：`PreferenceSource` 来源白名单枚举

- **第 47 行** `class PreferenceSource(StrEnum):` — 写入信号来源枚举。
- **第 48 行** `"""写入信号来源（D-10 四类白名单）。"""` — 四类来源也是白名单：只认这四种，任何未登记的渠道无法写入，避免权重表（`SOURCE_WEIGHT`）出现 KeyError 或绕过权重管控。
- **第 50 行** `EXPLICIT = "explicit"` — 显式声明：用户直接说「我要蓝色」，权重最高（1.0）。
- **第 51 行** `CLARIFICATION = "clarification"` — 澄清：用户回答追问时确认的偏好，权重 0.8。
- **第 52 行** `CORRECTION = "correction"` — 纠正：用户改正系统先前的判断，权重 0.7。
- **第 53 行** `ADOPTED_ARTIFACT = "adopted_artifact"` — 采纳产物：系统推断「用户接受了生成物」而来，最弱（0.3），因为它不是亲口陈述、可能只是懒得改。

### 第 56-62 行：`PreferenceDecision` 四操作枚举

- **第 56 行** `class PreferenceDecision(StrEnum):` — 写入决策枚举。
- **第 57 行** `"""写入四操作决策（D-10，写入时裁定冲突）。"""` — 关键语义：**写入时**裁定冲突，不是读取时。即新信号来时就决定它是 ADD / UPDATE / DELETE / NOOP 之一，决策结果随事件落库，读取时无需再算一遍——保证「同输入同决策」的可复算性与审计可追溯。
- **第 59 行** `ADD = "ADD"` — 字段原本为空，首次写入。
- **第 60 行** `UPDATE = "UPDATE"` — 新权重 ≥ 旧权重且值有变化，覆盖写入。
- **第 61 行** `DELETE = "DELETE"` — 用户清除，走独立入口（`clear`），不在纯函数里判定。
- **第 62 行** `NOOP = "NOOP"` — 值无变化或新权重更低，什么都不做——这是 I-M3「低权重不覆盖高权重」的落点。

### 第 65-71 行：`SOURCE_WEIGHT` 来源权重表

- **第 65 行** `SOURCE_WEIGHT: dict[PreferenceSource, float] = {` — 来源→固定权重映射。
- **第 66 行** `PreferenceSource.EXPLICIT: 1.0,` — 显式=1.0：用户亲口说，最高权威。
- **第 67 行** `PreferenceSource.CLARIFICATION: 0.8,` — 澄清=0.8：被追问后确认，略低于直接陈述但仍强。
- **第 68 行** `PreferenceSource.CORRECTION: 0.7,` — 纠正=0.7：改错，权威但针对的是修正动作；恰好卡在高置信阈值线上。
- **第 69 行** `PreferenceSource.ADOPTED_ARTIFACT: 0.3,` — 采纳产物=0.3：最弱、纯推断，所以永远不能覆盖前三档。

### 本文件设计要点

`types.py` 是整个记忆子系统的类型与常量单一真相源。三层记忆被压缩成四个纯数据类：`UserPreference`（语义，每字段证据化 + 全局版本）、`PreferenceEvent`（情节，只追加、双失效时间戳、带哈希链）、`UserProcedure`（程序，纯采纳计数）、`FieldEvidence`（字段证据快照），全部冻结或整体替换，杜绝原地篡改。七条纪律在这里全部埋下根：`I-M1` 靠 `PreferenceField` 白名单 + `JsonValue` 短值挡住 PII / 原文；`I-M3` 靠严格递增的 `SOURCE_WEIGHT` 表（1.0/0.8/0.7/0.3）；`I-M4` 靠 `superseded_at`/`revoked_at` 置位而非删行；`I-M7` 靠每个模型首位的 `user_id` 租户键；`I-P2` / `I-M2` 靠「只存计数、不存正文、不调模型」的结构本身。`PREFERENCE_VERSION_INITIAL=1` 把 0 留给「无记录」哨兵；30/180 天窗口与 1.5/0.3 系数、0.7/2 高置信双阈值、2 次采纳门槛，都是 ADR-002 给定的可调但集中管理的数——改一处全链路同步，绝不散落成魔法值。

### 本文件设计要点

`learning.py` 是 M07 的确定性规则引擎，四个公开函数覆盖写入裁定与检索排序的全链路。纯函数三不铁律贯穿始终：不读时钟（`now` 注入）、不调模型（I-M2，`call_count == 0`）、不碰存储——因此可复算、可单测，PG Store 直接复用。`decide_operation` 用「先判空 ADD、再判值不变 NOOP、最后**严格** `<` 比权重」的顺序，把 I-M3（低权重不覆盖高权重）钉死，同权重取新保证后验优先，DELETE 拆给独立 `clear` 入口保纯度。`is_high_confidence` 的「权重 ≥0.7 或证据数 ≥2」双通路分别覆盖「单条高质量」与「多条低质量」。`effective_weight` 在检索期按 30/180 天做 ×1.5 / ×0.3 三档衰减，只降权不删除、不裁剪到 1 以上、用 `max(age,0)` 防时钟漂移，`_parse_iso` fail-safe 回退 epoch 保证脏数据不中断主链。`rank_evidence` 先过滤高置信再以 `(-weight, 字段名)` 排序，字段名作平局键保证确定性。`should_inject_procedure` 用 ≥2 的纯计数判定，软提示不写 prompt 前缀（I-P1）、零 LLM（I-P2）。

### 本文件设计要点

`ports.py` 用七个 `@runtime_checkable` Protocol 把记忆读写与上下文装配全部抽象成可注入端口，只定义鸭子协议、不 import 任何实现，避免循环依赖，并让生产 PG 实现与测试 mock 无缝互换。两个 Store 端口（`PreferenceStorePort` / `ProcedureStorePort`）把 I-M4 钉进契约：`clear`「值置空 + version+1 + 事件标 revoked_at 不删行」、`record_revoke`「计数 -1、归零失效不删行、版本 +1」；I-M7 靠每个方法首位的 `user_id`、`session_id`（租户锚点）保证按租户/会话隔离。四个装配端口（Preference/Procedure/Retrieval/AttachmentInsight）对应上下文第 5/2/3/4 槽，统一遵守「未注入或无内容返回空串/空列表→省略该槽，禁止硬编码占位串冒充真实数据；生产关键端口缺失 fail-fast」；检索无结果转 notice + HUMAN_REQUIRED、附件 >20k token 只留对象键+预览，都是「诚实表达缺失、绝不编造」的体现。`ProcedurePort.hint_text` 明文 I-P1（软提示不写 prompt 前缀，防个体行为改写系统级规程、跨用户污染），`injection_text` / `hint_text` 都要求实现内部完成高置信过滤、衰减排序与阈值判定（I-P1 / I-P2）。第七个 `FactSummaryStorePort` 以 `session_id` 为租户锚点、`(0,"")` 为无事实哨兵、`append` 用 `session+turn` 唯一 + PG 失败 fail-closed，衔接起 ADR-009「每轮事实零 LLM 落库、下一轮读回接结论槽」的跨轮主线。方法体统一 `...` 并由 `purity-exempt-file` 声明为契约签名而非占位，docstring 逐参数点名、逐返回定界。
## 4. pg_stores.py 逐行讲解（454 行）

**为什么先读它**：这是 M07 记忆链的物理落点。三类记忆（语义 `user_preference` / 情节 `preference_event` / 程序 `user_procedure`）全部在这一个文件里落到 PG。它承担四件事：① 把偏好字段 + 证据 + version 存成一行；② 把每次写入追加成一条事件并用 hash 链串起来（只追加、失效不删行）；③ 用 `advisory xact lock` 串行化「读末行 hash → 算新 hash → 追加」与「读 version → +1 → 写回」，防并发断链/丢版本；④ PG 失败一律抛异常（fail-closed），**绝不降级成内存假实现**。本轮从 psycopg 直连改为 SQLAlchemy ORM：去掉了表名常量、`_sync_dsn`、`_connect_dict`、`Jsonb`、`Any` cast，改用 `Session` / `select` / `update` / `pg_insert` / `func.pg_advisory_xact_lock` 与 `control_plane.models` 里的 ORM 行类。下面逐行讲**当前版本**。

### 第 53-70 行：小工具函数（序列化 / 收窄）

- **第 53 行** `def _json_text(value: JsonValue | None) -> str:` — 把 JSON 值变成确定性文本，供 hash 复算。
- **第 54 行** `"""JSON 值的确定性文本（键排序、无空格），供 hash 与跨语言复算。"""` — 「键排序 + 无空格」是关键：同一份逻辑值无论 dict 插入顺序如何，序列化结果都一致，hash 才稳定、才能跨语言复算。

- **第 58 行** `def _encode_fields(fields: dict[PreferenceField, FieldEvidence]) -> dict[str, object]:` — 领域字段映射 → 可落 JSONB 的 dict。
- **第 59 行** `"""领域字段映射 → JSONB 可序列化的 dict（StrEnum 键转字符串）。"""` — 上一版返回 `Jsonb(...)`（psycopg 专用类型），本版改返回普通 dict，由 SQLAlchemy ORM 列类型负责 JSONB 绑定，这就是「不依赖具体 DBAPI」的具体体现。
- **第 60 行** `return {key.value: asdict(value) for key, value in fields.items()}` — `key.value` 把 `PreferenceField` 枚举转成字符串键；`asdict(value)` 把 `FieldEvidence` 展开成 `{value, source, weight, evidence_count, updated_at}`。整行即为「字段证据化」的落库形态。

- **第 65 行** `return float(value) if isinstance(value, (int, float)) and not isinstance(value, bool) else default` — `bool` 是 `int` 子类，必须显式排除，否则 `True` 会被当成 `1.0`。非数值一律回退 `default`。
- **第 68 行** `def _as_int(value: JsonValue | None, default: int = 0) -> int:` — 同理收窄为 int。
- **第 69 行** `"""把 JSON 边界值收窄为 int（非整数回退默认值，fail-safe）。"""` — 用于 `evidence_count`。

### 第 91-112 行：_event_hash（hash 链核心，关键安全逻辑）

- **第 91 行** `def _event_hash(event: PreferenceEvent, prev_hash: str) -> str:` — 复算一条事件行的 hash：输入是事件本体 + 前一条的 hash。
- **第 92-96 行** docstring：
  - **第 92 行** `"""复算事件行 hash：sha256(prev_hash + 各不可变字段的定序拼接)。` — 算法一句话：前序 hash + 不可变字段定序拼接 → sha256。
  - **第 94-95 行** `` ``superseded_at`` / ``revoked_at`` 在写入后仍会被 UPDATE，纳入 hash 会让链在正常失效流程下断裂，故只哈希写入时即确定的字段（D-13 失效后仍可验链）。 `` — **本文件最关键的例外**：这两个字段是「失效时间戳」，写入时为空，事后由 `_mark_events` / `clear` UPDATE 填上。如果把它们纳入 hash，那么一次正常的 UPDATE 失效就会让「存进去的 hash」与「重算的 hash」不一致，整条链在失效流程下全断。排除它们，才能做到「失效后仍可验链」，这正是 D-13「失效不删行还要可验」能成立的前提。
  - **第 96 行** `"""` — docstring 收尾。
- **第 97 行** `raw = "|".join(` — 用 `|` 拼接各字段（分隔符固定，防止歧义拼接）。
- **第 98-110 行** 被哈希的字段列表（**逐项都是写入时即确定、之后不再改的不可变字段**）：
  - **第 99 行** `prev_hash,` — 前一环 hash，链式结构的精髓：任何一条被改，其后所有行的 hash 都对不上。
  - **第 100 行** `event.user_id,` — 租户键进 hash：跨租户串链也能被验出（I-M7 在事件层的延伸）。

  - **第 102 行** `event.field_name.value,` — 字段名枚举值。
  - **第 103 行** `_json_text(event.old_value),` — 旧值确定性序列化（ADD 时为 `null`）。
  - **第 104 行** `_json_text(event.new_value),` — 新值确定性序列化（DELETE 时为 `null`）。

  - **第 110 行** `]` — 字段列表收尾。注意**没有** `id`、`row_hash`（自指）、`superseded_at`、`revoked_at`——前两个是数据库自增/自身，后两个是会变的失效时间。

### 本文件设计要点

1. **fail-closed 双纪律**：PG 失败抛异常（`session_scope` 传播、`record_adopt` 无返回行抛错、`_decode_fields`/`_event_from_row` 非法枚举抛错），绝不降级为内存实现；只有读取脏字段值用 fail-safe 收窄（避免一条脏数据打断整表读取）。
2. **hash 链的正确切分**：`_event_hash` 只哈希「写入时即确定的不可变字段」，`superseded_at`/`revoked_at` 因事后 UPDATE 被排除——这是 D-13「失效后仍可验链」成立的关键，否则每次正常失效都会断链。
3. **并发安全靠 advisory xact lock**：`apply`/`clear` 共用 `_PREF_ADVISORY_KEY`、`record_adopt`/`record_revoke` 共用 `_PROC_ADVISORY_KEY`，事务级锁自动释放，串行化「读-改-写」与「读末行 hash-追加」，防丢版本与断链。
4. **四操作语义**：ADD 新增、UPDATE 覆盖并失效旧证据、NOOP 只留审计事件（I-M3 低权重不覆盖高权重）、DELETE 仅在 `clear` 产生；有效写入 version+1。
5. **失效不删行（I-M4）**：`_mark_events` 只 UPDATE 失效列；`clear` = pop 值 + 打 `revoked_at` + version+1 + 追加 DELETE 事件，历史与链完整保留。
6. **程序记忆边界（I-P1/I-P2）**：只存结构化计数、不写 prompt 前缀；采纳/撤销零 LLM、下限 0、归零不删行。
7. **租户隔离（I-M7）**：所有查询/更新都带 `WHERE user_id`，偏好 upsert 以 `user_id` 为冲突键、程序记忆以 `(user_id, recipe_id)` 为冲突键；user_id 还进 hash。
8. **ORM 无关 DBAPI**：`Session`/`select`/`update`/`pg_insert`/`func` 替代 psycopg 原生 SQL 与 `Jsonb`，`_encode_fields` 返回普通 dict，DSN 由 `make_session_factory` 归一化收口。

5. **确定性**：衰减排序以字段名为平局裁决、软提示以 `(count, time)` 选最佳，同输入同输出，便于复现。

### 14.6 接线缺口诚实标注

- **已真实注入的端口**：`PreferencePort`（`PreferenceInjectionAdapter(PgPreferenceStore)`）、`ProcedurePort`（`ProcedureHintAdapter(PgProcedureStore)`）——worker 经 `_enrich_input` 注入，生产生效。
- **未注入的端口（接线缺口，非实现缺）**：`RetrievalPort` 真实实现由 **M10** 提供、`AttachmentInsightPort` 真实实现由 **M05** 提供，当前生产装配未注入；因此检索槽/附件洞察槽在现行链路中被省略。但内核侧 `_retrieval_message`（A″ 流水线）、`_attachment_message` 已完整实现，注入即可生效——这是接线缺口，不是实现缺。
- **`correction` 信号待 M08**：修正类信号（用户中途改口的 correction 反馈）当前未接入本链路的相关消费点，待 M08 落地。
- **无真实模型端点**：本分块的检索/洞察链路在现行装配中未挂真实模型端点（embedding/rerank 由上游服务负责），内核侧只做确定性 RRF/rerank 与装配；这同样是接线/部署形态问题，不是内核实现缺。

  - **为什么比描述**：描述没变就是重复提交（原 400 语义），不能误入重跑分支把正在跑的任务 Cancel 掉。
- **第 424-425 行** `# §4.2：任务中途"改需求"→ 中断当前 run 后以新描述重走。` / `# 描述未变仍是重复提交（原 400 语义），不误入重跑分支。` — 场景与防误判说明。
- **第 426 行** `run_description = req.description` — 用新描述。
- **第 427 行** `revision_kind = REVISION_DECISION_RERUN` — 打 RERUN 标记。

### 第 429-457 行：修正分支的执行

- **第 429 行** `if revision_kind:` — 命中两类之一。
- **第 430 行** `# §4.2：interrupt 幂等（RUNNING→PAUSED，PAUSED 保持），checkpoint/审计不删。`

### 第 458-489 行：else——原链路零回归

- **第 458 行** `else:` — 不是修正分支。
- **第 459 行** `# ---- 原有链路（零回归）：ADR-009 消歧 + submit_message ----`

### 第 491-512 行：入队

- **第 491 行** `# B1b：迁移成功后入队，dispatcher 消费驱动 agent loop（生产注入真实队列）`

  - **第 502 行** `"target_task_id": req.target_task_id or "",` — 多任务消歧的迭代目标。

- **第 508-510 行** `if revision_kind:` / `    # 下游据此识别修正轮次（仅两分支携带，正常路径不含该字段）。` / `    task_payload["revision"] = revision_kind` — 只有修正分支带 revision 字段。

- **第 512 行** `return _ok({"runId": row.run_id, "state": row.state.value})` — 202 已受理语义。

## 20. 细节速记卡

| 问 | 答（代码位置） |
|---|---|
| 记忆学习用模型吗？ | 不用——`learning.decide_operation` 纯代码，`call_count==0`（I-M2） |
| 低权重能覆盖高权重吗？ | 不能——NOOP 只记事件不改偏好（`learning.decide_operation`） |
| 清除偏好删行吗？ | 不删——只打 `revoked_at`，`version+1`（`PgPreferenceStore.clear`） |
| hash 链为什么排除 superseded_at/revoked_at？ | 这两列写入后还会 UPDATE，纳入会让正常失效流程断链（`pg_stores._event_hash`） |
| 并发写偏好怎么串行化？ | `pg_advisory_xact_lock(_PREF_ADVISORY_KEY)`（`PgPreferenceStore.apply`）；程序记忆用 `_PROC_ADVISORY_KEY` |
| 事实写入幂等怎么做？ | advisory lock + `ON CONFLICT DO NOTHING(index_elements=[session_id, turn_index])`（`fact_summary_store`） |
| 事实读失败会阻断吗？ | 不会——返回 `(0,"")` 省略该段（`dispatcher._read_fact_summary_with_index`） |
| 高置信 preferred_grids 从哪进校验链？ | `worker._preferred_grids_get` → `build_validator(preferred_grids_get)` [B1] |
| 四端口缺一个会怎样？ | 偏好/程序记忆是关键端口，`_enrich_input` 缺则 RuntimeError fail-fast；检索/附件端口未注入则对应槽省略 |
| 六槽位顺序能改吗？ | 不能——固定顺序保住 caching 前缀（`context/slots.assemble`） |
| 检索片段里的指令会执行吗？ | 不会——恒标 `[不可信数据]` + 注入模式过滤 + 只当数据（`_retrieval_message`） |
| token 超上限怎么办？ | 逐条试装，先砍证据不砍契约；连一条都放不下则整槽省略（`_retrieval_message`） |
| compress 时必须保留什么？ | `excluded_approaches`（`context/budget.compress_tool_messages`） |
| preference_version 影响什么？ | 进复现指纹十字段之一（I-M6），`_cost_sink` 从真实偏好读 |
| 程序记忆会改 prompt 前缀吗？ | 不会——只做"程序记忆提示："软提示，不改规程正文（I-P1） |
| 三类已实装信号是什么？ | explicit(REST PUT) / clarification(澄清点选) / adopted_artifact(采纳产物)；correction 待 M08 |
| 检索/附件洞察端口谁提供？ | M10 / M05，当前未注入，槽自动省略（不是实现缺，是接线缺口） |
| 会话修正两类分支怎么区分？ | AWAITING_INPUT+撤销词→MERGE；RUNNING/PAUSED+描述变了→RERUN（`server.post_message`） |
| 修正后历史怎么办？ | 新 run_id 重跑，checkpoint/task_turn/original_description 全部保留（`SessionService.submit_revision`） |
