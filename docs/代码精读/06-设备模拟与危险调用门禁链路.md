## 0. 读前GPS

### 设备 API 模拟解决什么

真机上的 widget 不是"想刷就刷"：Doze 低电耗模式会推迟定位与唤醒，刷新周期有系统下限（`scheduleRefresh` 30min），通知有每小时配额，定位/网络有最小间隔，存储写入有每秒上限；主线程同步任务超过 10s 会触发 ANR。如果沙箱里不模拟这些压制，生成出来的 TSX 会在"编译通过、渲染正常"的假象里过关，一到真机就被限流—— widget 卡住不更新，或者把用户电量耗光。因此链路在沙箱内用确定性的 `window.widgetDevice` mock 复刻限流/Doze/配额/耗时，并把每次调用序列化上报，交给 Python 做序列违规判定。

另一半问题是**危险调用前置拦截**：在用户描述或模型输出进入模型之前，就挡住"调用未声明/动态构造的设备 API、危险动作、危险全局调用"。命中即短路，不进模型，也不留到沙箱里去试。

### 单一事实来源

`device-apis.json` 定死约束 → Python `load_limits()` 读它得到 `DeviceLimits` → Python 把同一份对象作为 payload 的 `device_contract` 注入沙箱 → JS `loadDeviceContract()` 优先用 payload，容器内读不到文件时才退回内嵌同值副本。任何一处各自写死常量，都会导致**两处漂移**：mock 用 60s 而 detector 用 30s，于是出现"mock 放行但 detector 判违规"的假阳性，或"mock 早就把调用限流了而 detector 一无所知"的假阴性——同一份报告自相矛盾，门禁失去可信度。

### 三层

1. **契约层**：`device-apis.json`——唯一权威常量（接口白名单、限流值、阈值、结果码、违规类别）。
2. **Python 只读判定层**：`dangerous_call.py`（进模型前的词表层 + 形状层）与 `detector.py`（出沙箱后的序列判定）——纯函数、零模型、零副作用，只判定不修复。
3. **沙箱 mock 层**：`runner.js` 的 `installDeviceMock()`——装 `window.widgetDevice`，只做确定性压制建模，不接真实设备系统 API。

### 核心不变量

- **零模型判定**：危险调用与违规检测全部是字符串/正则/数值比较，不调模型；模型兜底只是可选建议，不作为门禁依据（否则判定不可复现，且破坏"命中短路不进模型"）。
- **fail-closed**：契约缺失/非法、外置词表非法、上报形状错误一律按失败处理；沙箱致命错误路径也照样输出 `device_calls: []`，不省略字段。
- **合法 API 不误报**：白名单来自契约 `api_limits` 的键，再加 `device.render.update` / `device.compute`；"未声明"以集合为准，不靠代码里硬编码接口名猜。
- **空 `device_calls` 零回归**：没有设备调用的 widget，违规结果是空元组，门禁项通过，老链路行为完全不变。
- **命中短路不进模型**：`input_guard.check_input()` 中危险调用命中立即返回 `short_circuit=True`，后续意图判定、预算判定与模型调用全部跳过。

一句话记忆：**契约一处定阈值，前置词表挡危险，沙箱 mock 演压制，序列判定出违规，空序列不扰老链路**。

## 1. device-apis.json 逐行讲解（27 行）

全文件 27 行，逐项讲。这个文件是三层共享的"宪法"：JS 的 mock 阈值、Python 的判定阈值、白名单与违规类别名，全都从这里来。

### 第 1-4 行：文件头与出处

- **第 1 行** `{` — JSON 根对象。注意它不是给某个程序读的配置片段，而是跨语言（Python/JS）共享的契约，因此必须是合法 JSON、不能有注释或尾逗号。

- **第 2 行** `"$schema": "device-apis v1 (ADR-010 §2.2 单一事实来源)",` — 自描述标签，指向 ADR-010 §2.2 并明确"单一事实来源"身份。它不参与运行期逻辑，但读者一眼知道改这个文件要走契约变更流程。不这么写：后人把它当普通配置随手改一个数字，不知道它同时约束着 mock 和检测器。

- **第 3 行** `"version": "1.0",` — 契约版本。版本化契约才能让"某次报告是按哪套阈值判的"可追溯。

- **第 4 行** `"source_note": "约束值参考 Android AppWidget/Glance 官方文档（2026-11-22 检索）：updatePeriodMillis≥30min、广播 10s ANR、Glance 建议每小时≤1次、RemoteViews 位图内存 6*w*h。",` — 记录每个数字的现实依据与检索日期。不这么写：30min、10s、6 倍这些数字就变成来路不明的魔法数，后人调值时无从判断是否突破了系统硬限制。

### 第 5-12 行：`api_limits`——六个接口的限流规格

- **第 5 行** `"api_limits": {` — 限流表的根。**关键**：这张表的键同时就是"合法设备 API 白名单"——`detector.py` 第 87 行用 `frozenset(api_limits)` 构造 `allowed_apis`。不这么写：白名单另立一份，契约加了接口而白名单没同步，合法调用立刻被误报为 `dangerous_api`。

- **第 6 行** `"device.getLocation": { "min_interval_ms": 30000, "doze_deferred": true },` — 定位：两次成功调用至少间隔 30s，且 Doze 下会被推迟。两个字段分别被 JS 的 `intervalLimited()`（runner.js 第 162 行）和 `dozeGuard()`（第 156 行）消费。

- **第 7 行** `"device.getBattery": { "min_interval_ms": 60000, "doze_deferred": false },` — 电量：最小间隔 60s，但 Doze 下不推迟。说明"是否受 Doze 影响"是**逐接口**的，不能全局一刀切；否则所有接口在 Doze 下都返回 `DOZE_DEFERRED`，widget 永远刷不出内容，real intent 被掩盖。

- **第 8 行** `"device.getNetworkStatus": { "min_interval_ms": 15000, "doze_deferred": true },` — 网络状态：间隔 15s，Doze 下推迟。

- **第 9 行** `"device.sendNotification": { "max_per_hour": 5, "doze_deferred": false },` — 通知用的是**另一种限流维度**：每小时配额而非最小间隔，属性名是 `max_per_hour`。detector 第 96 行 `_max_per_hour()` 专门读它，JS 第 178 行 `hourlyLimited()` 专门执行它。不这么写：把配额写成 `min_interval_ms`，mock 与检测器会把"1 小时 5 次"错当成"两次间隔 12 分钟"，判定维度全错。

- **第 10 行** `"device.scheduleRefresh": { "min_interval_ms": 1800000, "doze_deferred": false },` — 刷新调度：30min（1800000ms）下限。注意光靠"最小间隔"检测不够——mock 对过小的 `ms` 返回的是 `DENIED`（runner.js 第 220 行）而不是 `RATE_LIMITED`，所以 detector 第 170-179 行还必须按参数 `ms` 再做一次专项判定，否则这类违规会漏检。

- **第 11 行** `"device.storage.write": { "max_per_second": 10, "doze_deferred": false }` — 存储写入：每秒 10 次。JS 第 194 行 `perSecondLimited()` 执行，且只把写入 key 放进上报 `args`（第 205-206 行），不写内容。

- **第 12 行** `},` — 限流表结束。

### 第 13-18 行：`thresholds`——全局阈值

- **第 13 行** `"thresholds": {` — 与逐接口的 `api_limits` 相对，这里是跨接口共享的阈值。

- **第 14 行** `"full_render_per_minute": 10,` — 全量渲染阈值。detector 第 68-69 行 `full_render_per_minute` 属性读它，默认同值为 10。

- **第 15 行** `"retry_window_calls": 3,` — 重试风暴的判定窗口系数与阈值。detector 第 71-73 行 `retry_window` 读它，窗口长度 = 接口最小间隔 × 3（无最小间隔时兜底 3000ms，见第 161 行）。

- **第 16 行** `"anr_task_ms": 10000,` — ANR 阈值 10s。detector 第 63-65 行 `anr_ms` 读它，与 mock 的 `duration_ms` 上报配对（runner.js 第 235-251 行 `device.compute`）。

- **第 17 行** `"bitmap_memory_factor": 6` — 位图内存系数 6·w·h。诚实说明：本链路的检测函数**未消费**这个值，它留在契约里供渲染/内存预算侧使用；把它集中在此处，是为了不让渲染侧再写一份 6。

- **第 18 行** `},` — 阈值表结束。

### 第 19 行：`result_codes`——五种返回码

- **第 19 行** `"result_codes": ["OK", "RATE_LIMITED", "DOZE_DEFERRED", "QUOTA_EXCEEDED", "DENIED"],` — mock 可能返回的全部结果码，与 JS 各处字面量一一对应：`OK`（放行）、`RATE_LIMITED`（间隔/每秒超限）、`DOZE_DEFERRED`（Doze 推迟）、`QUOTA_EXCEEDED`（每小时配额满）、`DENIED`（参数非法，如 `scheduleRefresh` 的 `ms` 过小）。不这么写：JS 写 `"RATE_LIMIT"`、Python 第 160 行判 `"RATE_LIMITED"`，字符串对不上，`retry_storm` 检测直接全部漏检——这正是"限流后重试风暴漏检"的一个典型成因。

### 第 20-26 行：`danger_categories`——五类违规的稳定名字

- **第 20 行** `"danger_categories": {` — 违规类别表。detector 产出的 `Violation.category` 字符串就取这里的键名。

- **第 21 行** `"dangerous_api": "调用未声明或动态构造的设备 API",` — 对应 detector 第 117-121 行，以及 `dangerous_call.py` 第 94 行的 `dangerous_api:` 前缀留证。

- **第 22 行** `"high_frequency": "高频调用受限 API",` — 对应 detector 第 143-147、150-154、175-179 行（间隔、配额、`scheduleRefresh` 参数三种）。

- **第 23 行** `"render_storm": "频繁全量渲染",` — 对应 detector 第 133-137 行。

- **第 24 行** `"retry_storm": "限流后短时间内重试",` — 对应 detector 第 164-168 行。

- **第 25 行** `"long_task": "超 ANR 阈值的同步大任务"` — 对应 detector 第 123-127 行。

- **第 26 行** `}` — 类别表结束。

- **第 27 行** `}` — 根对象结束。

**本文件设计要点**：把"合法接口名单""各接口限流值""全局阈值""返回码""违规类别名"五类事实收敛到一个文件。Python 与 JS 都从这里派生，任何单边硬编码都会造成两处漂移。

## 2. dangerous_call.py 逐行讲解（103 行）

前置危险调用门禁的前两层就在这里：①词表层（危险动作短语 + 契约白名单外的接口名）；②AST/形状层（动态构造 API 名、危险全局调用）。第三层模型兜底明确不在此模块实现。

### 第 1-12 行：模块 docstring（三层分工与单一事实来源）

- **第 1 行** `"""ADR-010 §3 前置危险调用检测（确定性、零模型）。` — 一句话定位：确定性、零模型，归属 ADR-010 §3。

- **第 3-4 行** `三层中的前两层在此实现：①词表层（危险动作短语 + 契约内设备 API 白名单外的` / `接口名）；②AST/形状层（动态构造 API 名 \`device[name]()\`、字符串拼接调用）。` — 明确本模块的职责边界：只做前两层，形状层针对的是"用变量下标或字符串拼接构造接口名"这类绕过静态名单的手法。

- **第 5-6 行** `第三层便宜模型兜底是**可选建议**，不得单独放行——故不在此模块实现（无端点时` / `生产 fail-fast，且不作为门禁依据）。` — **关键纪律**：模型判定不能当门禁。如果让模型兜底"放行"，判定就变成概率性的、不可复现，而且直接违背"命中短路不进模型"——危险调用还没被挡住就先送进模型了。

- **第 8-11 行** ``危险动作词表：`patterns/dangerous_actions.json`，可由`` / `` `WIDGETPILOT_DANGEROUS_LEXICON_PATH` 按类别整体覆盖（外置非法 fail-fast），`` / ``与 ADR-005 敏感词库同纪律。危险接口名来自 `packages/contracts/device-apis.json` `` / `单一事实来源，不在代码内置具体接口名。` — 两个事实来源：动作短语来自词表文件（可外置覆盖），接口名来自契约。不这么写：在 Python 里硬编码一份 `device.xxx` 白名单，契约新增接口时忘记同步，合法 API 就被误报为危险——"合法 API 不误报"这条不变量直接破防。

- **第 12 行** `"""` — docstring 结束。

### 第 13-26 行：imports、常量与导出

- **第 13 行** `from __future__ import annotations` — 延迟注解，降低类型引用对 import 顺序的依赖。

- **第 15-19 行** `import json` / `import os` / `import re` / `from dataclasses import dataclass, field` / `from pathlib import Path` — 分别用于：读词表 JSON、读环境变量覆盖路径、两个正则匹配、`DangerVerdict` 数据类与默认工厂、路径拼接。

- **第 21 行** `from services.orchestrator.device_sim.detector import load_limits` — **关键复用**：白名单不自己算，直接调用判定层 `detector.load_limits()` 的 `allowed_apis`。这样"前置拦截认为合法"与"事后判定认为合法"用的是同一个集合；不这么写就会出现两套白名单各自漂移。

- **第 23 行** `__all__ = ["DangerVerdict", "detect_dangerous_calls"]` — 公共导出面只有判定结果与判定函数，内部正则/加载器不暴露。

- **第 25 行** `_LEXICON = Path(__file__).parent / "patterns" / "dangerous_actions.json"` — 内置词表路径，相对本文件定位，不受工作目录影响。

- **第 26 行** `_ENV_LEXICON = "WIDGETPILOT_DANGEROUS_LEXICON_PATH"` — 外置覆盖的环境变量名，集中为常量（避免魔法串散落）。

### 第 28-35 行：两条形状正则（形状层的核心）

- **第 28 行** `# 动态构造 API 名形状：device[name] / window.widgetDevice[name] / ["api"]()` — 列出要抓的三种写法。

- **第 29-32 行** `_DYNAMIC_API = re.compile(` / `r"(?:widgetDevice|device)\s*\[\s*[^\]\d'\"]|"` / `r"(?:widgetDevice|device)\s*\[\s*['\"]?[a-zA-Z_]\w*['\"]?\s*\]\s*\("` / `)` — 两支 alternation：第一支匹配 `device[非数字非引号开头]`（变量下标，如 `device[name]`），第二支匹配 `device["api"](` 或 `device[api](` 这种"下标后紧跟调用"的形态。`widgetDevice|device` 两种前缀都覆盖。不这么写：只写其中一支，另一类动态构造手法就被绕过——白名单再准也管不住"名字是运行时拼出来的"。**实测边界**：第一支 `[^\]\d'"]` 排除引号开头，所以 `device['readContacts']` 这类静态下标不命中；第二支的 `['\"]?[a-zA-Z_]\w*['\"]?` 允许带引号，会把**合法 API 的静态名下标一起吃掉**——`device["getLocation"]()` 被误报 `dynamic_api:constructed-name`。详见 §5.5。

- **第 33-35 行** `_DANGEROUS_GLOBALS = re.compile(` / `r"\b(eval|Function|fetch|XMLHttpRequest|child_process|require\s*\(\s*['\"]fs|process\.env)\s*\("` / `)` — 高危全局/模块调用：`eval`、`Function`、`fetch`、`XMLHttpRequest`、`child_process`、引入 `fs` 的 `require(...)`、`process.env`，整体要求以 `(` 跟随形成调用形态。不这么写：widget 代码里一个 `eval(...)` 或 `fetch(...)` 就能在沙箱外语义下执行任意逻辑/外联，前置层却毫无表示。**但必须标注实测边界**：末尾 `\s*\(` 对整个 alternation 统一生效，实际只有 `eval(` / `Function(` / `fetch(` / `XMLHttpRequest(` 这**四类**能命中；`child_process.exec("ls")`、`require('fs')`、`process.env.SECRET` 三种真实写法**全部抓不到**（分别要求 `child_process(`、`fs` 后紧跟 `(`、`process.env(`）。不要把这七类都当成已生效的防线——完整对照表与影响见 §5.5。

### 第 38-43 行：`DangerVerdict` 数据类

- **第 38 行** `@dataclass(frozen=True, slots=True)` — 不可变 + 无 `__dict__`，判定结果一旦产出就不能被下游改动（避免"判了 hit 又被改回 False"）。

- **第 39-40 行** `class DangerVerdict:` / `"""危险调用判定（hit=True 时 violations 含类别标签）。"""` — 结果契约：`hit=True` 时 `violations` 必定非空。

- **第 42 行** `hit: bool` — 是否命中，上游短路只看这个字段。

- **第 43 行** `violations: tuple[str, ...] = field(default_factory=tuple)` — 命中证据用不可变元组；`default_factory` 避免可变默认值共享。每条证据自带类别前缀（`dangerous_action:` / `dangerous_api:` / `dynamic_api:`），留证端可直接归类。

### 第 46-59 行：`_load_lexicon()`——词表加载与外置覆盖（fail-closed）

- **第 46-47 行** `def _load_lexicon() -> dict[str, list[str]]:` / `"""加载内置词表 + 可选外置覆盖；外置非法即抛（fail-closed）。"""` — 明确外置非法要抛异常，不静默退回内置表。

- **第 48 行** `raw = json.loads(_LEXICON.read_text(encoding="utf-8"))` — 先读内置词表作为基线。

- **第 49 行** `override = os.getenv(_ENV_LEXICON, "")` — 读环境变量；未设置时为空串，走内置表。

- **第 183-184 行** `def _as_int(value: JsonValue | None, default: int) -> int:` / `"""JSON 值安全收窄为 int（非 int/bool 返回默认值）。"""` — JSON 边界的统一收窄点，被上面所有阈值读取与参数读取复用。

- **第 185 行** `return value if isinstance(value, int) and not isinstance(value, bool) else default` — **`not isinstance(value, bool)` 不可省**：Python 中 `isinstance(True, int)` 为 True，不排除 bool 会把 `true` 当 1 参与阈值比较，产生诡异误判。这行与 `entry.py` 第 496 行同纪律（JSON 边界显式收窄）。

**本文件设计要点**：白名单来自契约且与前置层同源；五类规则按"调用序 × 规则序"稳定产出；两处兜底（`interval=0` 时窗口 3000ms、`ms=0` 放行）分别防住"重试风暴漏检"和"合法写法误报"；所有 JSON 值经 `_as_int` 一处收窄。

## 6. 类型支撑与无关项说明（types.py 1039 行 / slots.py 244 行）

### 第 40-47 行（types.py）：`JsonValue` / `JsonObject`——JSON 边界的类型约束

`detector.py` 第 19 行从此处导入 `JsonValue`，用于 `DeviceCall.args` 与 `DeviceLimits` 的字典值。

- **说明**：`types.py` 全文 1039 行，其余内容（State / Decision / GuardVerdict / 事件 / 评测结构等）与本链路无关，不在本文展开。

## 7. 上报与治理：从 `device_calls` 到门禁失败

JS 把序列写进报告后，治理发生在控制面 `services/sandbox_runner/entry.py`：

- **第 215 行** `# ADR-010 §2.3：设备 API 调用序列门禁（限流/渲染风暴/重试/大任务/危险 API）。` — 门禁位声明。
- **第 216 行** `# device_calls 缺省为空数组 → 零回归（无设备调用的 widget 不受影响）。` — 零回归纪律的注释落点。
- **第 217 行** `stages.append("DEVICE_API_ASSERT")` — 在断言阶段列表中登记本项，便于失败归因。
- **第 218 行** `device_ok = _device_calls_safe(report.get("device_calls", ()))` — 读报告顶层字段；缺省空元组，与 JS 三路径都输出空数组呼应。
- **第 219 行** `case_specs.append(("device_api_safe", device_ok))` — 作为一条断言用例留证。
- **第 223-224 行** `elif not (size_ok and runtime_ok and interactions_ok and device_ok):` / `reason = ReasonCode.SANDBOX_TEST_FAILED` — 设备调用不安全时，最终原因码走 `SANDBOX_TEST_FAILED`。

`_device_calls_safe()`（第 476-492 行）是形状校验边界：

- **第 478-479 行** `if not isinstance(raw, (list, tuple)):` / `return False  # 形状错误 fail-closed` — 顶层不是序列直接判不安全。
- **第 481-491 行** 逐条校验：第 482-483 行要求每项必须是 dict；第 484-486 行 `api` 必须是 str；第 487 行 `t_ms = max(0, _as_int(item.get("t_ms")))`；第 488 行 `code = str(item.get("code", "OK"))`；第 489 行 `args = _as_object(item.get("args", {}))`；第 490 行 `duration = max(0, _as_int(item.get("duration_ms")))`；第 491 行 `calls.append(DeviceCall(api=api, t_ms=t, code=code, args=args, duration_ms=duration))`。不这么写：形状错误直接喂给 detector，`DeviceCall` 构造或比较时抛异常，整条报告解析崩溃；这里把不可信边界收敛在一处。
- **第 492 行** `return not detect_violations(tuple(calls))` — 违规为空即安全；非空即 `device_ok=False`，触发上面的 `SANDBOX_TEST_FAILED`。

一句话串起来：**mock 上报 → 控制面收窄成 `DeviceCall` → `detect_violations` 出 `Violation` → 违规非空则门禁失败**；违规里的 `remediation` 是确定性文本，但**生产门禁 `entry.py:492` 只取布尔，并不把它交给上层生成修复建议**（见 §7.6）；判定层本身不改任何代码。

## 9. 细节速记卡

- **契约路径**：`packages/contracts/device-apis.json`，27 行；`detector.py` 第 29-31 行用 `parents[3]` 从文件位置定位，不依赖工作目录。
- **白名单组成**：`frozenset(api_limits) | {"device.render.update", "device.compute"}`（detector.py 第 87 行）；`dangerous_call.py` 第 64 行复用同一份，合法接口双形态判定（第 93 行）防误报。
- **契约三级加载**：payload → 真实契约文件 → 内嵌同值副本（runner.js 第 92-117 行）；thresholds 用 `Object.assign` 以兜底为底，防止缺键变 `undefined` 后被 `|| 0` 静默归零。
- **两处"不这么写会怎样"的高频坑**：契约两处漂移导致 mock 与 detector 互相矛盾；白名单单边维护导致合法 API 误报为 `dangerous_api`。
- **形状层开关**：只有 `source_kind == "code"` 才查动态构造 API 与危险全局调用（dangerous_call.py 第 97 行）；`input_guard.py` 第 65 行用默认 `"description"`，因此描述文本不会因出现 `device[name]` 字样被误报。
- **短路留证**：危险调用命中复用 `GuardHitType.INJECTION`、`rule_id="DANGEROUS_CALL"`、`decision=REJECT`、`excerpt[:80]`，并置 `short_circuit=True`——不置短路就会进模型。
- **`makeApi` 是唯一上报点**（runner.js 第 149 行）；`t_ms` 相对 `mountedAt`；Doze 优先且不更新限流时间戳（第 164-165 行）；被限流的调用也不更新 `lastAt`（第 172 行），否则限流状态自我延续。
- **返回码语义**：`RATE_LIMITED`（间隔/每秒）、`QUOTA_EXCEEDED`（每小时）、`DOZE_DEFERRED`（逐接口 Doze）、`DENIED`（`scheduleRefresh` 参数非法）。`retry_storm` 只认 `RATE_LIMITED` 作为起点，字符串写错就全链路漏检。
- **重试风暴双防線**：无 `min_interval` 时窗口兜底 3000ms（detector.py 第 161 行）；只数窗口内 `code == "OK"` 的重试（第 162 行）。
- **`ms=0` 放行**：`0 < ms < minimum`（第 174 行），因为 `updatePeriodMillis=0` 是交给 WorkManager 的合法写法；写成 `ms < minimum` 就误报。
- **数值收窄**：所有 JSON 边界值走 `_as_int`，显式排除 bool（第 185 行）；Python 里 `True` 是 `int` 的子类，不排除就会把 `true` 当 1。
- **零回归**：`render_storm` 只数 `mode == "full"`；未配限流的接口不参与间隔判定；空 `device_calls` 得到空违规元组，三路径都输出该字段且为空数组。
- **一条链串起来**：契约定阈值 → 前置词表/形状层挡危险 → 命中短路不进模型 → 沙箱 mock 演压制并上报 → 控制面收窄形状 → 五类违规判定 → 违规非空则 `SANDBOX_TEST_FAILED`，为空则零回归。
