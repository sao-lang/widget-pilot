## 0. 先建立整体认知

M05 回答一个问题：**把用户上传的图片/视频/文本，按"用户描述"变成带引用的 `AttachmentInsight`**。
role 不是猜的——"当背景"走视觉参考、"提取右上角日期"走 OCR，同一张图两种描述走两条路径。

三个必须刻进脑子的事实：

1. **唯一接触附件原文的域**，且原文永不进公共语料（M10 入库链路对 `att/*/original` 不可见）。
2. **每个依赖都是「Protocol 式双实现」**：对象存储、附件索引、租户守卫、处理器都有
   `InMemory*` 桩（无 Docker 跑单测）与生产实现（S3/PG/SessionStore/真实 OCR）。
   读懂这点，就理解为什么单测与真实环境跑的是同一套 `AttachmentService`。
3. **v1.7 双 confidence 拆分**：`role_confidence` 判 role 明确性（M06 消费），
   `insight_quality` 表处理结果质量（OCR 失败置低）。**绝不混用**。

```
阶段 1  入口与装配       api/main.py:create_prod_app → api/server.py:create_app(M05 段)
   ↓
阶段 2  编排心脏 ★       attachments/service.py（upload / patch_roles）
   ↓
阶段 3  纯函数决策层      sniff.py → validate.py → role_resolver.py → constants.py
   ↓
阶段 4  存储与处理器       stores.py + s3_store.py + pg_stores.py + processors.py + real_processors.py
   ↓
阶段 5  测试即文档        tests/unit/test_m05_*.py → tests/integration/test_m05_real_infra.py
```

> `models.py:Attachment` / 迁移 `0003` / `tenant_guard.py` 不单列阶段——当字典用，
> 遇到持久化字段或越权判定时回查。

## 1. 阶段 1 · 入口与装配

| 文件 | 读什么 |
|---|---|
| `api/main.py` | 生产装配全景：环境门禁 → PG 存储 + Redis 事件源 → **M05 注入** `AttachmentService(S3ObjectStore, PgAttachmentStore, SessionTenantGuard, RealProcessor)` → 挂 healthz/readyz |

## 2. 阶段 2 · 编排心脏（`service.py` 342 行，逐行读）

`AttachmentService` 是全模块唯一编排点。读懂 `upload()` 和 `patch_roles()` 两个方法，
其余都是小工具。铁律顺序：**租户校验 → 幂等 → 存原文 → 判 role → 分派处理器 → 封装洞察 → 落索引**。

### 2.1 `upload()`（77–178 行）—— 一次上传走完

| 步骤 | 代码 | 失败分支 |
|---|---|---|
| ① 归属校验 | `tenant.assert_owner(user_id, session_id)` | 403，不读文件内容 |
| ② 幂等 | `_find_by_idem`：session+description+sha256(file) | 命中直接复用旧 `attachment_id`（不重复上传） |
| ③ 存原文 | `objects.put_original` → `att/{u}/{s}/{id}/original` + sha256 | 写失败整体失败，不留悬空对象 |
| ④ 判 role | `resolve_role(description, kind)` → `(role, role_confidence)` | 歧义走澄清分支 |
| ⑤ 歧义分支 | `role=null` + `clarify_hint`，写入 `clarify_signals` | **不调 M04 置 `AWAITING_INPUT`**（B2，由 M06 判定） |
| ⑥ 处理器 | `processor.process(...)` 或静态 `dispatch(...)` | `TimeoutError`/`ValueError` → `FAILED` + `evidenceRef` |
| ⑦ 洞察 | `put_insight` → `insight_ref` 带 `#sha256:` 内容 hash | — |

**R-1 修复点**：`_find_by_idem` 跳过 `FAILED`/`REJECTED` 终态行——否则同输入重试
永远拿回失败行，无法恢复。

### 2.2 `patch_roles()`（180–228 行）—— 纠偏重跑

- **S-2 幂等**：同 role 且已 `INSIGHT_READY` → 直接返回，不重跑、不版本化。
- **S-3 双入口态**：`CLARIFICATION_NEEDED` 与 `INSIGHT_READY` 都以 `ROLE_ASSIGNED` 为起点。
- **A9**：旧洞察用 `archive_insight` 写成 `insight.v{n}.json`（只追加，不物理删），
  新洞察 ref 因带内容 hash 必然变化；**只动目标附件**，其他行不受影响。

### 2.3 小工具（速扫）

`read_insight`（hash 校验后解析）/ `serialize_extracted`（A10 红线真扫描，只扫 extracted
段——`source_ref` 按设计合法指向原文）/ `external_refs` / `_to_result`（10 字段响应）。

## 3. 阶段 3 · 纯函数决策层（无 I/O，可脱库单测）

| 文件 | 行数 | 读什么 |
|---|---|---|
| `constants.py` | 34 | 硬上限：`MAX_ATTACHMENT_BYTES`(10MiB)、`MAX_ATTACHMENTS_PER_SESSION`(5)、`ROLE_CLARIFY_THRESHOLD`(0.6)、`MAX_KEYFRAMES`；全部代码常量，无在线开关 |
| `sniff.py` | 50 | `sniff_mime(head)`：magic number 签名表（PNG/JPEG/GIF/WEBP/MP4），文本判据为"前 N 字节可打印 UTF-8 且无二进制控制字符"；未知返回 octet-stream |
| `validate.py` | 80 | `validate_transfer`：顺序固定 **kind → 声明 mime 白名单 → size → 数量 → 嗅探**，命中即短路；文本 mime（csv/json）与嗅探 text/plain 视为一致（B-1） |
| `role_resolver.py` | 64 | `resolve_role`：描述关键词 → role 纯规则表，多条命中取最高分；全不命中返回 `role=None` + confidence=0，**不调模型、不默认 role** |

**关注点**：`application/octet-stream` 是嗅探失败结果，**不能作为声明值通过**（S-4）——
否则任意二进制可绕过类型门禁成为 text 附件。

## 4. 阶段 4 · 存储与处理器（双实现可插拔）

### 4.1 三组双实现

| 接口方法 | 生产实现 | 测试桩 |
|---|---|---|
| `put_original` / `put_insight` / `get_with_hash_verify` / `get_raw` / `bump_version` / `archive_insight` | `s3_store.py`（193 行）：httpx + **AWS SigV4 手写签名**直连 MinIO（免 boto3），path-style URI `/{bucket}/{key}` | `stores.py:InMemoryObjectStore`（dict + sha256） |
| `insert` / `get` / `list_by_session` / `update` / `all_rows` | `pg_stores.py`（96 行）+ 迁移 `0003` + `models.py:Attachment` | `stores.py:InMemoryAttachmentStore` |
| `assert_owner(user_id, session_id)` | `tenant_guard.py`（23 行）：查 M04 SessionStore 归属 | `stores.py:FakeTenantGuard`（内存归属表） |

**S3 关注点**：`_signed()` 用 HMAC 链派生 signing key（secret → date → region → service →
aws4_request），`canonical_request` 六段以换行拼接；`_list()` 用 ListObjectsV2 解析 XML。
之所以不用 boto3：本机装 boto3/botocore 下载极慢，SigV4 手写约 60 行且零重依赖。

### 4.2 处理器：静态桩 vs 真实

| role/kind | 真实实现（`real_processors.py` 197 行） | 桩（`processors.py` 83 行） |
|---|---|---|
| `visual_reference` + 图片 | Pillow 真解码 → 主色（量化桶 Top-3）+ WEBP 缩略图 base64 + 尺寸；像素上限 4096 | 返回文件名字符串 |
| `content_extraction` | rapidocr-onnxruntime 区域化 OCR，含 bbox + score | 空 `ocr_text` |
| `video`（任意 role） | imageio-ffmpeg 静态二进制，`fps=1` 单次调用抽帧 ≤`MAX_KEYFRAMES`，base64 JPEG | 文件名列表 |
| `data_source` | JSON/CSV 严格解析，单元格保持字符串，**不 eval** | 简单 split |

`processor_adapter.py:RealProcessor` 是统一入口：按 `kind == "video"` 优先走视频，
否则按 role 分派。`service` 通过构造参数 `processor=` 注入——**生产注入 RealProcessor，
单测不注入（走静态桩）**，这是同一套编排跑两种环境的钥匙。

**降级契约**（§2.3）：可选依赖缺失时 `insight_quality=0` + `degraded=True`，
**不跳过校验、不动 `role_confidence`**——OCR 失败绝不能被 M06 误判为 role 歧义。

**ffmpeg 坑**：imageio 自带二进制不含 libx264/lavfi；测试素材用 image2 读 PNG 序列 +
mpeg4 编码生成 MP4，抽帧用 `fps=1` 而非逐帧 `select=eq(n,...)`。

## 6. 一条主线贯穿（自检用）

读完用 `POST /api/attachments` 自检，能讲清每跳落在哪个文件、失败返回什么码：

```
① POST /api/attachments       → server.py:upload_attachment()
② 鉴权（解码 JWT）             → current_user() → UserRow                失败 401
③ 流式限量读 + 传输校验         → validate_transfer()                     失败 413/422
④ 租户校验                     → SessionTenantGuard.assert_owner()        失败 403
⑤ 幂等命中？                    → service:_find_by_idem()                  命中复用旧 id
⑥ 存原文到 MinIO               → s3_store:put_original() → SigV4 PUT
⑦ 判 role                      → role_resolver:resolve_role()
   歧义 → clarify_signals（不置 AWAITING_INPUT，M06 判）
⑧ 真实处理器                   → RealProcessor.process() → Pillow/OCR/ffmpeg
⑨ 洞察 + PG 索引               → put_insight() + PgAttachmentStore.insert()
⑩ 响应 10 字段                 → _m05_ok()（code/message/traceId/retryable）
```

**这十步里嵌着所有修复防护点**：③ 流式读（B-2 OOM）、④ 归属（A12）、⑦ B2 澄清归属、
⑧ S1 双 confidence、⑨ 内容 hash ref（A9）、R-1 FAILED 行不复用。

## 10. 完整性审计补强（2026-11-21，六 Blocker 清零）

独立审计发现 6 个 Blocker，TDD 修复并经第二轮 fresh-context 复核：

| 编号 | 问题 | 修复落点 |
|---|---|---|
| A17 | `subprocess.TimeoutExpired` 非 `TimeoutError` 子类，真实 ffmpeg 超时逃逸 500 | `service.py` 显式捕获 + 写真实 error 对象 + evidenceRef；REST 映射 500 |
| A15 | 视频 `extracted` 无 OCR `regions`（设计要"提取画面里的日期"） | `real_processors.py` 每帧跑 rapidocr，返回 frame_index/bbox/text/score |
| A12 | `GET /api/sessions/{id}/attachments` 端点缺失 | `server.py` 补齐 + SessionTenantGuard 403（不泄漏存在性） |
| A8 | attachment/notice SSE 事件零发射 | `events.py` InMemoryEventSink + RedisEventSink；service 三处发射；main.py 生产注入 |
| N2 | 生产 `patch_roles` 走静态桩而非注入的 RealProcessor | `service.py:patch_roles` 改走 `self.processor.process(...)` |
| N4 | 幂等键非唯一 + read-then-write 竞态 | 迁移 `0004` 唯一索引 + `_insert_or_reuse` 折叠 IntegrityError |

第二轮复核又发现并修复两个**由修复引入**的 Major：
- **R-1**：FAILED 行 + 唯一索引 = 重试永久 500 → `_insert_or_reuse` 对 FAILED 行做状态刷新（保留 id）。真实 PG 验证：first=FAILED → retry=INSIGHT_READY 同 id。
- **R-2**：M05 用全局 seq 与 M04 会话 seq 冲突致 SSE 续传丢失 → `RedisEventSink.next_seq(session_id)` 改为 per-session Redis INCR。

另修 best-effort 事件（sink 故障不拖垮上传）、Pydantic 严格 `AttachmentInsight`（A14）、
`dispatch(alert_sink=)` 告警（A18）、错误响应 evidenceRef（N5）。
