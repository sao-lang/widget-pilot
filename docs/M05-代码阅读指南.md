# M05 · 附件处理域代码阅读指南

> 对应模块文档：`docs/modules/M05-附件处理域.md`（v1.1）
> 实现状态：S3 TDD 落地 + S5 独立 review 修复（2 Blocker / 6 Should 全清），40 个新增单测
> 测试：`test_m05_transfer.py`（12）、`test_m05_service.py`（7）、`test_m05_advanced.py`（8）、`test_m05_review_fixes.py`（13）

## 1. 边界一句话

把上传的图片/视频/文本，经「传输层校验 → 对象存储 → 描述判 role → 处理器分派」变成带引用的
`AttachmentInsight`；**唯一接触附件原文的域，原文永不进公共语料**。

## 2. 文件地图（服务层 `services/control_plane/attachments/`）

| 文件 | 职责 | 关键入口 |
|---|---|---|
| `constants.py` | 硬上限与阈值（代码常量，无在线开关） | `MAX_ATTACHMENT_BYTES` / `ROLE_CLARIFY_THRESHOLD` |
| `sniff.py` | magic number 嗅探（不信声明值） | `sniff_mime(head)` |
| `validate.py` | 四类传输层校验，顺序固定 | `validate_transfer(...)` → `ValidateResult` |
| `role_resolver.py` | 描述 → role 纯规则 registry（不调模型） | `resolve_role(description, kind)` |
| `processors.py` | role → handler 静态分派（A15–A18） | `dispatch(role, kind, ref)` |
| `stores.py` | 对象存储 + 附件索引 + 租户守卫桩 | `InMemoryObjectStore` / `AttachmentRow` |
| `service.py` | 上传/纠偏重跑编排 + 澄清信号 | `AttachmentService.upload/patch_roles` |

REST 接线在 `services/control_plane/api/server.py` 的 `create_app(..., attachment_service=...)`：
`POST /api/attachments`（上传）、`PATCH /api/sessions/{id}/attachment-roles`（纠偏）。

## 3. 数据怎么流（上传一次的完整路径）

```
1. UploadHandler 读 multipart → validate_transfer（kind→size→数量→嗅探，任一不过短路）
2. TenantGuard.assert_owner（越权 403，不读文件内容）
3. 幂等键 = session:description:sha256(file)；命中复用同一 attachment_id
4. ObjectStore.put_original → att/{user}/{session}/{id}/original + sha256
5. RoleResolver.resolve_role → role + role_confidence（纯规则，最高分命中）
6. 歧义（role=None 或 confidence<0.6）→ role=null + clarify_hint，**不调 M04 置状态**（B2）
7. 明确 → dispatch 处理器 → AttachmentInsight{source_ref, extracted, insight_quality}
8. put_insight → insight_ref 带 `#sha256:` 内容 hash（内容变 ref 变，A9）
```

## 4. 三条最容易踩的设计约束

1. **v1.7 S1 双 confidence**：`role_confidence` 判 role 明确性（M06 消费）；
   `insight_quality` 表处理结果质量（OCR 失败置低）。**不可混用**——OCR 失败不得把
   `role_confidence` 置 0，否则 M06 误判 role 歧义。
2. **v1.7 B2 澄清归属**：M05 只产出澄清信号（`clarify_signals`），置 `AWAITING_INPUT` 由 M06。
   测试 `test_a7` 断言 `state_sink.awaiting_calls == []` 守住这条边界。
3. **v1.7 B1 description 必填**：role 由描述决定，上传请求体缺 `description` 无法判 role。

## 5. 为什么这样测

- **内存桩**：`InMemoryObjectStore` / `FakeTenantGuard` / `FakeStateSink` 让 27 个用例
  不依赖 Docker / OCR / ffmpeg；真实 OCR 属 §8.5 集成冒烟（本轮未接）。
- **A1/A2 同图两描述**：`resolve_role` 纯规则保证两条路径；服务层两次上传产出不同
  `insight_ref` + 不同 `handler`。
- **A11 hash 篡改**：`store.tamper()` 注入，`get_with_hash_verify` 应抛 `ValueError`。
- **A9 纠偏只动一个**：`patch_roles` 仅更新目标行的 `insight_ref`，旧洞察写 `insight.v{n}.json`。

## 6. S5 独立 review 修复要点（勿回退）

| 编号 | 问题 | 修复落点 |
|---|---|---|
| B-1 | CSV/JSON 合法文本被误判伪造 | `validate.py` 文本 mime 白名单 + text/plain 回显 |
| B-2 | 一次性读全文件可 OOM | API 流式分块读至 `MAX+1` 即停（413） |
| S-1 | API 响应缺 ApiResponse 四字段 | `_m05_ok` / `_m05_error` 独立 helper |
| S-2 | 重复 PATCH 重跑 + 派生 ref 无 hash | `patch_roles` 同 role 早退；派生 ref 带 hash |
| S-3 | 畸形 PATCH 体 500 | `PatchRoleItem` Pydantic 校验 |
| S-4 | octet-stream 绕过类型门禁 | 声明 mime 白名单前置 |
| S-5 | 红线扫描半重言式 + thumbnail_ref 漏原文路径 | `serialize_extracted` 真扫 + `_derived_base` 独立 key |
| S-6 | dispatch 与服务脱节、无 FAILED 分支 | 服务真实调 `dispatch` + 失败→FAILED+evidenceRef |

## 7. 真实环境实现（2026-11-20 补齐）

| 组件 | 生产实现 | 测试桩实现 |
|---|---|---|
| 对象存储 | `s3_store.py` → boto3 直连 MinIO（`S3_ENDPOINT`，`att/*` key + hash 校验） | `stores.py: InMemoryObjectStore` |
| 附件索引 | `pg_stores.py` → `Attachment` 表（迁移 0003，租户索引） | `stores.py: InMemoryAttachmentStore` |
| 租户守卫 | `tenant_guard.py` → M04 SessionStore 查归属 | `stores.py: FakeTenantGuard` |
| 图片主色/缩略图 | `real_processors.py: process_visual` → Pillow 真解码（像素上限 4096） | `processors.py: dispatch` 静态桩 |
| OCR | `process_ocr` → rapidocr_onnxruntime 区域化（含 bbox），缺依赖时降级 `insight_quality=0` | 静态桩 |
| 视频关键帧 | `process_video` → imageio-ffmpeg 静态二进制抽帧（≤`MAX_KEYFRAMES`） | 静态桩 |
| 文本解析 | `process_data_source` → JSON/CSV 严格解析，值不 eval | 静态桩 |

生产接线：`main.py:create_prod_app` 注入 `AttachmentService(S3ObjectStore, PgAttachmentStore, SessionTenantGuard, RealProcessor)`；`POST /api/attachments` 与 `PATCH .../attachment-roles` 真实出现在生产路由表。

集成测试：`tests/integration/test_m05_real_infra.py`（真 PNG → Pillow 主色 + MinIO 原文 + PG 行）；Docker core 起时真跑，依赖不可达时明确 skip。

## 8. 已知边界（非回归，待后续模块联调）

- 传输层校验在 REST 边界执行；直接调 `AttachmentService.upload()` 的调用方须自行先校验。
- OCR/ffmpeg 为可选依赖：缺失时按 §2.3 降级（仅元信息、`insight_quality=0`），不跳过校验、不误伤 `role_confidence`。
- 审计 `AttachmentAudit` 只追加 hash 链尚未逐条落（设计 §6.4/§7 要求，后续补）。
