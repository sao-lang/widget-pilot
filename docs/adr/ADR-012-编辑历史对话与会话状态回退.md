# ADR-012：编辑历史对话与会话状态回退（设计已批准）

**状态**: **设计已批准 / 设计定稿**（2026-11-23；用户拍板 D1–D5 全部按推荐方案：turn 级分叉 / 保留旧分支 / interrupt 后分叉 / task 内分支 / 独立 ADR）。**本轮只出设计文档，不改码、不动契约/DB/前端**；实现待后续用户明确要求时另行启动。
**范围**: 允许用户在会话中**编辑某一条历史对话**，并从该时点**回退会话状态**、以编辑后的内容重新生成。借鉴 Claude / Cursor / WorkBuddy 的"从历史消息分叉重生成"模式。
**关联**: `ADR-009`（多轮迭代：前向追加 + turn 版本链，本 ADR 在其上扩展）、`ADR-010`（会话修正语义：当前任务重入，与本 ADR 的"历史时点回退"不同）、`ADR-008` §7A（历史思考过程展示，是"看"，本 ADR 是"改"）、`docs/modules/M17-时间线回放与状态管理.md` §3.2/§4.3（"从这里重生成 from_seq"设计，从未落地）；`generation_task` / `task_turn` / `sessions.bundle_ref`。
**变更类型**: 数据模型 + 会话状态机 + REST 契约 + 编排接线 + 前端 reducer 的设计变更。
**一句话结论**: 采用**分支（branch）模型**——不改历史、不删审计，从用户选中的历史 `turn` 分叉出新分支，把 `SessionState` / `current_bundle_ref` / 上下文快照恢复到该时点，再以编辑后的描述发起新一轮；旧分支完整保留可切回。

---

## §1 背景与需求

用户 2026-11-23 原话：「用户可以编辑之前的某次对话，会话状态需要可以回退到编辑的时候，你出个设计，对照目前的设计和代码实现，好像已经有了对话迭代修改的逻辑了。」

用户的直觉对了一半：项目确实有"对话迭代修改"逻辑（ADR-009），但那是**纯前向追加**，不是"编辑历史 + 回退"。

## §3 设计原则与关键决策

### 3.1 分支模型而非原地改写（核心决策）

- **不改历史 `task_turn`**：它是审计证据（`uuid5(task_id, turn_index)` 幂等、只追加），原地改写会破坏审计链与按 turn 归因的成本账（ADR-009 G4）。
- **回退 = 分叉**：用户编辑历史第 k 轮 → 从 `(task_id, turn_index=k)` 派生新分支 `branch_id`，新分支以编辑后的描述为第 k+1 轮（或独立编号），旧分支 k+1…N 保留。
- **会话当前视图 = 活动分支的 head**：`sessions.bundle_ref` / `generation_task.current_bundle_ref` 指向活动分支最新产物；切换分支 = 移动这两个指针 + 恢复 `SessionState` 到该 head 的记录态。
- 借鉴：Claude.ai「Edit message」从该消息分叉新对话；Git 的 branch/head 语义；本项目 M17「从这里重生成 from_seq」的方向。

### 3.2 与"原地覆盖"方案的对比（为什么选分支）

| 维度 | 分支（本 ADR 采用） | 原地改写历史 turn |
|---|---|---|
| 审计/成本 | 历史不可变，按 turn 归因完整 | 改写需重写成本账，破坏不可变纪律 |
| 用户误操作 | 可切回旧分支，无损 | 改了无法撤销（除非再存一份旧值，等于分支） |
| 实现复杂度 | 加 branch 维度 + 指针切换 | 看似简单，实则要处理"已发事件/产物引用悬空" |
| 与现有设计一致 | 沿用 ADR-009 版本链 + M17 回放 | 与"历史不删"纪律冲突 |

### 3.3 非目标

- N1：不改 `SessionState` 枚举（不新增 ROLLBACK 态）——回退是"分叉 + 指针切换 + 进入新一轮 RUNNING"，状态仍是 8 值。
- N2：不删除/改写任何历史 `task_turn`、事件、产物、成本记录。
- N3：不把原始对话消息全文回灌 prompt（沿用 ADR-009 §4 结构化事实摘要）。
- N4：不实现 M17 scrubber 的完整"任意 seq 重生成"（本 ADR 锚定到 **turn** 粒度，不做事件级 from_seq 分叉；事件级留给 M17 落地时对齐）。
- N5：不改 LLM wire / 不引入 Agent 框架。

## §4 数据模型

### 4.1 新增列 / 表（迁移建议 0020）

| 对象 | 变更 | 含义 |
|---|---|---|
| `generation_task` | + `active_branch_id TEXT` | 当前活动分支 id（默认 `main`） |
| `generation_task` | + `branch_head_turn INTEGER` | 活动分支的 head turn_index |
| `task_turn` | + `branch_id TEXT NOT NULL DEFAULT 'main'` | 该轮所属分支 |
| `task_turn` | + `parent_turn_id TEXT nullable` | 分叉来源轮（首轮为 null）；分支内 turn 链的父亲 |
| 唯一约束 | `(task_id, branch_id, turn_index)` 替换原 `(task_id, turn_index)` | 同 turn 号在不同分支可并存 |

> 兼容：迁移时用一条 UPDATE 把存量 `task_turn.branch_id='main'`、`parent_turn_id` 按同任务上一轮回填；旧 `current_bundle_ref` 归入 main 分支。

### 4.2 分支快照（回退所需状态）

回退到历史 turn k 时，需要恢复的不只是产物引用，还有会话状态与上下文：

| 恢复项 | 来源 | 说明 |
|---|---|---|
| `SessionState` | 该 turn 完成时记录的 `state`（新增 `task_turn.state_at_head`） | DONE→COMPLETED、FAILED→FAILED 等 |
| `current_bundle_ref` | 该 turn 的 `result_bundle_ref` | 产物指针回退 |
| `sessions.bundle_ref` | 活动分支 head 的 bundle | 会话级产物指针 |
| 上下文 FactSummary | 该 turn 的 `fact_summary_ref`（现状未填，本 ADR 补齐写入） | 回灌到编辑时刻的确定性事实，不含后续轮 |

## §5 API 契约（草案）

```
POST /api/sessions/{session_id}/turns/{turn_id}/edit
  body: { "description": "编辑后的修改意图", "target_task_id"?: string }
  → 202 {
      code:"OK",
      data:{ branchId, newTurnIndex, runId, state:"RUNNING", forkedFromTurnId }
    }
```

- `turn_id` = 用户选中要编辑的历史轮（`task_turn.id = uuid5(task_id, turn_index)`）。
- 行为：校验归属（session/turn 属于当前用户）→ 从该 turn 分叉新 `branch_id`（如 `b-<uuid8>`）→ 复制分叉点快照（bundle/fact/state）→ 把新分支设为 active → 以 `description` 发起新一轮（复用 ADR-009 §5 迭代执行流程，门禁照跑）。
- 幂等：同 `(turn_id, description hash)` 在短窗口内重复请求返回同一 `branchId`（幂等键）。
- 并发：同一 task 的分支创建用 advisory lock（沿用 `allocate_turn` 的锁思路），防并发分叉冲突。

```
GET /api/tasks/{task_id}/branches
  → 200 { code:"OK", data:{ branches:[
      { branchId, headTurnIndex, state, currentBundleRef, forkedFromTurnId, createdAt }, ... ] } }

POST /api/tasks/{task_id}/branches/{branch_id}/activate
  → 200 { code:"OK", data:{ activeBranchId, state, currentBundleRef } }
```

- `activate` = 切换活动分支（把指针与 `SessionState` 恢复到该分支 head），不产生新轮次、不调模型。
- 切分支时会话若 RUNNING：先 `interrupt` 幂等（沿用 ADR-010 §4.2），旧分支保留现场。

## §6 编排与事件

1. **edit 入口**（API 层）：鉴权 + 校验 turn 归属 + 记录分叉审计（`audit_event`，动作 `TURN_EDIT_FORK`）。
2. **快照恢复**：把分叉点的 `result_bundle_ref`/`fact_summary_ref`/`state_at_head` 写入新分支 head 记录，并把 task/session 的活动指针切到新分支。
3. **新一轮执行**：复用 dispatcher `_plan_and_fanout` / `process_one`（ADR-011 单 agent 内核），`target_task_id` 保留语义；`turn_index` 在新分支内 +1。
4. **事件归因**：新增事件顶层 `branchId?`（沿用现有 `taskId`/`turn` 归因的扩展方式，schema 加可选字段）；reasoning 事件（ADR-008）同样带 branchId，前端按分支渲染。
5. **成本**：`cost_ledger` 的 `evidence_ref` 结构化承载 `branch_id`（沿用 ADR-009 按 task+turn 归因的扩展）。

## §7 前端（M14/M17）

- 历史对话条目旁提供「编辑并重新生成」按钮（只在用户自己的历史 turn 上显示）。
- 点击 → 打开编辑框（预填该轮 `user_intent`）→ 提交 `POST /edit` → 新分支的 SSE 流按 `branchId` 归约（M17 reducer 增加 branch 维度，旧分支视图保留）。
- 分支切换器：显示分支树/列表，点 `activate` 切回旧分支；视图按 M17 `SessionView` 从该分支事件重放。
- 不做乐观更新（回退/重生成是不可逆操作，沿用 M17 §3.4 D 白名单纪律）。

## §8 安全与合规

- 编辑历史不允许绕过进护栏：新描述照跑 ADR-004 意图级联 + ADR-005 输入护栏；改的是"哪一版"，不是"绕过判定"。
- 分叉审计必留：`TURN_EDIT_FORK` / `BRANCH_ACTIVATE` 写 `audit_event`，可按 trace 追溯谁在何时从哪轮分叉。
- 越权：turn/task/session 三层归属校验，防跨租户编辑他人历史。
- 不删历史：分叉只新增分支与轮次，旧分支数据不动——符合 ADR-009/010 的"历史不删"纪律。

## §9 状态、原因码与契约门禁

| 项 | 结论 |
|---|---|
| `SessionState` | 不变（8 值）；回退体现为"分叉后进入新一轮 RUNNING" |
| `ReasonCode` | 复用 `INPUT_INVALID`（非法 turn/分支）、`STATE_CONFLICT`（运行中切分支）等现有码；不新增 |
| `AgentEventKind` | 不变；事件顶层增可选 `branchId` 字段 |
| OpenAPI/SDK | 新增 3 端点 + 事件字段 → 四生成物同步（`pnpm gen:all` + `contracts:check` drift=[]） |
| DB | 迁移 0020（加列 + 约束变更 + 存量回填）；本仓 SQLAlchemy 2.1 无 `Inspector.has_column`，幂等守卫用 `get_columns()` |
| 验收 | 真 PG 迁移 upgrade/downgrade；pytest 全绿；契约门禁；两轮独立 review（沿用 ADR-011 流程） |
