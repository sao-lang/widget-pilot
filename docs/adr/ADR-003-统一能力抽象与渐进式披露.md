# ADR-003：tool 与 skill 统一为 Capability 抽象 + 渐进式披露

**状态**: 已确认（节点④设计拷问 Q1–Q9 前沿清零，2026-11-21 06:5x；允许进入写代码）
**范围**: 把 agent 可调用的 tool 与可加载的 skill 收敛为统一 `Capability` 抽象，按 L0/L1/L2 三级渐进披露，由 LLM 按需加载；意图路由从「决定加载什么」退为「安全门禁」
**技术栈摘要**: Python 3.13 / Pydantic v2 / FastAPI / Postgres + Redis / 零 Agent 框架手写 harness（详见 §4）
**关联**: 前置 `设计方案.md` §2.4 #9/#10、§11.6、X6；关联代码 `packages/agent_core/tools/`、`packages/agent_core/loop/`、`services/guardrails/`；来源需求=用户 2026-11-21 决策
**变更类型**: 补充设计 + 重构依据（§13 必填）

---

## §1 设计意图（Design Intent）

- **一句话意图**：守住「能力可按需发现、常驻成本可控」——让模型自己决定用什么能力，而不是由前置校验链替它决定；同时不破坏确定性安全门禁。
- **设计原则**（可判定）：
  1. **一个抽象**：tool 与 skill 都是 `Capability`，只有 `kind` 与 L2 行为不同；出现第二套能力注册机制即违背。
  2. **分级披露**：模型在 L0 只看 `id + brief + cost_hint`；完整 schema / 正文必须经显式加载才进入上下文。L0 注入完整 schema 即违背。
  3. **LLM 自主选择**：加载哪个能力由模型输出决定，不由静态映射表决定；静态表只能作为白名单/默认建议，不能剥夺模型选择权。
  4. **门禁确定性**：拒绝类判定（越权/PII/注入/规格冲突）仍由 L1 规则裁定，不交给模型自报；任何 L2 请求都必须过闸。
  5. **预算不可绕过**：L1 加载与 L2 执行统一计入 X4 四维预算；存在不计入的加载路径即违背。
- **价值排序 / 冲突裁决**：安全确定性 > 常驻成本 > 模型自由度 > 实现简洁。当"让模型自由加载"与"安全门禁"冲突，门禁胜。
- **反意图**：不追求通用工具集（shell / 网络 / 任意文件写）；不做多 Agent 角色；不把历史代码/附件原文当指令回喂。
- **与既有设计意图的关系**：**改变** §2.4 #9 的手段（从「不新增常驻工具、技能走 need_skill」改为「L0 只常驻摘要、schema/正文按需披露」），但保留其精神（省每轮常驻税）；§2.6 X6 由「M06 静态预取」改为「统一披露 + 门禁」。

## §2 背景与目标

- **现状**（源码核实，2026-11-21）：
  - tool 侧：`packages/agent_core/tools/registry.py` 定义 `REGISTRY`/`register`/`freeze_registry`，`invoke.py` 实现五步；但生产代码**零 `register()`、零 `freeze_registry()` 调用**，模型请求**不下发 tool schema**；`loop/run.py:148-152` 的 `CALL_TOOL` 分支不调 `invoke()`，只回灌假 ref `tool-result/{run_id}/{rev}`。
  - skill 侧：`services/guardrails/need_skill.py`（四项校验）、`skill_router.py`（`(widget_type,grid)→recipe_id[]` 静态映射）、三张 PG 日志表均在；但 `packages/prompts/recipes/` **目录不存在**，规程正文为空。
  - 文档口径冲突：`skill_router.py:11` 与 M06 文档 241 行称 M10 维护规程库；M10 文档 146/266 行称 M06/M07 维护。
- **动机**：现状是「工具断链空壳 + skill 通校验空内容」，且 skill 由意图路由静态决定（因果倒置）。不改则 agent 无真实可执行能力，模型无法自主按需取用能力。
- **影响面**：M03（agent_core 内核）、M06（护栏路由）、M07（上下文装配）、M10（规程库）、M05/M08（附件处理/代码执行）、M02（契约事件）、`设计方案.md`、M03/M06/M07/M10/M15 文档。
- **成功标准**：模型在 L0 目录看到全部能力 → 显式请求 L1 详情 → 请求 L2 执行/加载 → 全程过 M06 闸门并计入 X4 预算；生产代码存在真实注册与真实执行链路（零 fake 冒充）。

## §3 范围与边界

- **范围内**：`Capability` 抽象与 registry；L0/L1/L2 披露协议；`LOAD_CAPABILITY` 统一决策与 run loop 接线；M06 能力请求校验（泛化 `need_skill`）；M07 目录槽位与加载结果落槽；规程库骨架；附件处理/代码执行注册为 tool；文档同步。
- **范围外**：真实模型接入（M20/M07 既有排除项）；通用工具集（shell/网络/任意文件写）；多 Agent 编排；前端渲染改动。
- **反向排除**：不得把 `Capability` 做成第二套与 `ToolSpec` 并存的注册机制（必须替换）；不得让 L2 加载绕过预算；不得在 L0 注入完整 schema 或规程正文。

## §5 需求清单（编号、可测、可追溯）

- FR-1：定义 `Capability` 数据类，字段至少含 `id/kind(Literal["tool","skill"])/brief/detail_ref/payload_ref/surfaces/cost_hint`；`kind` 只有两值。 — 验收：`test_capability_model` 校验字段与枚举。
- FR-2：`REGISTRY` 支持按 `id` 注册、L0 目录视图（只含 id/kind/brief/cost_hint）、L1 详情、L2 执行/加载回调；启动期冻结后不可变。 — 验收：`test_registry_levels` + `test_registry_freeze`。
- FR-3：新增 `DecisionKind.LOAD_CAPABILITY`，字段 `capability_id/level(1|2)/args/surface`；`decide()` 产出该决策，`run()` 按 level 分派 L1 下发 / L2 执行或加载。 — 验收：`test_load_capability_decision` + `test_run_load_levels`。
- FR-4：`run()` 的 L2-tool 分支真实调用能力 handler（替换现有假 ref 回灌），结果经 `max_output_chars` 截断后回灌可信槽位。 — 验收：`test_run_executes_capability_handler`（handler 被调用计数=1）。
- FR-5：模型请求在 L0 阶段下发能力目录（仅摘要），不下发完整 schema / 正文；L1 请求后才注入对应详情。 — 验收：`test_l0_catalog_no_schema`。
- FR-6：M06 `need_skill` 四项校验泛化为能力请求校验：白名单（capability 已注册）、surface 授权、level 合法、单轮次数与 token 上限；拒绝类仍由 L1 规则裁定。 — 验收：`test_capability_guard_*`（沿用/改造现有 `test_m06_skills_guardhit.py`）。
- FR-7：意图路由（四级级联）不再产出 `recipe_ids`；技能预取整套删除（`prefetch()` / `_PREFETCH_MAP` / `SkillPrefetchLog` / `ValidationResult.recipe_ids` / `/api/skills` 端点 / 迁移 0009 drop 表）——纯按需加载，不留兼容层。 — 验收：`test_prefetch_fields_are_gone` + `test_skills_endpoint_removed`。
- FR-8：M07 上下文固定槽位新增 L0 目录段（位置：系统契约之后），L1/L2 加载结果按 kind 落入 schema 槽或规程槽；保 prompt caching。 — 验收：`test_context_slots_catalog_position`。
- FR-9：规程库骨架落地于 `packages/prompts/recipes/`，至少含 1 个真实 recipe（`recipe.calendar.month.v3`），绑定 `recipe_id/version/token_cost`；M10 负责索引，M06/M07 维护正文（口径二选一，见 §13）。 — 验收：文件存在 + `test_recipe_manifest_load`。
- FR-10：附件处理（`tool.attachment.process`）与代码执行（`tool.code.execute`）注册为 `kind=tool` 的 Capability；handler 内只收对象存储引用，复用 M05 processor 与 M08 沙箱，不重造原文/沙箱边界。 — 验收：`test_attachment_capability_ref_only` + `test_code_capability_sandbox`。
- FR-11：L1 加载与 L2 执行统一计入 X4 四维预算（tool_calls + token），触顶确定性中断。 — 验收：`test_capability_result_stored_and_tokens_accumulated`。
- NFR-1：安全确定性——任何 L2 请求过 M06 闸门；密钥/PII/附件原文不进 L0 目录与日志。 — 验收：安全红线扫描 + `test_l0_no_raw_attachment`。
- NFR-2：源码纯净——生产代码零 fake/内存桩冒充 adapter，动态类型不放宽；`source_purity.py --strict` 通过。 — 验收：脚本退出码 0。
- NFR-3：契约一致——新增 `LOAD_CAPABILITY` 决策/事件经 M02 契约登记，`pnpm contracts:check` drift=[]。 — 验收：契约门禁 OK。

## §6 Approaches（必备节）

| 方案 | 做法 | 优点 | 取舍 / 代价 | 结论 |
|---|---|---|---|---|
| A | tool 与 skill 统一 `Capability`，L0/L1/L2 分级披露，`LOAD_CAPABILITY` 单通道，LLM 自主选择 | 一个抽象、一份门禁、省常驻税、解除因果倒置 | 改动面大（M03/M06/M07 联动），需重写 §11.6 | **采用** |
| B | 保留 tool（CALL_TOOL）与 skill（need_skill）两套通道，各自加分级披露 | 改动小，不动已验收 M06 | 两套注册/两份门禁，口径长期分裂，违背用户「统一工具」诉求 | 备选（否决） |
| C | 只补现有断链（真实注册 tool + 补规程库），不做统一抽象与披露 | 最小改动，最快恢复可用 | 未解决「M06 替模型决定 skill」的因果倒置，无渐进披露 | 备选（否决） |

- 选 A 的理由：回溯 §1——"一个抽象"与"LLM 自主选择"是用户明确诉求，B/C 均不满足；代价（改动面）由分阶段落地吸收。

## §7 架构设计

### 7.1 架构总览

```
LLM 输出 Decision(LOAD_CAPABILITY)
        │
        ▼
[ M06 能力请求闸门 ]  白名单 / surface / level / 次数 / token（拒绝类 L1 规则裁定）
        │ pass
        ▼
[ M03 dispatch ]  level=1 → L1 详情（schema/manifest）注入
                  level=2 → kind=tool: handler 执行 / kind=skill: 正文注入
        │
        ▼
[ M07 上下文槽位 ] 系统契约 → L0 目录 → 规程/详情 → 检索 → 附件 → 记忆 → 结论
        │
        ▼
[ X4 预算 ] L1/L2 统一计入 tool_calls + token（FR-11）
```

### 7.2 分层与模块职责

- **内核层（M03）**：`Capability` 定义、registry（L0/L1/L2）、`LOAD_CAPABILITY` 决策、run loop 分派；不 import M06 策略。
- **门禁层（M06）**：能力请求校验（泛化 need_skill），意图路由只做放行/拒绝判定，不决定加载内容。
- **装配层（M07）**：L0 目录槽位 + 加载结果落槽；composition root 在 orchestrator `deps.py`/`dispatcher.py`。
- **能力实现层**：M05 附件 processor、M08 沙箱、M10 规程库——各自提供真实 handler/正文，注册进 registry。

### 7.3 模块契约

- `Capability(id, kind, brief, detail_ref, payload_ref, surfaces, cost_hint)` — 定义于 M03，全模块共用（FR-1）。
- `REGISTRY.level0() -> list[CapabilityBrief]` / `detail(id) -> schema|manifest` / `execute(id, args) -> ToolResult` — M03 public API（FR-2）。
- `DecisionKind.LOAD_CAPABILITY(capability_id, level, args, surface)` — M03→M06→M03 闭环（FR-3）。
- `check_capability_request(req, turn, allowlist) -> CapabilityResult` — M06 public API（FR-6）。

### 7.4 数据流

L0 目录（装配期注入）→ 模型读到能力清单 → 输出 `LOAD_CAPABILITY(level=1)` → M06 校验 → M03 下发详情 → 模型输出 `LOAD_CAPABILITY(level=2)` → M06 校验 → M03 执行/加载 → 结果回灌可信槽位 + 计预算 → 继续生成。闭环字段：`capability_id` 贯穿、`level` 决定行为、`result_ref` 回灌。

### 7.5 装配入口（composition root）

`services/orchestrator/deps.py` 构造 `Deps` 时注入 registry（真实注册 M05/M08/M10 能力）；`dispatcher.py` 在 `run()` 前过 M06 校验链。此二者是"接口就绪 ≠ 系统可用"的关键——必须真实注册，否则回到断链。

### 7.6 接线四问（设计阶段预填，S4 逐条核实）

1. 谁调用它？— `LOAD_CAPABILITY` 由 `decide()` 产出、`run()` 消费；`execute()` 由 run loop 调用（FR-4 锁死，不得再假回灌）。
2. 它调用谁？— L2-tool handler 注入 M05 processor / M08 sandbox；L2-skill 注入 M10 recipe loader。
3. 信号被谁消费？— `capability` 事件（M02）由 M11 审计消费；`result_ref` 由下一轮 `decide()` 消费。
4. 数据流闭环？— L0 目录 → 模型选择 → L1/L2 → 结果回灌 → 预算 → 继续生成，无空转字段。

## §8 其他关键设计维度

### 8.1 术语与领域模型

- **Capability（能力）**：agent 可发现/调用的统一单元，两族 `tool`（动作）/`skill`（知识）。
- **L0/L1/L2**：披露层级——L0 摘要常驻、L1 详情按需、L2 执行/正文按需。
- **规程（recipe）**：skill 的内容本体，版本化文件，`recipe_id` 为句柄。
- **闸门（guard）**：M06 能力请求校验，确定性、不靠提示。

### 8.2 数据与存储

- L1/L2 请求与结果写审计/日志（复用 M06 `need_skill_log`，迁移 0008 扩 capability_id/level 列并补齐写入方；`skill_prefetch_log` 随预取删除由迁移 0009 drop）。
- 规程正文存 `packages/prompts/recipes/`（版本化文件）+ PG 索引（M10）。

### 8.3 错误、异常与降级

- 未注册 id → 拒绝（CAPABILITY_DENIED）；参数非法 → INPUT_INVALID；越权 surface → CAPABILITY_DENIED；次数/token 超限 → 拒绝并可自纠正回边；handler 故障 → CoreError.infra 上抛。
- 降级：L2 故障不静默成功；预算触顶确定性中断（不降级放行）。

### 8.4 依赖与外部集成

- M05 processor（附件）、M08 sandbox（代码执行）、M10 recipe loader（规程）——均为既有 port，注入真实实现。
- 失败影响：handler 缺失 → 注册期 fail-fast，不允许运行时 None 降级。

### 8.5 可观测性

- 每个 L1/L2 请求写 `capability` 事件 + PG 日志（id/level/surface/decision/latency），支撑"信号被消费""预算被计入"举证。

### 8.6 兼容与迁移

- 替换 `CALL_TOOL`/`need_skill` 两套决策为 `LOAD_CAPABILITY`；M02 契约与事件 schema 同步；旧 `spec.tool/args` 字段保留为兼容别名或直接迁移（见 §10）。
- 灰度：先在测试注入注册，验证全链路后切生产装配。

## §13.1 后续决策：技能预取整套删除（2026-11-21）

实施后核查发现：`ValidationResult.recipe_ids` 全仓零消费者——`prefetch()` 的产物
被算出来、写日志、发事件、塞进一个没人读的字段，是每次请求的空转死代码；
`skill_router.py` 注释声称自己是"L0 白名单来源/建议来源"，实际 registry 注册 L0
并不读它。用户拍板**不留兼容层、不打补丁，彻底删除**：

| 删除项 | 落地 |
|---|---|
| `prefetch()` / `_PREFETCH_MAP` / `PrefetchResult` | 删 `skill_router.py` 与 types 定义 |
| `SkillPrefetchLogRow` / `PgSkillPrefetchLogStore` / 内存替身 | 删 Row、Store、port、装配、测试 |
| `skill_prefetch_log` 表（0005 建、0008 扩列） | 迁移 0009 drop（幂等） |
| `ValidationResult.recipe_ids` / skill 事件的 `recipe_ids`/`prefetch_hit` | 删字段；skill 事件只留 need_skill 归因 |
| `/api/skills` 端点 + `SkillManifest` schema | 删端点与 openapi schema，重新生成 SDK |
| `ConfigSnapshot.prefetch_count` | 删指纹字段（它指纹的东西已不存在） |

验收：`test_prefetch_fields_are_gone`（无 recipe_ids/预取事件字段）、
`test_skills_endpoint_removed`（404，无兼容端点）。纯按需加载：模型只看
`registry.level0()` 全量目录，经 `LOAD_CAPABILITY` 自主选择。
