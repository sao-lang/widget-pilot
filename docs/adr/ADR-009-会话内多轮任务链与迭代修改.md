# ADR-009：会话内多轮任务链与迭代修改（草案 v0.1）

**状态**: 草案 v0.1（2026-11-22；用户提出需求并拍板三项：粒度=会话内多任务并存且可反复修改 / 上下文=结构化事实摘要 / 范围=先出 ADR 不改码）
**范围**: 让一个 `session` 能跨多条用户消息持续存在——同一会话内可并存多个 widget 生成任务，可对任一任务反复迭代修改；每轮只把「结构化事实摘要」回灌上下文，不累积原始对话消息。
**关联**: `ADR-001`（规格缺省询问）、`ADR-002`（记忆）、`ADR-006`（一次对话多控件生成：**本 ADR 的直系前置**，复用其 `task_id`/`generation_task`/`parent_run_id` 三层标识）、`ADR-008`（reasoning 通道）；`docs/modules/00-总览与模块地图.md` §1.7 非目标、M04/M07 模块文档。
**变更类型**: 设计变更（会话状态机 + 新表 + 事件契约 + 上下文装配 + REST）；**本 ADR 只定方案，不含实现**。
**一句话结论**: 把 ADR-006 的「一次消息内扇出多任务」扩展为「跨多条消息的任务链」——`generation_task` 从一次性子任务升级为**可迭代的持久任务实体**，会话 `COMPLETED` 不再是会话死亡而是「当前批次完成、可接受下一轮」；上下文用零 LLM 的结构化事实摘要回灌，守住固定前缀与 caching。

---

## §0 为什么需要这份 ADR

用户 2026-11-22 原话：「一个会话内，用户可以连续不停地修改某个 widget，或者做完一个 widget 又发起一个 widget 任务，这个会话内可能存在多个 widget 的任务，可能对某（多）个 widget 多次修改，AI 都要可以执行」「不太行，需要支持多轮对话，否则每次任务都是一次性的」。

现状（已核对源码，2026-11-22）：
- 会话 `submit_message` 要求 `DRAFT`，分配唯一 `run_id`（`sessions/service.py:133-170`）；`COMPLETED` 是终态，之后不能再提交生成消息。
- `spec.messages` 是**本轮装配结果**，只有两处写入：`run.py:244` 整体替换为六槽位、`run.py:123` 能力拒绝时追加一条；没有跨轮累积（`run.py`/`decide.py` 全量检索）。
- 用户澄清答案落在 `State.clarification_answer` **单字段**（覆盖式），不是消息列表——这是"单轮内的问答"，不是"跨轮对话"。
- 模型输出走 SSE 事件流（Redis 窗口 500），只给前端展示，不回灌 prompt。
- `bundle_ref` 在 `complete()` 时写入 SessionRow（M09 产物），但后续轮次不读回。

**这不是再写个循环就能解决的事**：会话状态机、任务标识、事件归因、成本账、上下文装配都按"单 run 单任务"假设设计。ADR-006 已为"一次消息多任务"引入 `task_id`/`generation_task`，但它是**一次性扇出**——任务完成即结束，没有"对同一任务再改一轮"的路径。本 ADR 把那条路补上。

## §1 与既有非目标的覆盖声明（必须显式）

`docs/modules/00-总览与模块地图.md` §1.7 非目标原文含：**「不做通用聊天助手（只处理控件生成）」**。

- **本 ADR 不撤销这条**：系统仍然只处理「控件生成/修改」请求，不做开放域闲聊、问答、写作。
- **有条件覆盖其"一次性"解读**：原非目标暗示"一会话=一个生成任务=一次性交付"。本 ADR 明确——一个会话可以是**多条控件生成/修改消息的序列**，但每条消息仍必须是控件相关意图（由 M06 意图级联把门，非控件意图照常拒绝）。
- 覆盖边界：不做"记住用户三句话前的闲聊内容"，只做"记住与本会话控件任务相关的结构化事实"。

用户已拍板的三项（2026-11-22）：
1. **粒度**：会话内多任务并存 + 同一任务反复修改（比 ADR-006 的"一次多控件"更进一步）。
2. **上下文策略**：**结构化事实摘要**——不回放原始 messages，每轮结论压成短事实，放会话结论槽；守 caching 前缀、零 LLM。
3. **范围**：先出 ADR，确认后再谈实现。

## §2 目标 / 非目标

**目标**
- G1：一个会话内可先后/并存多个 widget 任务，各有独立 `task_id`、`run_id`、产物、状态。
- G2：可对任一已有任务发起迭代修改（"把日历改成农历""配色换深色"），产出新版本产物，历史版本可追溯。
- G3：模型能看到**与本会话相关的结构化事实**（做过哪些任务、各自当前 spec 摘要、最近一次 User 修改意图），且这些事实以固定形态进入结论槽，不破坏 1–2 槽 caching 前缀。
- G4：迭代不丢审计——每轮修改的事件、成本、复现指纹可归因到 `task_id` + `turn_index`。

**非目标**
- N1：不做通用聊天助手；非控件意图仍由 M06 拒绝（沿用 §1 覆盖边界）。
- N2：不回放原始 user/assistant 消息文本进 prompt（用户拍板：结构化事实摘要）。
- N3：不引入 LLM 做对话摘要/历史压缩（零 LLM 事实抽取，I-M2 纪律延续）。
- N4：不改 M20 的 wire（`Responses` 不用 `previous_response_id`、不做服务端 store，多轮由 M03/M07 自有链路负责——延续 M20 §9 的既有决定）。
- N5：不在本 ADR 实现；实现须待本 ADR 确认 + ADR-006 P0–P2 前置。

## §3 核心模型：把 `generation_task` 升级为持久可迭代实体

ADR-006 已定义三层标识 `session_id` / `parent_run_id` / `task_id`，并新建 `generation_task` 表（建议迁移 `0012_generation_tasks`）。本 ADR **复用并扩展**，不另起一套。

### 3.1 标识扩展

| 标识 | 归属 | 生成时机 | 与 ADR-006 的关系 |
|---|---|---|---|
| `session_id` | 会话 | 建会话 | 不变，跨轮唯一锚点 |
| `task_id` | widget 任务 | 首次规划落库 | **不变**；同一 widget 的多次迭代共享同一 `task_id`（这是关键） |
| `parent_run_id` | 一次用户消息 | `submit_message` | **不变**；每轮消息分配新的父 run，即 ADR-006 里的"本次请求父 run" |
| `run_id` | 一次执行 | 任务首次消费 / 迭代消费 | **扩展**：同一 `task_id` 的第 N 次迭代分配新 `run_id`，与 ADR-006 的"子 run 首次消费分配"同构 |
| `turn_index` | 迭代序号 | 每次对任务的修改 | **新增**（本 ADR）：`(task_id, turn_index)` 唯一，1-based；turn 1 是首次生成，turn>1 是迭代修改 |

**关键**：`generation_task.id`（`task_id`）从"一次性任务"升级为"widget 任务实体"；一次迭代 = 该实体下的一条新 `run_id` + 一条 `turn` 记录。这样 ADR-006 的"一次消息 N 个任务"和本 ADR 的"跨消息反复改一个任务"用同一张表表达。

### 3.2 表变更（在 ADR-006 的 `generation_task` 之上增量）

| 新列 / 新表 | 归属 | 含义 |
|---|---|---|
| `generation_task.current_bundle_ref` | 加列 | 该任务当前最新版本产物（`bundle_id`）；迭代时更新 |
| `generation_task.last_turn_index` | 加列 | 当前迭代序号；用于 `turn_index` 分配与乐观并发 |
| `generation_task.status` | 用现有 `state` | ADR-006 的子任务状态机 `PENDING→...→DONE` 沿用；迭代时任务回到 `QUEUED`，不是新建任务 |
| **新表 `task_turn`**（建议迁移 `0013_task_turns`） | 新表 | `id=uuid5(task_id, turn_index)`、`task_id`、`turn_index`、`parent_run_id`、`run_id`、`user_intent`（本轮修改意图短文本）、`fact_summary_ref`（对象存储的 FactSummary JSON）、`result_bundle_ref`、`cost_ref`、`created_at` |

`task_turn` 唯一索引 `(task_id, turn_index)`；索引 `(parent_run_id)` 供一轮消息的多个迭代聚合。上一版产物不删——`result_bundle_ref` 逐 turn 留痕，支持"回退到第 1 版"。

### 3.3 会话状态机扩展（最小改动）

ADR-006 §4.3 已定：会话层沿用 8 值 `SessionState`，`COMPLETED` 是父 run 裁决后的唯一终态。

本 ADR 的扩展：**`COMPLETED` 从"会话死亡"语义改为"当前轮次已完成、可接受下一条控件消息"**。不新增枚举值（避免契约震荡），而是：
- `submit_message` 放开限制：允许 `DRAFT | COMPLETED`（以及 ADR-006 引入的完成态）状态下提交**新控件消息**；`RUNNING/AWAITING_INPUT/VALIDATING` 仍拒绝并发提交。
- 新消息进入时，会话状态回到 `RUNNING`，`Session.run_id` 更新为新的 `parent_run_id`（ADR-006 语义：本次请求父 run）。
- 会话级 `title` 不变；任务列表从 `generation_task` 按 `session_id` 查询聚合。

**不新增 `PARTIAL`**（沿用 ADR-006 O3 拍板）。

## §4 结构化事实摘要：上下文怎么回灌（用户拍板方案）

### 4.1 核心原则

**不回放原始对话消息**。每轮结束后，把"本轮发生了什么"压成固定形态的短事实，存成 `FactSummary` JSON（对象存储），`task_turn.fact_summary_ref` 指向它。下一轮装配时读取本会话相关任务的最新 `FactSummary`，渲染进**会话结论槽**（固定最后一段，`slots.py:196` `_conclusion_message`），不动 1–2 槽前缀 → caching 保持。

### 4.2 `FactSummary` schema（版本化，零 LLM 生成）

```
FactSummary {
  schema_version: "v1"
  session_id: str
  tasks: [
    {
      task_id: str
      title: str                      # widget 简述（来自 description 前 N 字，非模型生成）
      current_spec_digest: {          # 从 State.spec 确定性抽取，不存全文
        widget_type / grid / palette / key_features[]
      }
      last_intent: str                # 用户最近一次修改意图（短文本，来自 Input.text）
      turn_count: int
      current_bundle_ref: str | None
      status: str
    }
  ]
}
```

- **确定性生成**：`FactSummary` 由 `State.spec` + `Input.text` + `generation_task` 行**纯代码拼装**，不调模型（N3）；字段白名单，禁塞 PII/代码原文（延续 I-M1）。
- **有界**：`tasks` 上限与每任务 `key_features` 上限由 `constants` 固定（影子校准），超限时按 `updated_at` 保留最近 N 个任务——这是"结构化裁剪"，不是"聊天历史窗口化"。
- **token 上限**：渲染进结论槽时复用 `slots.max_tokens`，与检索/记忆槽同一预算纪律。

### 4.3 渲染位置与缓存前缀

- 结论槽（`CONCLUSION_PREFIX`）当前内容是 `state.spec.model_dump()` + `excluded_approaches`（`slots.py:196-202`）。
- 多轮时扩展为：`spec JSON` + `excluded_approaches` + `FactSummary 渲染段`。
- 约束：`FactSummary` 段**只在最后一段追加**，不改前面 6 槽的任何字节；装配快照对比断言（I18）扩展为"跨轮前缀 diff = 空"。

## §5 端到端流程（编号，可直接拆 PR）

1. **入口**：用户在已有 `session` 上 `POST /api/sessions/{id}/messages`，带 `description`（修改意图）+ 可选 `target_task_id`（指定改哪个 widget；省略则由系统按最近任务或用户消歧决定）。
2. **门禁**：`validate_chain` 照常跑——意图必须是控件生成/修改（非目标 §1 覆盖边界），安全子集（注入/PII/敏感词）不因多轮放宽。
3. **任务解析**：
   - 有 `target_task_id`：加载该 `generation_task` + 最新 `FactSummary` + `current_bundle_ref`（上一版产物）。
   - 无 `target_task_id` 且会话内有多个任务：进入消歧（复用 ADR-001 `ASK_USER`，问"改哪个"）；仅一个任务：默认它。
   - 新 widget 意图：走 ADR-006 规划，新建 `generation_task`（新 `task_id`）。
4. **迭代执行**：目标 task 分配新 `run_id`、`turn_index = last_turn_index + 1`，写 `task_turn` 行；上一版 `bundle_ref` 与 `FactSummary` 作为上下文注入（§4）。
5. **装配**：`run()` 调 `assemble()`，六槽位固定；结论槽追加本会话 `FactSummary`；上下文端口（偏好/程序记忆）照常注入。
6. **产物**：新版本 `bundle_ref` 写回 `generation_task.current_bundle_ref` 与 `task_turn.result_bundle_ref`；旧版本不删。
7. **归因**：事件 seq 带 `task_id`/`turn_index`（ADR-006 §6.2 的 task_id 归因扩展）；成本账 `cost_ledger` 增列或在 `evidence_ref` 结构化承载 `task_id`+`turn_index`。
8. **摘要落地**：本轮结束生成新 `FactSummary`，更新 task_turn 的 `fact_summary_ref`，供下一轮读取。
9. **会话终态**：父 run 裁决后会话回 `COMPLETED`（§3.3 语义），可接受下一条消息。

## §6 关键机制

### 6.1 并发与幂等
- 同一 `task_id` 的连续迭代用 `generation_task.last_turn_index` 乐观并发；并发两轮修改同一任务 → 后到者 409 或排队（待拍板 O3）。
- `task_turn.id = uuid5(task_id, turn_index)` 天然幂等；重试不产生重复 turn。
- 不同 `task_id` 的迭代可并行（沿用 ADR-006 并发上限 O4）。

### 6.2 事件与成本
- SSE 事件 payload 带 `task_id`+`turn_index`（ADR-006 已要求 task_id 归因，本 ADR 加 turn）；前端按任务分卡、按 turn 展示版本历史。
- 成本：每 turn 独立 `run_id` → `cost_ledger` 已有 `run_id` 唯一约束可直接复用；`model_tier`/用量按 turn 归集，父消息级聚合由 `parent_run_id` 关联。
- 复现指纹：`ReproInputs` 增 `task_id`/`turn_index`（或等价地由 `fact_summary_ref` 的版本号承载）——延续 ADR-006 §6.7 对多任务复现的要求。

### 6.3 与 ADR-006 的边界
- ADR-006 解决"**一条消息 → N 个新任务**"（扇出）；本 ADR 解决"**N 条消息 → 同一会话的任务链，可反复改**"（跨轮）。
- 二者共用 `generation_task` 表与 `task_id` 标识；ADR-006 的 `parent_run_id` 在本 ADR 里每轮消息都会更新——这正是"跨轮"的表达。
- **前置依赖**：本 ADR 的实现必须在 ADR-006 P0–P2（基础表 + 标识 + 事件归因）之后，否则 `task_id` 无落点。

### 6.4 取消与失败
- 取消某一轮迭代：只取消该 `run_id`，`generation_task` 回到上一版本 `current_bundle_ref`，`task_turn` 记 `CANCELLED`。
- 失败：单 turn 失败不影响同会话其他任务；会话不因单 turn 失败进入终态（区别于现状"一次失败=会话 FAILED"）。

## §8 建议落地顺序（每步可独立验收）

| 步 | 内容 | 验收 |

## §10 风险与未决

| # | 项目 | 结论 / 推荐 | 影响 |
|---|---|---|---|
| O1 | `FactSummary` 的任务上限与字段上限 | 推荐 `MAX_TASKS_IN_SUMMARY=8`、`MAX_KEY_FEATURES=5`，影子校准 | 超限时按时间裁剪，需验收"不丢当前任务" |
| O2 | 非控件意图在多轮会话的处理 | 推荐沿用 M06 拒绝；**不**因为"在对话中"放宽 | 守住 §1 覆盖边界，防退化成通用聊天 |
| O3 | 同一 task 并发迭代冲突策略 | 推荐乐观并发 + 409（不静默排队） | 前端需处理 409 重试 |
| O4 | 无 `target_task_id` 且多任务的默认行为 | 推荐 `ASK_USER` 消歧（不默认最近任务） | 与 ADR-006 O5"仅歧义时确认"一致 |
| O5 | 产物版本保留策略 | 推荐全留（turn 级 `result_bundle_ref`），不做 GC | 存储增长；M09 需支持多版本 bundle（其设计已含版本/hash） |
| O6 | 与 ADR-006 的实现先后 | **硬前置**：P0–P2 之后才做本 ADR P1+ | ADR-006 仍未改码 → 本 ADR 也进不了实现 |
| O7 | 结构化摘要能否满足"记得更早修改" | 推荐只保留每任务 last_intent + spec 摘要，不保留完整历史意图链 | 用户要"记得三句话前"则不满足；需 revisit §1 覆盖边界 |

**其他风险**：会话 `COMPLETED` 可再提交会改变 SSE 消费者假设（前端需按 `parent_run_id` 区分轮次）；`FactSummary` 的 `last_intent` 是用户原文短文本，需确保 M06 注入过滤已过（不能把攻击载荷带进下一轮）；`cost_ledger` 按 turn 分账需要与 M11 指标对齐。
