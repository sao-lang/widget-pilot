## §1 设计意图（Design Intent）

- **一句话意图**：整条级联只回答「用户是不是想要一个手机 widget」，不回答「是哪一种 widget」；`WidgetType` 仅作路由/遥测提示槽位，任何未知意图落 `custom` 也不被拒。
- **设计原则**（可判定，适用于 L1–L4 与语义层）：
  1. **类型不是门禁**：L1 触发、L2 样本、L3/L4 输出、语义层槽位检查均不得依赖 `alarm|clock|task|calendar` 枚举；放行依据是「生成/放置/展示意图 + 宿主或控件对象」。
  2. **内容词开放**：天气、倒计时、便签、健康、快递、股票、智能家居等数据词族**只加权不设门槛**；新场景出现时不需要修改级联才能放行。
  3. **负向联合条件**：查询/闲聊/创作类词不得裸用一票否决，必须与「无宿主 + 无生成动词」联合判定。
  4. **拒绝类零模型**：I14 不变——`OUT_OF_SCOPE` 仍只出自 L1，`is_out_of_scope()` 先于语义层短路，零 embed/classifier/gateway 调用；L2/L3/L4 即使输出 OUT_OF_SCOPE 也不采纳为拒绝。
  5. **回归硬约束**：现有三条硬样本必须同时成立：`今天天气怎么样` → OUT_OF_SCOPE；`帮我做一个聊天界面控件`/`做一个天气预报的日历 widget`/`生成一个翻译任务清单卡片` → 放行；`给我整一个能显示日期的小玩意` → L1 未命中（走 L2/L3）。
  6. **契约只收窄不换形**：`IntentCategory`/`RouteLayer`/`fallback_reason` 六个归因串/事件 payload 键/`ValidationResult.widget_type` 字段/`IntentGateway.resolve` 输出三字段全部保留；只改判定依据与样本内容。
- **价值排序**：召回（新场景不误拒） > 拒绝类确定性（I14） > 既有测试稳定性 > 词表简洁。
- **反意图**：不把 L1 做成 LLM 分类器；不把「天气/新闻/显示/卡片/桌面」等裸词单独作为正向或负向判据；不在本阶段实现设备 API 与沙箱校验。

## §2 背景与目标

- **现状**（源码核实，2026-11-21）：
  - `constants.py:84-87` 正向表是 `(做|生成|来|给我|创建).*(控件|组件|日历|时钟|闹钟|待办|任务|清单|卡片|界面|widget|calendar|clock)` 与 `^(日历|时钟|闹钟|待办|任务|清单)`——**控件类型被写在触发条件里**。
  - `constants.py:77-81` 负向表含裸词 `天气|新闻|聊天|翻译`；`intent_cascade.py:52-68` 靠「正向优先」兜住合法控件请求，但「桌面上显示未来一周天气」「把快递进度放到主屏」「帮我做个锁屏倒计时」全部落不到正向，其中带裸词的还会被拒。
  - `patterns/intent.py:11` 另有一份更窄的负向正则（`今天(天气|新闻).*怎么样|...`），与 L1 口径不一致；`validate_chain.py:382-387` 的 `_infer_widget` 又硬编码了四组词——同一概念三处事实来源。
  - L2 `semantic_router.py:21-25` 只有三条类型化样本（`生成手机控件 日历 时钟 待办`/`做一个能翻月的日历控件`/`给我一个时钟组件`），`:49` 的 `_VOCAB` 额外注入 `{"日历","时钟","闹钟","待办","控件","翻月","日期","组件"}`；样本扩容会改变共享 bigram 词表维度，`0.75` 阈值须重校准。
  - 语义层 `semantic.py:31-51` 的 R1 槽位检查依赖 `WIDGET_HINTS`（类型词）或 `FEATURE_HINTS`（绑类型的特征词）；`grid_resolver.py:24-29,100-117` 用 `WIDGET_TYPICAL_GRIDS` 按类型给密度建议——新场景（天气卡片/快递组件）只能靠特征词兜底。
  - `change_gate.py:15-33` 的 `ConfigSnapshot` 指纹不含意图词表/样本版本，词表与样本扩展不会触发回归门禁。
- **用户目标**：补充真实场景（一周天气需多接口校验、闹钟需对接设备、刷新/渲染影响续航、生成代码需安全与设备接口校验），并明确「不要限定死 widget 类型」；2026-11-21 20:2x 追加要求「级联路由整个都要调整，里面 widget 都要去类型化」。
- **为什么整条级联一起改**：只改 L1 会让 L2 样本库、语义层槽位与密度建议继续按类型裁定，新场景在 L1 放行后仍会在语义层被 `INPUT_INVALID`/`SPEC_MISSING` 挡下；L3/L4 本身只输出 `IntentCategory`（`types.py:34-40`），不需改输出契约，只需明确其判定语义是「是否生成 widget」而非类型。设备/性能/安全校验依赖 M08 沙箱执行与隔离，当前 `sandbox_runner/executor.py` 只有裸 `docker run`、无隔离，故列为后续阶段。

## §5 需求清单（编号、可测、可追溯）

- FR-1：正向表覆盖「生成/创建/放置/展示动作 × 宿主位置/控件对象」联合条件，宿主词包含 桌面/主屏/锁屏/负一屏/小组件/万能卡片/服务卡片/卡片/挂件/面板/Widget/智能叠放。 — 验收：`桌面上显示未来一周天气`、`帮我做个锁屏倒计时`、`把快递进度放到主屏` 由 L1 判为 WIDGET_GENERATION。
- FR-2：正向表覆盖「数据词 × 宿主」紧邻共现（`一周天气卡片`、`快递小组件`）；表外新数据词由「生成动作 × 宿主」规则兜底（须有动作，不裸词放行）。 — 验收：表内数据词与宿主共现命中；未收录数据词配合生成动词与宿主仍能命中。
- FR-3：负向表覆盖 8 族（查询问答/告知叙述/非 widget 创作/设备直操/教程咨询/开发语境/裸数据词/状态描述），且全部为联合条件或锚定形式。 — 验收：`今天天气怎么样`、`讲个笑话`、`写个爬虫`、`天气`（裸词）判 OUT_OF_SCOPE。
- FR-4：负向表不得吃掉包含宿主或生成动作的合法请求。 — 验收：现有 `test_a3_legitimate_widget_not_rejected` 三条 + 新增 `能帮我在桌面加个天气吗`、`小组件怎么添加`（后者应为负向教程族，需有正向生成动词才翻正）。
- FR-5：长尾保护——`给我整一个能显示日期的小玩意` 继续走 L2/L3。 — 验收：`_l1_rule_intent` 对其返回 None；`test_a25_route_layer_logged` 的 L1=2/3 比例不变。
- FR-6：`patterns/intent.py` 的 `INTENT_GENERIC_CHAT` regex 与 L1 负向表同源。 — 验收：同一组样本在 `is_out_of_scope()` 与 `check_input()` 结论一致。
- FR-7：词表版本进入 `ConfigSnapshot` 指纹。 — 验收：扩展词表后 `diff_config` 非空。
- FR-8：拒绝类语义与留证链不变。 — 验收：`test_a3_out_of_scope`、`test_a24_reject_zero_models`、`test_a3_short_circuit_writes_guard_hit`、`test_error_event_emitted_for_out_of_scope` 原样通过。
- FR-9：L2 样本库去类型化——`_SAMPLES[WIDGET_GENERATION]` 扩为 11 类无类型词说法，`_VOCAB` 去掉 `日历/时钟/闹钟/待办` 硬编码；`INTENT_SAMPLES_VERSION=v2`。默认 embedder 对未见说法仍可能降级 L3/L4（结构化兜底放行），本阶段不做阈值硬校准。 — 验收：样本与词表常量中不含 widget 类型词；`DefaultEmbedder` 零依赖测试仍绿。
- FR-10：语义层 R1 槽位去类型化——「宿主/产物锚点 OR 开放特征词」即视为描述充分，提示文案不再举具体类型。 — 验收：`帮我做一个天气卡片` 与 `桌面上显示一周天气` 过 R1；`来个有样式的玩意` 仍拒。
- FR-11：密度建议去类型化——`grid_resolver` 以 `DENSITY_HINTS`（内容特征→建议网格）替代 `_detect_widget + WIDGET_TYPICAL_GRIDS`，未知落默认建议。 — 验收：新场景描述能拿到 GridSpec 建议；冲突过滤用例仍绿。
- FR-12：类型字段只为契约兼容——`validate_chain.widget_type` 恒 `WidgetType.CUSTOM`，无 `_infer_widget`/`intent_hints._HINT_PATTERNS` 等任何推断模块；不参与放行/升级判定。 — 验收：任意描述均 `widget_type=custom`；`intent_hints` 模块不存在；routing 事件键集与 `ValidationResult.widget_type` 字段保留。
- FR-13：L3/L4 语义明确——`StructuredFallback`/`IntentGateway.resolve` 只输出 `IntentCategory`，不产生 widget 类型字段；OUT_OF_SCOPE 输出不被采纳为拒绝。 — 验收：`test_m06_routing_ports.py` 的 L2/L3/L4 拒绝不采纳用例原样通过。

## §6 Approaches（必备节）

| 方案 | 做法 | 结论 |
|---|---|---|
| A 扩充 `WidgetType` 枚举 | 每来一个场景加一个类型值 | **否决**：类型仍是门禁，场景无限而枚举有限；改契约需四份副本+SDK 重生成 |
| B 裸词继续扩表 | 在正向/负向表里罗列更多名词 | **否决**：`天气`/`显示`/`卡片`/`桌面` 裸词必然误判；现有长尾测试被 L1 吸收，15+ 用例红 |
| C 语义族联合条件 | 动作/宿主/数据词分组，AND + 共现窗口，负向联合排除 | **采纳**：保留双循环与 I14，词表保持 `tuple[str,...]`，召回与稳定性兼得 |
| D 把 L1 换成小模型分类 | 用 embedding/LLM 判意图 | **否决**：I14 要求拒绝类零模型调用；延迟与成本不可接受 |

## §7 架构设计

### 7.1 判定流（不变）

`_l1_rule_intent(text)`：正向表逐条 `re.search` → 命中即 `WIDGET_GENERATION`；负向表逐条 → 命中即 `OUT_OF_SCOPE`；否则 `None`。`is_out_of_scope()` 仅取 `OUT_OF_SCOPE`，`validate_chain` step0 先于语义层短路。`intent_cascade.py:116/172/215` 三处 I14 校验原样保留。

### 7.2 正向语义族（P1–P8）

| 族 | 内容 | 触发力 |
|---|---|---|
| P1 创建生成 | 做/生成/创建/弄/搞/来个/整个/整一个/新建 | 必要（与 P2/P4 共现） |
| P2 放置安置 | 加/添加/放/摆/挂/贴/塞/放到/加到/置于 | 必要（与 P4 共现） |
| P3 展示呈现 | 显示/展示/呈现/能看到/看得见 | 必须与 P4 宿主共现，禁止裸用 |
| P4 宿主/产物锚点 | 桌面/主屏/锁屏/负一屏/小组件/组件/万能卡片/服务卡片/卡片/挂件/面板/Widget/智能叠放 + 广义 控件/界面/列表 | 核心锚点 |
| P5 组合/叠放 | 并排/一起/同时/加上/旁边/叠/堆叠/组合 | 加权，不单独触发 |
| P6 时间/刷新修饰 | 一周/未来几天/每 N 分钟/实时/自动刷新/常驻/离…还有 | 加权，不单独触发 |
| P7 数据/能力词 | 气象/时间/日程效率/健康/系统/金融/生活/媒体/设备/通讯十族（开放） | 弱加权，永不单独触发 |
| P8 指代省略 | 也加一个/再来一个放旁边 | 低置信补充，依赖上下文承接（本阶段不实现） |

组合成正则的示意（最终以 constants 内具名常量拼接为准）：

```text
P1/P2 × {0,12} × P4                       # 做/加/放 + 宿主/控件
P4 × {0,8} × P3                           # 桌面/锁屏 + 显示/展示
P7 × {0,6} × P4                           # 天气/快递/股票 + 卡片/组件
P1/P2 × {0,8} × P7 × {0,6} × P4           # 生成 + 数据词 + 宿主
```

### 7.3 负向语义族（N1–N8）

| 族 | 例 | 联合条件 |
|---|---|---|
| N1 查询问答 | `今天天气怎么样`、`金价多少`、`快递到哪了` | 疑问/询问句式 **AND** 无 P4 宿主 **AND** 无 P1/P2 |
| N2 告知叙述 | `告诉我…`、`讲讲历史`、`解释一下…` | 告知动词 **AND** 无 P4 |
| N3 非 widget 创作 | `写个爬虫`、`翻译这段`、`写首诗`、`帮我写封邮件` | 创作动词 × 非 widget 产物名词 |
| N4 设备直操 | `把灯关了`、`播放周杰伦的歌`、`设个 7 点闹钟`、`下单` | 执行动词直接作用设备/服务 **AND** 无 P4 |
| N5 教程咨询 | `小组件怎么添加`、`Widget 怎么用` | 询问操作方法 **AND** 无明确生成动词 |
| N6 开发语境 | `写个 Android Widget`、`用 Swift 做个小组件项目` | 代码/项目/SDK/API/开发/报错 与 widget 词共现 |
| N7 裸数据词 | `天气`、`股票`、`倒计时`、`电量` | 整句锚定，无宿主无动作 |
| N8 状态描述 | `屏幕显示无信号`、`显示电量不足` | 显示 + 错误/状态名词，无宿主生成意图 |

### 7.4 长尾与灰区

- `给我整一个能显示日期的小玩意`：「整一个」在 P1 但「小玩意」不在 P4，`显示` 是 P3 且无宿主 → 三条联合条件均不成立 → L1 返回 None，保留 L2/L3 测试分层。
- `能帮我在桌面加个天气吗？`：疑问句但 P4「桌面」+ P2「加」共现 → 正向裁定，疑问语气不否决正向。
- `帮我做一个聊天界面控件` / `生成一个翻译任务清单卡片`：P1 + P4 命中 → 正向，负向裸词不吞。
- `今天天气怎么样`：无 P4/P1/P2，N1 问句命中 → OUT_OF_SCOPE，零模型。

### 7.5 重复源收敛

1. `patterns/intent.py` 的 regex 由 `INTENT_GUARD_PATTERNS` 拼接生成——与 L1 负向语义族同源的 `check_input` 子集（N1/N4 因进护栏无正向优先而自带「宿主 + 生成动词」联合排除，复审 B1），保留 `rule_id=INTENT_GENERIC_CHAT` 与 hit_type。
2. `change_gate.py:15-33` 的 `ConfigSnapshot` 增 `intent_vocab_version` 字段（初值 `v2`），词表改动即在 `diff_config` 留痕。
3. `semantic_router._SAMPLES/_VOCAB` 同步去掉类型词、扩为 11 类无类型说法，版本升 `v2`；`semantic.py` 槽位检查改用锚点/特征词，`grid_resolver.py` 改用 `DENSITY_HINTS`。
4. `validate_chain.widget_type` 恒为 `WidgetType.CUSTOM`——字段与 routing 事件键仅为契约兼容保留；任何从描述推断类型的模块（含 `intent_hints._HINT_PATTERNS`）已删除，L1/L2/L3/L4 均不消费该值。

### 7.6 阶段切分与依赖闸门

```text
本次改码（L1 词表 + L2 样本/词表 + 语义层 + 密度建议 + hint + 指纹）→ TDD/全量门禁/独立复审
                              → 后续：设备 API/续航/沙箱校验（需 M08 隔离能力先补齐）
```

级联全链一次验收；M08 沙箱隔离未落地不进后续阶段。

## §8 其他关键设计维度

- **留证与事件**：step0 短路仍写 `guard_hit`（`INTENT_GENERIC_CHAT`）、四字段 guard hits、error 事件、`IntentRouteLogRow(L1, OUT_OF_SCOPE)`；正向放行仍产 guard/routing/plan 三类事件。本方案不改事件 schema。
- **可观测性**：新增词表版本写入配置指纹；建议（非本阶段）在 routing 事件附加命中的语义族 id，便于统计误判率与覆盖率。
- **风险与缓解**：① 正向扩得太宽吞掉长尾 → 用三条硬样本作回归闸门；② 负向收紧放走纯问答 → `今天天气怎么样` 与 `check_input` 一致性用例；③ 词表版本失控 → `change_gate` 指纹。
- **隐私/安全**：L1 只读用户描述字符串，不落原文之外的存储；注入/PII 仍由 `input_guard` 独立负责。

## §9 样例之外覆盖（examples → full spec）

用户样例是「天气 widget 要调接口」「闹钟要对接设备」「刷新影响续航」「代码要安全校验」。按 `examples-to-spec` 六维外推：

| 维度 | 补全项 | 依据 |
|---|---|---|
| 同类枚举 | 信息展示/时间日程/效率工具/健康运动/设备控制/媒体娱乐/生活服务/金融信息/系统状态/AI 生成/通讯社交 11 类，及中英文说法 | 从「天气/闹钟/任务」三个样例外推同类手机 widget 场景 |
| 边界值 | 裸数据词、只有宿主词、只有动作词、超长组合句、疑问句、中英混排 | 从「天气」裸词误拒反推 |
| 异常路径 | 未收录数据词、未知宿主别名、拼写/空格变体、`Widget` 大小写 | 从「不要限定死类型」反推开放集合需求 |
| 变体 | `小组件/组件/挂件/万能卡片/服务卡片/Widget`；`做/整/弄/加/放/摆/挂` | 从「做一个…」单一说法外推 |
| 关联项 | `patterns/intent.py`、`change_gate`、`semantic_router`、`_infer_widget`、M06 文档与代码阅读指南 | 从「改词表」外推同概念其他出现 |
| 反向 | 纯问答/创作/设备直操/教程/开发语境必须仍拒；长尾小玩意仍走 L2/L3 | 从「覆盖大部分意图」外推误判防线 |

以上补全项均已纳入 §5/§7；需用户拍板的边界在 §10。

## §11 约束与红线

- 不改 `IntentCategory` / `ReasonCode` / 事件 schema / SDK 契约；不新增 widget 类型枚举值。
- L1/L2/L3/L4 的拒绝与升级语义不变：L1 零模型、正向优先、`None` 可继续级联；I14 三处校验与六个 fallback 归因串原样保留。
- 任何正向规则不得仅凭裸数据词或裸「显示」命中；任何负向规则不得仅凭裸 `天气/新闻/翻译/聊天` 否决；L2 样本/词表不得把 widget 类型当分类键。
- 全级联改码必须以现有硬样本与分层测试全绿为出口，禁止改断言造假绿。
- 后续设备/续航/沙箱阶段之前不得声称「代码安全性/续航/设备对接已校验」。
