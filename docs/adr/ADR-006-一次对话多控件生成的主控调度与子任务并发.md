# ADR-006：一次对话多控件生成的主控调度与子任务并发（v1.0，代码已落地）

**状态**: **v1.0 已落地（2026-11-22）**——任务层（契约 + 迁移 + 规划器 + fan-out/fan-in + Coordinator + seq 原子化 + 事件归因）与角色层（见 ADR-007）均已改码并有测试证据；**保守触发**（§5 step3 / §6.7 澄清）：单 widget 信号走现有 `run()` 直路（零回归），仅多 widget 信号走规划器。全量 **622 passed**（真 PG/Redis/Docker 集成真跑）、ruff 全绿、pyright 0 errors、`contracts:check` drift=[]。**缺口（不冒充已实现）**：无真实模型端点 → Planner 生产 fail-fast、测试 mock；M08 V3 门禁未强制串进 `run()`（见 M08 §9.0）；逐块证据见 §8/§12。
**范围**: 一次用户消息要求生成 ≥2 个 widget 时，在安全门禁通过后先做路径规划，单任务沿用现有固定流程，多任务拆成并发子任务并由确定性主控统一调度、汇总与回传
**关联**: `docs/adr/ADR-001`（规格缺省询问 / 执行中澄清）、`ADR-002`（记忆）、`ADR-003`（能力按需披露）、`ADR-004`（意图级联去类型化）、`ADR-005`（进护栏）、`ADR-007`（角色层，本 ADR 任务层的上层）；`docs/modules/00-总览与模块地图.md` §1.6 D-5 / §1.7、M04/M06/M07 模块文档
**变更类型**: 设计变更（会话状态 + 事件契约 + PG 迁移 + 编排调度）；v0.1–v0.2 为草案，v1.0 已按本 ADR 完成实现（证据见 §8/§12）
**一句话结论**: 保留现有 agent loop 作为唯一执行内核，在它前面加一层「约束式 LLM TaskPlanner + 确定性 Coordinator」；主控不调用模型，规划器才调用模型且只产出受事实约束的结构化任务清单；校验采用「前置安全门禁 → 规划 → 计划级校验 → 子任务出护栏」三明治，而不是一次性全量校验。

## §0 为什么需要这份 ADR

用户原话场景：一次对话中可能要求生成 2 个以上 widget；用户输入和附件进后端后先校验，校验没问题再规划路径；单任务走现在的固定流程，多任务拆成多个 agent 同时工作，主控 agent 统一调度。

这不是"再写个循环"就能解决的事：现状的会话、事件序号、SSE 流、成本账、租约全都按**单 run**假设设计。本 ADR 先把"哪些必须改、哪些可以原样复用、哪些明确不做"钉死，避免改码时散落决策。

2026-11-22 用户追加反馈，已并入本版：
1. 规划器不能用纯规则——用户输入不可预估，附件分配与描述派生需要语义理解（§6.7）。
2. 校验链在规划之前还是之后需要明确——答案是分职责三明治（§6.3），不是二选一。
3. 拍板：主控 = 确定性调度器；部分成功 = `COMPLETED + notice`；仅歧义时向用户确认计划。

## §2 与既有非目标的覆盖声明（必须显式）

- `docs/modules/00-总览与模块地图.md` §1.7 写明"不做多 Agent 角色编排"，§1.6 D-5 写明"不使用任何 Agent 框架"。
- **D-5 不变**：仍然不引入 LangChain / LangGraph / Temporal / 任何 Agent 框架；`decide()`、checkpoint、租约、事件流继续手写。
- **§1.7 的那一条被本 ADR 有条件覆盖**：新增的是**确定性、受控的任务扇出（fan-out/fan-in）**——子任务执行体就是现有的 `run()`，主控是调度器而不是新角色、不是自由对话的多 agent 协作。覆盖仅限"一次请求内多个独立 widget 生成"；通用多角色编排、agent 之间自由通信、DAG 工作流仍为非目标。
- 用户已拍板 O1 = 确定性主控，因此不触发"LLM 主控"的第二次覆盖，无需 ADR-007。**调用模型的是规划器，不是主控**——这个边界要在实现时保持，不能让 planner 反过来决定入队/终态。

### 2.1 术语定性：这不是"多 Agent 架构"，而是"同构执行单元的并发扇出"

- 项目文档语境里的"多 Agent 架构"指**多角色、多目标、agent 间通信/协商/共享工作记忆**的系统（§1.7 非目标）。本方案不满足其中任何一条：所有子任务跑的是同一个 `run()` 内核、持有同一套能力/记忆端口，彼此不知道对方存在、不通信、不协商、没有共享可写内存；主控是零模型的确定性状态机，不是 agent。
- 若按"任何自主执行循环都算 agent"的宽口径，确实有 N 个 agent 实例在跑；所以更准确的命名是**「单 agent 类型的 N 路并发扇出 + 中心化调度」**（parallel map / fan-out executor），而不是 multi-agent system。
- 这与 2026-11-22 早些时候"现阶段不适合多 agent"的评估不矛盾：那次评估针对的是**把系统拆成多个 agent 角色**；本次新增的是**一次请求内多个独立交付物**的并发需求，两者不在同一轴。
- **与 ADR-007 合并后的定性（2026-11-22 用户拍板）**：多 widget 任务（N>1）直接接入 ADR-007 的 Generator/Reviewer 角色层，因此**多 widget 任务整体就是多 Agent 架构**；本 ADR 单独看仍只是任务层扇出，不是多 agent。统一阅读入口：`docs/多Widget任务的多Agent协作架构-整合设计.md`。
- 若将来再做按 widget 类型专精的角色分化或 agent 自主再拆分任务，仍需另行评审并按真实多 agent 重评 D-5 / §1.7；本 ADR 不为此背书。

## §3 目标 / 非目标

**目标**
1. 一次消息生成 N 个独立 widget；N=1 时行为与现在逐字节一致。
2. 安全门禁先于规划，计划校验先于 fan-out，产物出护栏照旧；三道关各管一段，不互相替代。
3. 子任务真正并发、故障隔离、成本独立分账、事件可按任务归因。
4. 会话只有一个权威终态，用户只看到一条 SSE 流、一个 `done`。
5. 规划器能在不可预估的自然语言输入下完成附件分配与描述派生，但输出必须受确定性事实约束且可复现。

**非目标（v1 明确不做）**
- 通用 DAG / 任务依赖图 / 子任务互相调用或对话。
- 主控用 LLM 决定调度（O1 已拍板不做）。
- 新增 `SessionState.PARTIAL`（O3 已拍板不做）。
- 通用 Agent 框架、agent 间共享可写内存、跨会话任务协作。
- 模型端点缺失时**静默降级为规则规划器**——v1 规划器必须用模型，生产缺端点即 fail-fast（§6.7）。

## §4 核心模型：三层标识与两个状态机

### 4.1 标识

| 标识 | 归属 | 生成时机 | 说明 |
|---|---|---|---|
| `session_id` | 会话 | 建会话 | 不变，用户与 SSE 的唯一锚点 |
| `parent_run_id` | 会话 | `submit_message` | **复用现有 `Session.run_id` 列**，语义升级为"本次请求父 run" |
| `task_id` | 生成任务 | 规划落库时 | `uuid5(parent_run_id, task_index)`，重试稳定、天然幂等 |
| `run_id` | 子任务 | 子任务首次消费时 | 每个子任务独立，直接复用租约 / checkpoint / cost_ledger |
| `task_index` / `task_total` | 生成任务 | 规划时 | 1-based，用于排序、预算切分与前端分卡 |

**关键**：`Session.run_id` 不新增列；子 run 不塞进 session 主记录，而是放进新表，避免把单列改成数组。

### 4.2 新表 `generation_task`（建议迁移 `0012_generation_tasks`）

| 列 | 类型 | 约束 | 含义 |
|---|---|---|---|
| `id` | text | PK | `task_id` |
| `session_id` | text | NOT NULL, FK sessions.id | 租户隔离经 session 传递 |
| `parent_run_id` | text | NOT NULL | 父 run，聚合锚点 |
| `run_id` | text | NULL, UNIQUE | 子 run；消费时分配，未启动为 NULL |
| `task_index` / `task_total` | integer | NOT NULL | 序号 / 总数 |
| `description` | text | NOT NULL | 子任务描述（规划器派生，父级原文另存 `original_description`） |
| `grid` | text | NULL | 子任务规格；必须与规划校验结果一致或由用户确认 |
| `attachment_ids` | jsonb | NOT NULL default `[]` | 附件子集 ID，原文只上传一次 |
| `state` | text | NOT NULL | 子任务状态机（§4.3） |
| `result_ref` | text | NULL | 成功产物 `bundle_id` |
| `reason_code` / `evidence_ref` | text | NULL | 失败原因与证据 |
| `created_at` / `updated_at` | timestamptz | NOT NULL | 审计与超时判定 |

唯一索引 `(parent_run_id, task_index)` 保证规划重入不产生重复子任务；索引 `(session_id, state)` 供 coordinator 扫描。

**规划留证列**：另建议加 `plan_trace_ref`（指向对象存储的 `PlanTrace` JSON，§6.7），否则模型规划结果不可复现、出了错拆无法追责。

### 4.3 两个状态机

- **会话层**：沿用现有 8 值 `SessionState`，不扩枚举。`RUNNING` = 规划中或子任务在途；`AWAITING_INPUT` = 任一子任务或规划器需澄清；`COMPLETED` / `FAILED` / `CANCELLED` = 父 run 裁决后的唯一终态。
- **子任务层**（新内部枚举，放 `services/orchestrator/tasks/states.py`，不进 M02 契约枚举）：`PENDING → QUEUED → RUNNING → VALIDATING → DONE`，旁路 `AWAITING_INPUT / FAILED / CANCELLED`。子任务终态不等于会话终态。

## §5 端到端流程（编号，可直接拆 PR）

1. **入口（不变）**：`POST /api/sessions/{id}/messages` → Pydantic `extra="forbid"` → JWT + TenantGuard → 附件此前已上传为 `attachment_ids`（S3/MinIO + PG）。
2. **建父 run（不变）**：`submit_message` 要求 DRAFT，`state=DRAFT→RUNNING`，分配 `parent_run_id`，保存 `original_description`。
3. **入队"规划任务"一条（仅多 widget 信号；保守触发，见 §6.7 第 7 点）**：不是立刻入队 N 条，而是先入队 1 条带 `planning=1` 的父任务；`test_m04_enqueue` 的"1 次 post = 恰好 1 条"断言因此保持成立。
   - **实现澄清（2026-11-22）**：§5 step3 原文"每条请求入队规划任务一条"与 §6.7/§3 目标 1"单任务零回归、不经过规划器"冲突。落地采用**保守触发**——单 widget 信号请求直接走现有 `run()` 直路（不入规划任务、零回归，真 PG/Redis 可验收）；仅多 widget 信号请求入 `planning=1` 规划任务。触发只回答"是否调规划器"，**N 的裁定、描述派生、附件分配全部仍由真实 `PlanLLM` 完成**（用户否决纯规则规划）。证据：`services/orchestrator/tasks/fanout.py:44` `needs_planning`（连接词/数词/对象词触发）、`dispatcher.py:550-585`。
4. **V1 前置安全门禁**：worker 取到规划任务后先跑 `validate_chain` 的**安全子集**——越界 `is_out_of_scope`、`check_input`（注入/PII/敏感词）、意图白名单（只判"是不是控件生成请求"，**不强行做单 widget 分类**）；拒绝/挂起路径与今天完全相同。guard 证据 hash 固化后随子任务继承。**不在这里跑逐 widget 规格充分性**，否则多任务消息会被整条误拒。
5. **规划（LLM + 事实约束）**：`FactExtractor` 先零模型产出 `PlanningFacts`（原文证据引用、附件 id/role/insight 摘要、已确认 grid、预算与并发上限）；`PlanLLM` 经真实模型端口产出严格 JSON 的 `TaskPlanDraft`（§6.7）；`PlanValidator` 零模型 fail-closed 校验，必要时有界修复 1 次。通过后产出结构化 `plan` 事件（§6.2）。
6. **V2 计划级校验（fan-out 前最后门禁）**：`PlanValidator` 校验 schema、附件 id 必须来自 facts 且 role 兼容、派生描述过 `check_input`、grid 合法、任务数/预算上限、依赖检测；歧义 → `AWAITING_INPUT`（`SPEC_MISSING` / `CLARIFICATION_REQUIRED` / `SPEC_CONFLICT`），安全命中 → `GUARD_INPUT_HIT`，超预算 → `BUDGET_EXHAUSTED`，超任务数 → `INPUT_INVALID`。依赖任务 v1 拒绝并请用户拆开（不做 DAG）。
7. **落库**：写 N 行 `generation_task`；`task_id = uuid5(parent_run_id, task_index)`，同时写 `plan_trace_ref`。
   - **N == 1**：直接走现有 `process_one → run()` 路径，`TaskFields` 不变、事件**不带** `taskId`、终态回写不变；子任务行仅用于可观测与成本归集。这是零回归分支。
   - **N > 1**：父预算预占，入队 N 条子任务（携带 `task_id / parent_run_id / task_index / task_total / planning=0`）。
8. **并发执行**：每个子任务由现有 worker 消费、分配独立 `run_id`、抢自己的 PG 租约、跑同一个 `run()` 内核、写自己的 checkpoint 与 cost_ledger。并发来源优先是 Redis consumer group 多消费者（多起 orchestrator 副本）；单副本内可选 `asyncio.gather` 限量并发（同一上限配置，默认关闭）。
9. **主控汇总**：`Coordinator`（orchestrator 内组件，不新增服务）轮询 + 事件驱动检查 `generation_task.state`；全部终态后幂等裁决会话终态，发出唯一的会话级 `done`，payload 带 `results[]`（task_id → bundle_id / reason_code）。
10. **结果回传与 V3**：所有子任务事件写入同一 session SSE Stream，靠 `taskId` 分区；前端按 task 渲染多张卡片，时间线按 seq 全局排序。每个子任务生成产物仍走现有出护栏/沙箱校验（M08），即 V3。

## §6 关键机制

### 6.1 并发、幂等、重试
- 复用 Redis Streams consumer group、XAUTOCLAIM（idle 5000ms）与 `MAX_RETRY=3`；子任务重试沿用 `task_id` 稳定键，不会重复建行。
- `run_id` 在子任务首次消费时分配；重试沿用同一 `run_id` 与 checkpoint 续跑，不新建 run。
- 租约 30s / 心跳 10s 不变；每个子 run 独立租约，互不阻塞。
- 规划器调用失败/超时属于父任务失败，走既有重试与死信，不产生半截 `generation_task`（校验通过后才落库）。

### 6.2 事件 seq 与归因（并发下的硬要求）
- **统一 seq 分配**：新增 `wp:eventseq:{session_id}` 的 Redis 原子 `INCR`，以 `max(session.last_seq, 事件窗口最大 seq)` 做一次性 seed；M04 loop、M05 sink、Coordinator、子任务共用这一域。现有 `seq.py:next_seq(events, session_id)` 从"重算"降级为 seed 兜底，不再作为运行时分配器。
- **事件加两个可选顶层字段**：`taskId: string`、`taskIndex: integer`。`additionalProperties: false` 故必须同步 schema 与手写 `AgentEvent`。
- **语义规则（重要）**：`done` / `error` **带 `taskId` = 子任务级，不带 = 会话级**。子任务失败可以发带 `taskId` 的 `error` 而不结束会话；只有 Coordinator 能发不带 `taskId` 的 `done` / `error`。`artifact` 一律带 `taskId`。
- **不新增 `AgentEventKind`**：17 种保持不变，`test_m03_contract` 的计数断言不动。`plan` payload 的 `oneOf` 增一个对象分支承载 `TaskPlan`，保留原字符串分支向前兼容。
- 子任务事件 `phase` 只写 `RUNNING` / `VALIDATING` / `AWAITING_INPUT`；`COMPLETED` / `FAILED` / `CANCELLED` 只允许 Coordinator 写。

### 6.3 校验时序：三明治，不是"之前或之后"二选一

| 阶段 | 校验内容 | 位置 | 为什么放在这里 |
|---|---|---|---|
| V0 | Pydantic `extra="forbid"`、JWT/TenantGuard、附件传输与幂等 | 入口，规划前 | 结构与租户边界必须先守，附件 id 必须真实存在 |
| V1 | 越界、注入/PII/敏感词、"是否控件生成请求"意图白名单 | **规划前** | 规划器会调用模型；不能让未过安全门禁的输入触发模型调用，否则越狱/间接注入与预算双重失控 |
| V2 | 计划 schema、附件引用真实性/role 兼容、派生描述 `check_input`、逐任务规格充分性、预算/并发、依赖 | **规划后、fan-out 前** | 规划器产物是新文本，原文校验覆盖不到；多任务的规格缺失必须逐任务判，不能在全局判 |
| V3 | 每个子任务 `run()` 内的语义校验与出护栏/沙箱（M08） | 执行中 / 产物后 | 生成结果仍需按既有门禁验收，不能被"计划已校验"替代 |

- 用户原话"校验没问题，先规划路径"对应的是 **V0 + V1**；完整闭环是 **V1 → V2 → V3**，缺一段都会出事：只前置会让坏计划直接 fan-out；只后置等于拿未经净化的用户输入去喂模型。
- 现有 `validate_chain` 是"单意图单任务"的全链（越界 → `check_input` → 语义充分性 → L1–L4 → `routing`/`plan`）。多任务下拆成两半：V1 保留安全子集与 `routing` 事件；语义充分性/规格判定移到 V2 逐任务做。**不在 V1 强行做 L1–L4 单分类**，否则"一个时钟 + 一个日历"这类多意图请求会被当成意图冲突。
- 附件只上传/解析一次（`AttachmentInsight` 落 S3/MinIO），V2 只检查规划器引用的 id 子集是否合法，子任务通过引用读取，不做二次处理。
- guard_hit 与 audit 留证带 `task_id`（表加列或写进 evidenceRef 结构化引用），否则同会话多任务无法归因。

### 6.4 澄清与恢复
- 子任务需要澄清 → 该子任务进 `AWAITING_INPUT`，Coordinator 把会话置 `AWAITING_INPUT`；**其他子任务继续跑**，不整体暂停。
- 规划器输出歧义（O5：仅歧义时确认）→ V2 置会话 `AWAITING_INPUT` 并发 `notice`，用户回答后**重跑规划**而非只补一个字段；已落库的 `generation_task` 在重规划时按 `uuid5` 复用/更新，不追加重复行。
- `POST /api/sessions/{id}/clarifications` 新增可选 `taskId`；缺省兼容现状（单任务）。回答后只重入对应子任务，上下文从 `generation_task.description` + `original_description` + `clarification_reply` 组装。
- 跨天恢复：`GET /sessions/{id}` 的 `run_id` 仍是 `parent_run_id`，另加 `tasks[]` 摘要（task_id / state / result_ref / grid），前端据此恢复多卡视图。

### 6.5 成本与预算
- 父 run 预算 = 全局剩余预算；fan-out 前预占，子任务上限 `min(策略单任务上限, 剩余预算 / N)`。
- 规划器调用本身也计费，并计入父 run 预算；V1 拒绝的请求不应产生规划器调用（可由 mock 断言调用次数为 0）。
- 每个子 run 独立 `cost_ledger` 行（已天然唯一），Coordinator 汇总 `cost_summary`；某子任务触顶只取消该子任务，剩余未启动任务不再入队。
- 复现指纹需包含 `task_id`、`PlanTrace`（§6.7），否则同一会话多任务无法稳定复现。

### 6.6 取消与失败
- 父级 `/cancel` → 所有未终态子任务置 `CANCELLED`；agent loop 在每个 super-step 边界读子任务状态做协作式取消（同时修掉 §1 中记录的现有竞态）。
- 全部子任务失败 → 会话 `FAILED`；部分成功 → 会话 `COMPLETED`，同时发一条 `notice` 汇总失败 task_id + reason_code，前端逐卡显示；成功 bundle 照常进控件墙。O3 已拍板，不新增 PARTIAL。
- "证据先于结论"由 `notice` 中的原因码 + 证据引用满足。

### 6.7 规划器详细设计（用户 2026-11-22 反馈：纯规则覆盖不了不可预估输入）

**结论**：规划决策交给模型，但模型只能在一个由确定性事实圈定的空间里做结构化选择；任何越界输出由零模型 validator fail-closed 拒绝。规则负责"给事实"，不负责"下结论"。

1. **`FactExtractor`（零模型）** 产出 `PlanningFacts`：
   - `original_description`（已过 V1，带 sha256 / evidenceRef）
   - `attachments[]`：`{id, role, mime, sha256, insight_ref, brief}`；`brief` 是长度受限的确定性摘要，附件正文不直接进规划 prompt（防间接注入与超长上下文）
   - `confirmed_grid` / `grid_source`、`preference_hints`（只读，不强制）、`budget_remaining`、`max_tasks`、租户/会话/trace 标识
2. **`PlanLLM`（真实 `ModelGatewayPort`，结构化 JSON 输出）** 产出 `TaskPlanDraft`：`tasks[{index, description, grid?, attachment_ids[], rationale}]` + `ambiguous_reason?`。硬约束：只能引用 facts 里的附件 id；一个附件被多任务引用必须给出理由；`rationale` 是结论式短句、不输出思维链；用户内容放在明确的数据段而非指令段（V1 已过滤，仍要做注入隔离）。
3. **`PlanValidator`（零模型，fail-closed）**：严格 schema；附件 id 必须存在且属于本会话、role 与任务语义兼容；派生描述过 `check_input`；grid ∈ `GridSpec` 或与已确认值一致；`1 ≤ N ≤ max_tasks`；预算切分合法；检测任务间依赖；重复/覆盖任务去重。失败时把结构化错误回灌模型做**有界修复 1 次**，仍失败按 §5 step 6 的 reason code 处理。
4. **`PlanTrace`**：记录 `prompt_hash / facts_hash / model_id+version / draft_hash / repair_count / validator_result`，写入 `generation_task.plan_trace_ref`、复现指纹与审计；同一 trace 可重放规划结果。
5. **模型缺口纪律**：当前无真实模型端点/key/权重 → `PlanLLM` 必须保留真实端口接线并在生产缺失时 **fail-fast**，不得静默降级为规则规划；测试用 mock 端口；在 `docs/modules/M07-模型依赖与测试缺口标注.md` 模板下新增规划器缺口条目。后果：多任务端到端验收在真实环境需等端点就绪（登记"环境阻断"），但**单任务零回归路径不经过规划器，可照常验收**。
6. **规划器不是主控**：`PlanLLM` 只返回任务清单，不返回入队顺序之外的调度指令；入队、预算裁决、终态仍归确定性 Coordinator（O1 边界）。
7. **保守触发澄清（2026-11-22 落地决策，回写 §5 step3 冲突）**：
   - **冲突**：§5 step3 写"每条请求入队规划任务一条"，而 §3 目标 1 / §6.7 第 5 点写"单任务零回归、不经过规划器"——二者对"单 widget 请求是否调规划器"给出相反指令。
   - **决策**：采用**保守触发**。`needs_planning(description)`（`services/orchestrator/tasks/fanout.py:44-52`）按连接词（和/与/及/、/）、数词+量词（两个/3 张…）、复数指代（都/各做一个）以及"连接词 + ≥2 个不同控件对象词"判定是否需要规划；**单 widget 信号直接走现有 `run()` 直路，零回归；仅多 widget 信号走规划器**。
   - **边界**：触发信号**只决定是否调用规划器**，绝不参与 N 裁定、描述派生、附件分配、grid 决策——这些全部仍由真实 `PlanLLM` 在 `PlanningFacts` 事实空间内裁定（§6.7 第 2/3 点，用户否决纯规则规划）。
   - **理由**：让"单任务零回归"与"多任务走规划"两条验收路径都可独立真实验收（前者不依赖模型端点），同时避免把自然语言触发信号误当成规划结论。
   - **证据**：`services/orchestrator/tasks/fanout.py:31-52`（`_MULTI_SIGNAL` / `_CONNECTIVE_WORDS` / `_WIDGET_OBJECTS` / `needs_planning`）、`dispatcher.py:550-585`（`needs_planning` 守卫 + `run_fanout_planning` 真实 PlanLLM）。

## §9 可断言验收用例（草案）

1. Given 单任务描述；When 提交；Then 入队恰好 1 条、`TaskFields` 无新必填字段、事件无 `taskId`、终态与现状一致。
2. Given "做一个时钟，再做一个 4x4 日历，日历用附件 A 做风格参考"；When 规划（mock 模型）；Then `TaskPlan.tasks.length == 2`，各带派生描述、grid、附件子集与稳定 `task_id`。
3. Given N=3；When 执行；Then 3 个不同 `run_id`、3 行 cost_ledger、3 份独立 checkpoint，且 SSE 中 seq 严格递增无重复。
4. Given 两子任务并行；When 其中一个出护栏命中；Then 该任务发带 `taskId` 的 `error`，另一任务完成，会话不提前 `FAILED`。
5. Given 全部子任务 DONE；When fan-in；Then 恰好 1 条不带 `taskId` 的 `done`、session `COMPLETED`、结果数 == N。
6. Given 部分失败；When fan-in；Then `COMPLETED` + `notice`（含失败 task_id 与 reason_code），成功 bundle 可渲染。
7. Given 子任务需要澄清；When 回答；Then 只重入该 `task_id`，其他子任务状态不被重置。
8. Given 父级 cancel；When 子任务在 RUNNING；Then 在下一个 super-step 边界转为 CANCELLED，且最终不被完成回写覆盖。
9. Given 规划产出第 2 个任务依赖第 1 个；When V2；Then 不 fan-out，返回 `CLARIFICATION_REQUIRED`。
10. Given 同一 `parent_run_id` 重复规划；When 落库；Then `generation_task` 行数不增加（uuid5 唯一约束）。
11. Given V1 命中注入/PII；When 进入规划阶段前；Then 模型端口调用次数为 0，请求按 `GUARD_INPUT_HIT` 拒绝——证明安全门禁确实在规划**之前**。
12. Given 规划器输出一个不在 `PlanningFacts.attachments` 里的附件 id；When V2；Then 整份计划被拒、不落 `generation_task`、不 fan-out，且 `PlanTrace` 留证。
13. Given 规划器派生描述含注入形状；When V2；Then `GUARD_INPUT_HIT`，有界修复 1 次后仍失败则挂起，不进入执行。
