## 0. 关键结论摘要（≤10 条）

1. **三层分层已成 2025-2026 行业共识**：working（上下文内）/ episodic（交互历史）/ semantic（提炼事实），
   外加 archival cold storage；分歧只在"谁决定层间移动、何时移动"。【论文/官方：MemGPT/Letta、LangMem、Zep、Cognee 文档】
2. **M7 现有 v1.4 记忆设计方向与社区主流高度一致**：三层边界、写入时四操作裁定、检索期衰减、
   失效不删除（软失效）、零 LLM 抽取。社区里 Zep/Graphiti 的 bi-temporal 失效、Mem0g 的边失效、
   Mem0 的 ADD/UPDATE/DELETE/NOOP 都是同一思路的不同实现。【论文/官方】
3. **但 M7 只有"偏好记忆"一种长期记忆，缺程序记忆（procedural）**：社区主流（LangMem、CrewAI、MemOS）
   都把"学会怎么做"作为独立一类；M7 可在不引入 LLM 的前提下，用"采纳产物/复用 recipe 版本"作显式程序信号补上。【论文/官方】
4. **"简单方案够不够"是开放问题**：Letta 自己用"整段对话写文件 + 强模型按需重读"在 LoCoMo 拿到 74.0%，
   高于 Mem0 论文报告的 68.5%——说明 retrieval-shaped benchmark 可能高估复杂记忆系统的必要性。
   但 Letta 同时承认该 benchmark 没测"陈旧事实、用户隔离、成本、错误行为"，不能反推"不需要记忆系统"。【论文/官方+媒体】
5. **图记忆（Zep/Graphiti、Cognee、Mem0g、A-MEM）的价值集中在关系/时序推理**；WidgetPilot 的偏好是
   少量结构化字段（palette / grids / widget types），**上知识图谱属于过度工程**：延迟、成本、schema 维护、
   PII 画像合规风险都显著。【论文/官方+媒体】
6. **Context engineering 的四操作框架（Write / Select / Compress / Isolate）已被 LangChain、Anthropic、
   Manus 共同采用**；M7 的六槽位固定装配 + JIT offloading + 只压缩 tool message 已覆盖 Write/Select/Compress，
   Isolate 因单 loop 零 Agent 框架被明确不采纳——理由成立（多 agent 约 15× token）。【论文/官方+媒体】
7. **缓存前缀纪律是生产 Agent 的第一性指标**：Manus 称 KV-cache hit rate 是"生产 agent 最重要的单一指标"，
   缓存输入成本可比未缓存低约 10×；M7 已要求 system prompt 前缀逐字不变、append-only、工具只 mask 不 remove——
   正确，应固化为回归门禁。【媒体/二手：Manus 2025-07-18】
8. **检索必须"宽召回 + 强制重排 + 证据包组装"**：社区共识是先混合召回 100-300 候选，rerank 到 20-40，
   再按"指令优先、去重、多样化、硬 token 上限"组装；把召回原文直接塞进上下文是典型反模式。【论文/官方+社区】
9. **记忆写入是安全攻击面**：OWASP《Top 10 for Agentic Applications》(2025-12) 把"Memory and Context Poisoning"
   列为 ASI-06；MINJA 报告 98.2% 注入成功率，AgentPoison 用 <0.1% 污染率做到 >80% 攻击成功率。
   M7 的"零 LLM 抽取 + 四类信号白名单 + 源权重 + PII 禁存"恰好是有效缓解，应保留并补"写入来源审计 + 用户可见可删"。【论文/官方+媒体】
10. **无真实模型环境下，社区方案中凡依赖 embedding / 摘要压缩 / 语义抽取 / 重排 / LLM-as-judge 的能力一律
    "留真实接线 + mock 测试 + 缺口追踪文档"**；M7 当前"不引入 LLM 摘要器/不调用模型抽取"的取舍，
    恰好把大部分模型依赖挡在记忆路径之外，是成本与确定性的优势，但 M10 检索链路的 embedding/rerank 缺口必须单独标注。【项目约定+本报告建议】

## 1. 记忆分层：社区全景

### 1.1 时间尺度分层（短期 vs 长期）

| 尺度 | 载体 | 典型 TTL / 生命周期 | 代表实现 |
|---|---|---|---|
| 会话内工作记忆 | 上下文窗口 / checkpoint / 事件流 | 会话结束即清 | LangGraph checkpoints、Letta Core memory、Mem0 conversation/session memory |
| 会话级压缩记忆 | 摘要 / 结构化笔记，按需回读 | 分钟~小时，任务完成即重置 | Deep Agents scratchpad、Claude Code compaction、Mem0 session memory (`run_id` 绑定自动过期) |
| 跨会话长期记忆 | 向量/图/KV 持久化 | 数周~永久，可配置 retention | Mem0 user memory、Letta archival、Zep semantic entity layer、Cognee graph |

【论文/官方：Mem0 docs via aiwiki.ai；Zylos 2026-04 综述；Letta 文档】

### 1.2 认知类型分层（working / episodic / semantic / procedural）

| 类型 | 存什么 | 社区典型实现 | 组织方式 |
|---|---|---|---|
| Working | 当前步的原始消息、工具结果、活跃状态 | Letta Core memory blocks（always in context，2-4KB，可带 size limit） | 常驻上下文 / Jinja 模板编译 |
| Episodic | "何时/何地/发生了什么"的交互经历 | Letta Recall（自动持久化全量交互，向量+全文+混合检索）、Zep episode subgraph（无损 raw source of truth）、LangMem episodic（few-shot 经验） | 只追加日志 + 时间过滤 |
| Semantic | 提炼出的稳定事实/偏好/实体关系 | Mem0 semantic facts（权重 0.6）、Zep semantic entity subgraph（v3 支持 9 种节点/8 种关系）、LangMem semantic（profiles 单文档 / collections 开放集） | KV / 向量 / 知识图谱 |
| Procedural | "怎么做"的工作流、工具使用习惯、prompt 规则 | LangMem procedural（prompt optimizer / Trustcall 改 system prompt）、CrewAI/MemOS tool & skill memory | prompt 规则 / 技能库 |

【论文/官方：LangMem 发布文与文档、Zep 架构文档、Letta/MemGPT 论文】
> 注：Mem0 在 user memory 内部用 semantic 0.6 / episodic 0.3 / procedural 0.1 的**类型权重**参与检索打分，
> 且top-5、<200 token 注入——这是可直接借鉴的"记忆预算"思路。【论文/官方：Mem0 论文与 aiwiki 整理】

### 1.3 写入 / 巩固 / 检索 / 遗忘 / 淘汰机制（社区做法对照）

| 机制 | 社区做法 | 关键出处 |
|---|---|---|
| 写入 | ① 模型判断 salience 后写（Mem0 抽取、Letta 工具调用、Cursor Memories 曾用的 sidecar）；② 规则/工具门控写入（显式 `PUT /preferences`）；③ 后台异步巩固（LangMem "subconscious"、Letta sleep-time、ChatGPT Dreaming） | Mem0 论文、LangMem 文档、Letta 2025 sleep-time paper |
| 巩固 | 重复项合并、冲突消解、树/图连接、短→长期迁移（MemOS MemScheduler）；LLM 重写相邻笔记（A-MEM evolution） | MemOS arXiv 2507.03724、A-MEM arXiv 2502.12110 |
| 检索 | 混合召回（向量+BM25+图遍历）→ rerank → 按权重/recency/类型打分 → token 预算内注入 | Zep/Graphiti 检索管线、Chroma 检索建议 |
| 遗忘 | 软失效（Zep bi-temporal 把过期事实标 invalid 不删；Mem0g resolver 标旧关系 invalid）；硬删除（Mem0 base DELETE）；用户清除 / forget API（Cognee `forget` 连派生产物一起删） | Zep、Mem0 论文、Cognee 1.0 API |
| 淘汰 | TTL / retention 期、访问衰减（Mem0 检索期 recency 加权）、LRU+TTL（MemOS），"失效不删行"便于审计 | MemOS 文档、各产品 privacy 文档 |

## 2. 代表性社区方案对比表

> 状态均为 2025-2026 查证；带 `*` 的数字为厂商自报或社区说法，未独立核实。

| 方案 | 记忆分层 | 存储 | 检索 | 上下文管理 | 适用场景 | 坑 / 取舍 |
|---|---|---|---|---|---|---|
| **Mem0 / Mem0g**（arXiv 2504.19413, 2025-04；Apache 2.0 + 托管平台） | 4 层作用域：conversation / session(`run_id`) / user / org；user 内分 semantic/episodic/procedural | 向量(Qdrant 默认, 1536维)+图(Neo4j/Neptune, Mem0g)+KV；20+ 向量库可插拔 | 抽取期用 session summary+最近 m=10 条；更新期按 top-s=10 相似记忆，LLM 选 ADD/UPDATE/DELETE/NOOP；检索按 relevance+recency+type 权重(semantic 0.6/episodic 0.3/procedural 0.1)，top-5 <200 token 注入 | 用摘要+原子事实替代整段历史；异步刷新 summary 不阻塞写入 | 个人助理、跨会话偏好、快速落地的生产 agent | base DELETE 是硬删（历史丢失）；无显式 decay/TTL 策略；安全/投毒非一等公民；benchmark 争议大（见 §5.2）；图版 p95 更高、需 Neo4j |
| **Zep / Graphiti**（arXiv 2501.13956；Graphiti Apache 2.0，~19.7k stars@2025-11，~29k@2026*） | 三层子图：episodic(无损 raw) / semantic entity(9 节点/8 边类型, v3) / community(聚类降噪)；2026 加 saga 抽象 | 时序知识图谱；Neo4j 5.26+ 默认，FalkorDB(亚 10ms)、Kuzu、Neptune+OpenSearch；企业版 Context Lake/Konig 用"热图内存+快照到对象存储" | **bi-temporal**（valid time + transaction time），过期事实降为 invalid 不删；混合检索=向量+BM25+图遍历+多策略 rerank，**检索期不调 LLM**；典型 <100ms*；图搜索 p95 从 600ms 优化到 150ms* | 2025 末 Zep v3 改名"context engineering platform"；MCP server 1.0@2025-11 | 企业跨会话事实追踪、需要"过去某时点真值"、多跳推理 | 企业级规模成本高（S&P 451 Research 2026-04 明确指出）；schema 刚性限制开放域；抽取事实是模型输出、可能错；个人画像需 purpose limitation/retention/删除路径（GDPR 风险）；与 Mem0 公开 benchmark 互撕 |
| **Letta / MemGPT**（arXiv 2310.08560；2024-09 改名，~$10M seed；v1@2026） | OS 虚拟内存隐喻三层：Core(常驻 2-4KB memory blocks, agent 自改) / Recall(全量交互可搜) / Archival(显式长期冷存) | Core 落 DB + Jinja 编译；Recall 向量+全文+混合；Archival 向量/图库；2025+ MemFS(Git-backed Markdown)、Context Repositories(git 版本化记忆) | **Agent 自主调工具管理记忆**（`core_memory_replace` / `archival_memory_search/insert`）；Recall 向量+全文+时间过滤 | v1 去掉 heartbeat/send_message，原生 assistant message + reasoning；sleep-time compute 后台整合；"white-box memory" | 需要 agent 自主管理记忆、研究型/编码型长任务 | LLM 管理的换页每次都要模型决策→延迟+token 开销（自家 benchmark 承认）；确定性差；与 M7 "零模型抽取 + 确定性"路线冲突 |
| **LangMem**（LangChain, 2025-02；MIT；v0.0.30@2025-10，**pre-1.0**，~746K 月下载*） | semantic(facts: collections/profiles) / episodic(经验 few-shot) / **procedural(改 system prompt 的 prompt optimizer)** | 存储无关 core API；原生 LangGraph BaseStore；生产 PostgresStore；namespace 按 user_id 隔离 | hot path（agent 主动调 memory 工具，有可感知延迟）或 background（memory manager 会话后异步抽取）；自动 consolidation 合并相关/消解矛盾 | namespace 隔离；thread 内短期交给 LangGraph checkpointing | 已用 LangGraph、想要"程序记忆/自我改进 prompt" | 每次抽取都是模型调用，需 API key；hot path 增加延迟和 agent 决策负担；发布节奏慢（7 个月无新包）；pre-1.0 风险 |
| **MemOS**（MemTensor, arXiv 2507.03724@2025-07；Apache 2.0, v2.0, ~11.9k stars*） | **MemCube** 容器三类：plaintext / activation(KV-cache) / parameter(LoRA)；生命周期状态机 Generated→Activated→Merged→Archived→Expired | 图库(NebulaGraph/Neo4j)+向量；MemScheduler 用 Next-Scene Prediction 预加载；MemGovernance 管权限/保留/审计 | 混合检索（语义+关键词+图链接），按类型分组返回 | "Time Machine"版本回滚；文本↔KV-cache↔参数跨形态转换；KV 注入把 TTFT 2.04s→0.12s* | 本地模型、需要可调度的统一记忆治理、多 agent 共享/隔离 | **重**：同步保存 2-5s（Flash-Lite）/10-24s（Flash），每次保存多次模型调用*；KV-cache 占 GPU（Qwen3-8B 约 0.83GiB/记忆）；benchmark 为厂商自跑；activation/parameter memory 依赖本地模型访问——与本项目"无真实模型"环境冲突 |
| **A-MEM**（arXiv 2502.12110, NeurIPS 2025；Rutgers/Ant/Salesforce） | Zettelkasten 原子笔记：每条含 content/timestamp/keywords/tags/contextual description/embedding/links | 向量+链接网络；无预定义 schema | 余弦 top-k 找邻居 → LLM 决定建链 → 新记忆触发 LLM **更新邻居笔记属性**（memory evolution）；检索=余弦 top-k + 链接关联 | 多属性结构化笔记 + 动态链接，抗冗余 | 需要关系发现、多跳推理、动态知识网络 | 反复 LLM 巩固→延迟 + 过度抽象丢细节*；质量受底层 LLM 限制；论文数字（多跳近 6×、1200-2500 token）需谨慎对比 |
| **Cognee**（Apache 2.0, ~12k stars, 5M+ SDK runs/月@2026Q3*） | ECL 管道（Extract→Cognify→Load）；episodic/semantic/procedural + temporal mode（保留被取代事实的有效期） | 图(Kuzu/Neo4j/FalkorDB)+向量(LanceDB/pgvector)+关系(Postgres)，单 Postgres 可三合一 | 混合检索+ranking+token 预算；四动词 remember/recall/**improve**(反馈回权)/**forget**(删事实及其派生产物) | MCP server 暴露 remember/recall/forget；datasets 读写删分享权限；session_id 分会话 | 多 agent 共享记忆、需要跨文档实体消解和"真正删干净" | 官方自述"单轮 chatbot / 短历史不需要图谱"；Cognify 有 LLM 调用+本体对齐成本；时序取代/并发写冲突/长链溯源仍是开放问题 |
| **Supermemory**（supermemory.ai, ~18.6k stars*；闭源核心+API/MCP） | learner-1 对用户/任务/租户上下文做抽取与"dreaming"；层级记忆（hot KV / 深层按需） | 向量-图库（Cloudflare Durable Objects + Postgres*）；连接器 Google Drive/Notion/OneDrive | `/add` `/connect` `/search`；Infinite Chat API 把记忆管理内联进会话历史，只发必要的；MCP 跨平台共享 | 实时把 token 注入上下文（hooks）；context rewriting + broad connections | 想快速接入、跨工具/多模型移植记忆 | 数据出域到第三方（隐私/PII 风险）；benchmark 全为厂商自报（#1 LongMemEval/LoCoMo/ConvoMem*）；"记得太多"需自行规划；搜索延迟 187/356ms* 为生产流量自报 |

## 3. 上下文管理：社区主流做法

### 3.1 四操作框架（Write / Select / Compress / Isolate）

由 LangChain 的 Lance Martin 提出，Anthropic 2025-09《Effective context engineering for AI agents》与 Manus
2025-07-18 生产复盘共同收敛：【论文/官方+媒体：aiagentmemory.org/articles/context-engineering、dropagentic.com、generativeai.pub】

| 操作 | 含义 | 社区具体手段 |
|---|---|---|
| **Write** | 把信息持久化到上下文之外 | scratchpad / 文件 / 数据库 / 长期记忆；结构化笔记（agentic memory） |
| **Select** | 每步只拉回需要的切片 | RAG + 语义检索 + 图检索 + tool-description 检索；recent k 轮；namespace 过滤 |
| **Compress** | 用紧凑表示替换大块 | 递归/层次摘要、auto-compaction、trim/pruning、可恢复压缩（保留 URL/path，丢内容） |
| **Isolate** | 拆分上下文降低干扰 | 子 agent（返回 1000-2000 token 摘要）、sandbox、runtime state schema 只暴露所需 |

### 3.2 压缩 / offloading / 缓存的具体参数（可借鉴）

| 技术 | 社区参数/做法 | 出处 |
|---|---|---|
| 大工具输出 offloading | Deep Agents：**单次 tool 输出 >20,000 token 写文件**，对话里只留 path + 前 10 行预览；上下文到窗口 **85%** 时用文件指针替换旧 tool 调用 | LangChain Deep Agents（2026-01），dropagentic.com |
| Auto-compaction | Claude Code 近窗口上限触发，摘要保留"关键决策/未解 bug/实现细节/最近文件"，丢重复 tool 输出；Cognition 用**微调过的 compaction 模型**因为通用摘要会丢关键决策 | dropagentic.com、wpnews.pro（部分为社区说法） |
| 可恢复压缩 | 原始完整对话另写文件，需要时再搜；"restorable compression"保留路径/URL | Anthropic / dropagentic.com |
| 缓存纪律 | Manus：KV-cache hit rate 是"生产 agent 最重要单一指标"，input:output≈100:1，缓存 Sonnet 输入 $0.30/M vs 未缓存 $3*；**前缀逐字不变、append 不 edit**；工具定义"mask 不 remove" | Manus 2025-07-18，aiagentmemory.org/articles/context-engineering |
| 错误/计划保留 | Manus：把失败动作及错误输出留在上下文（模型从错误中学）；维护 todo.md 周期性复读目标和进度以对抗 Lost in the Middle | 同上；guanweilu.cn 转述 |
| 上下文失败模式 | Breunig 归纳：poisoning / distraction / confusion / clash / fighting the weights / inertia；inertia 的解法是隔离到新 agent + offload notes + 删历史 | aiagentmemory.org/articles/context-engineering |

### 3.3 检索与 token 预算（可借鉴）

- **检索管线**：混合召回（向量 + lexical/regex + metadata filter）→ 候选池 100-300 → rerank（LLM/cross-encoder）到 20-40 →
  组装（指令优先、去重、多样化、hard token cap）→ 小 gold set 进 CI。【gist.githubusercontent.com/hugobowne/... Context Engineering 2025】
- **分层 token 预算**（社区示例，非标准）：Role/Policy 1-5%、Goal/Constraints 2-5%、Tools 5-20%、Evidence 40-70%、
  Memory/State 5-15%、Buffer 5-10%；**超出时先砍 evidence，不砍契约/安全规则**。【contextstudios.ai/blog/context-engineering...】
- **证据包（evidence pack）**：每条检索结果转成{标题/来源/provenance, 3-7 条 claim, 1-3 短引用, 时间戳}，再做语义去重——
  抗 context rot 且保留可追溯性。【contextstudios.ai】
- **注入安全**：所有检索文本/工具输出标注为 UNTRUSTED DATA，过滤"ignore previous…"等指令模式（OWASP 注入防御）。【contextstudios.ai、promptwatch.com】

## 4. 对 M7 的明确建议

> 以下建议以 M7 现有设计（v1.4 记忆 + v1.8 上下文工程增补）为基线，标注"保留 / 补强 / 不建议"。

### 4.1 (a) 建议的记忆类型分层表（存储 / TTL / 检索策略）

M7 现有三层（工作 / 情节 PreferenceEvent / 语义 UserPreference）**方向正确，予以保留**；建议做三处补强：

| 层 | 类型 | 内容 | 存储（生产真实实现） | TTL / 生命周期 | 检索策略 | 与现有设计的关系 |
|---|---|---|---|---|---|---|
| L1 | **Working** | 当前 super-step、`clarification_answer`、检索片段槽、工具结果 | M04 `Run`/checkpoint/SSE + 上下文窗口 | 会话内，结束即清 | 常驻（不检索） | **保留**（M04 已有） |
| L2 | **Episodic（证据层）** | "何时/何会话/何种信号/学到或撤销了哪个字段什么值" + **写入来源(source_type: explicit/clarification/correction/adopted_artifact)与触发证据引用** | PG `PreferenceEvent` 只追加表（带 hash 链更稳） | 180 天到期**失效不删行**；审计可回溯 | 按 user_id + 字段索引；写入时冲突裁定用；检索期按 recency 加权 | **补强**：现有已有时效，建议把 source_type 显式列化、写入来源审计落 trace（记忆投毒取证需要） |
| L3 | **Semantic（偏好层）** | `{palette, preferred_grids, preferred_widget_types}` + 每字段 `source/source_weight/evidence_count/version` | PG `UserPreference` 结构化字段 | 长期，随版本更新 | **高置信门禁**：`weight≥0.7 或 evidence_count≥2`；30 天内强化 ×1.5、超 180 天 ×0.3，只降权不删；按权重降序截断，不挤占 1-2 槽 caching 前缀 | **保留**，完全符合社区"profile 单文档只留最新状态"做法 |
| L4（新） | **Procedural（轻量程序记忆）** | "该用户偏好复用哪类 recipe / 哪种 widget 结构模板"——仅从**显式采纳/复用行为**提取，不从文本抽取 | PG 新表 `UserProcedure`（recipe_version/widget_type/采用次数/最近采用时间）或并入 UserPreference 字段 | 长期；显式遗忘可达 | 命中当前 widget_type 且 `采用次数≥2` 时，作为"规程"槽的加权提示注入（≤N token），不改变 recipe 版本本身 | **新增建议**：对标 LangMem procedural，但**零 LLM**（用 adopt 信号），契合 ADR-002 D-10 |
| 旁路 | **Large artifact offload** | 单次 >20k token 的检索片段/附件洞察 | S3 对象存储 + `object_key + 预览 N 行` 引用进 manifest 与复现指纹 | 随产物留存期 | JIT 按需回放（引用进 repro_fingerprint） | **补强**：M7 v1.8 已设计，建议固化为强制门禁 |

**明确不建议采纳的分层**：
- **activation memory / KV-cache memory（MemOS）/ parameter memory**：依赖本地模型权重与 GPU，与"无真实模型 + 换模型只改配置"约束冲突。
- **知识图谱层（Zep/Cognee/Mem0g/A-MEM）**：WidgetPilot 偏好字段少、无多跳关系查询需求，图谱的 schema/延迟/成本/PII 画像合规收益为负。
- **LLM 自主管理记忆（Letta）/ LLM 抽取事实（Mem0/LangMem background）**：与 ADR-002"零 LLM 抽取、`call_count==0`"直接冲突，且引入延迟/不确定性/投毒面。
- **程序记忆写 system prompt（LangMem prompt optimizer）**：破坏 prompt 前缀稳定与 caching，且不可审计；仅借鉴"显式复用信号"思路。

### 4.2 (b) 建议的上下文组装流水线（六槽位 + 每步硬预算）

保留 M7 六槽位固定顺序（保 caching 前缀），在其上补"检索重排 + 证据包 + 注入安全 + 分层预算 + 可恢复压缩"：

```
[输入] M06 ValidationResult(widget_type/grid/recipe_ids/tier/attachment_refs/evidence_ref)
  │
  ├─ Slot1 系统契约（版本化 prompt + WidgetSpec schema 骨架）        ← 缓存前缀，逐字不变，无时间戳
  ├─ Slot2 规程（recipe_ids 对应版本 + 轻量程序记忆 L4 加权提示）     ← 缓存前缀；骨架/正文去重
  ├─ Slot3 检索片段（M10）  ← ① 混合召回 100-300（向量+BM25+filter）
  │                          ② **强制 rerank 到 20-40**（见 §5.1 模型依赖）
  │                          ③ 证据包化（来源/claim/短引用/时间）+ 语义去重 + 标 UNTRUSTED DATA
  │                          ④ 无结果 → notice + HUMAN_REQUIRED，不编造（保留 A17）
  ├─ Slot4 附件洞察（M05 AttachmentInsight）                        ← >20k token 落 S3，留 object_key+预览
  ├─ Slot5 用户记忆（UserPreference 高置信门禁 + 衰减权重排序）      ← 半稳定，超预算降序截断，不动前缀
  └─ Slot6 会话结论（state 结论/引用，含 excluded_approaches 已排除方案）
  │
  ├─ 预算：分层 token 上限（契约/规程≈固定，检索片段+附件+记忆为可压缩区）
  ├─ 压缩：超阈值只压缩 tool message；**必保留任务契约与 excluded_approaches**；原始快照写 S3（可恢复压缩）
  ├─ 缓存：append-only；工具运行中只 mask 不 remove；system 前缀不含时间戳
  └─ 指纹：repro_fingerprint 含 prompt/recipe/retrieval_snapshot/model/version/tier/preference_version
           └─ context_snapshot.json 落 evidence/...（不含附件原文/整段历史代码）
```

**与社区对齐点**：Write=槽 5/6 + S3 offload；Select=槽 3 混合召回+rerank；Compress=tool message 压缩+可恢复快照；
Isolate=单 loop 内用槽位/命名空间隔离，不引入多 agent（M7 已明确不采纳，理由成立）。

## 5. 风险与可信度专章

### 5.1 延迟 / 成本 / 隐私 / PII / 复杂度

- **延迟**：检索+重排+记忆注入每一次模型调用都累加；Mem0 报告 p95 搜索 ~0.2s*、Zep <100ms*、
  MemOS 同步保存 2-5s*——任何"每次写都调模型"的方案都会拖慢 M7 的生成回路。【论文/媒体，均为厂商自报】
- **成本**：图记忆与 LLM 抽取按 token 计费；多 agent 约 15× token；缓存命中可使输入成本降约 10×——
  M7 的 caching 纪律直接决定 X4 成本账。【Manus 复盘；社区说法需核实具体倍数】
- **隐私/PII**：记忆即个人画像。ChatGPT/Claude/Gemini 消费版默认开训练、长期留存；澳洲 2025 隐私法把
  "推断出的个人信息"也纳入监管，要求删除触达主库/备份/派生 embedding。【myvaultai.com、13labs.au】
  M7 已有"禁存 PII 原文 + 可清除 + 公共语料双向隔离"，应补"删除/清除要触达派生引用"。
- **复杂度**：Cognee/MemOS 的多层抽象、schema/治理配置远超 WidgetPilot 偏好规模；LangMem pre-1.0 发布节奏慢。

### 5.2 Benchmark 可信度（直接决定"不要照抄厂商分数"）

- LoCoMo 答案键约 **6.4% 错误**（1540 题中 99 处，Penfield Labs 审计，经 Dell Zhang 2026-05 引用；
  **注意**审计方有竞争记忆项目，作者自述已交叉核对——`【社区说法/未核实】`）；
  标准 judge（gpt-4o-mini 原 prompt）接受了 **62.81%** 的"错误但话题相关"答案；理论满分约 93.6%，
  低于 ±6 分的差距属噪声。【agentos.sh/en/blog/memory-benchmark-transparency-audit、maximem.ai/blog】
- 厂商互撕：Mem0 论文给 Zep 65.99%，Zep 重跑称 75.14%（并自纠早先 84%），Mem0 去掉对抗题后重算 58.44%；
  双方互相指责 speaker role 误判/配置错误。Letta 无法复现 Mem0 对 MemGPT 的跑分，用纯文件搜索 agent 在 GPT-4o-mini 拿到 74.0%。
  【agentsystems.blog/agent-memory-benchmark、llms3.com/blog（2026-07）】
- OSS 与托管版本差异：Mem0 OSS SDK 第三方跑 LongMemEval 49.0% vs 厂商 Platform 94.4%（不同模型/预算）。【maximem.ai/blog】
- 结论：**benchmark 是过滤器不是决策器**；M7 选型用自己的 gold set（§4.5）。

### 5.3 记忆投毒 / 注入（M7 必须防的攻击面）

- OWASP《Top 10 for Agentic Applications》(2025-12) 将 **ASI-06 Memory and Context Poisoning** 列为十大风险之一，
  点名多 agent 共享记忆的放大效应。【论文/官方：OWASP】
- MINJA（arXiv 2503.03704, NeurIPS 2025）：仅凭普通 query 访问即可注入，平均注入成功率 **98.2%**，
  诱发恶意推理攻击成功率 **76.8%**。【论文/官方】
- AgentPoison（NeurIPS 2024）：污染率 <0.1% 即 >80% 攻击成功率，良性性能下降 <1%。【论文/官方】
- 真实产品事件：ChatGPT SpAIware（2024，持久化记忆外泄，2 个多月才修复）、Gemini 延迟工具调用注入
  （Rehberger 2025-02，把用户年龄写成 102）、Claude memory tool 对抗图像注入（2026，10 次中 5 次成功*）、
  "ZombieAgent"跨会话持久注入（2026-01）。【媒体/二手：akto.io、agentstateattack.com、sysdig.com】
- **对 M7 的直接启示**：① 写内存只能来自四类白名单信号，且来源可审计；② 检索文本/工具输出标 UNTRUSTED DATA；
  ③ 记忆可查看/可清除（FR-23 已有）；④ 跨 user scope 隔离列化；⑤ `excluded_approaches` 保留也有抗"记忆惯性"价值。
