## 应该改（Should）

### S1 · `adapters.py:108-130`

现象：`save` 的 B2 租约继承由旧实现的**单条** `INSERT ... SELECT`（子查询取 MAX(rev) 行租约，与 INSERT 处于同一语句快照）拆成事务内**两条**语句——先 `SELECT ... ORDER BY rev DESC LIMIT 1` 读租约，再 `session.add()` 新行。两步之间若另一事务提交了更高 rev 行并改写了租约，新行继承的将是"曾查到的上一行"租约而非"提交时刻真正的最新行"。

为什么重要：B2 是上一轮修复的并发 Blocker（持锁 worker 写 checkpoint 后不能丢锁）。当前调用模式下持锁 worker 串行写 checkpoint、抢锁前不写 checkpoint，该窗口实际不可达，集成测试也通过；但相对旧 SQL 的单语句原子性是一次语义弱化，一旦将来出现并发写同一 run 的新 rev，可能重新引入"双持锁者"。不改不炸，属于会积累成问题的类型。

改法：给读上一行的 SELECT 加行锁，把读与写在事务内闭包化（与旧单语句快照等价）：

```python
                prev = session.execute(
                    select(Checkpoint.lease_owner, Checkpoint.lease_until)
                    .where(Checkpoint.run_id == run_id)
                    .order_by(Checkpoint.rev.desc())
                    .limit(1)
                    .with_for_update()   # 锁定最新 rev 行，防 SELECT 与 INSERT 之间租约被并发改动
                ).first()
```

或恢复单语句 `insert(Checkpoint).from_select(...)`（维护成本更高，不优先）。

### S2 · `accounts/pg_stores.py:56-64`

现象：旧实现 `except psycopg.errors.UniqueViolation: raise DuplicateEmailError` 对**所有**唯一冲突（email 与主键 id）都映射为 `DuplicateEmailError`；新实现只在 `constraint_name == "users_email_key"` 时映射，主键冲突走 `raise exc.orig`（抛 `psycopg.errors.UniqueViolation`）。同时第 58 行注释"主键(id)冲突还原为 psycopg 原异常（原实现直接透传 UniqueViolation）"与旧实现真实行为不符——旧实现并非透传，而是同样映射成 DuplicateEmailError。

为什么重要：用户要求"异常类型对外不变"。email 冲突（唯一可达路径）行为等价且有测试背书；主键冲突因 id 为服务端生成 uuid 实际不可达，故非 Blocker。但依赖硬编码约束名 `users_email_key` 是脆弱点（schema 若被外部改过约束名即失效），且错误注释会误导后续维护者判断行为等价边界。

改法：二选一，保持对外一致。建议与原实现严格对齐并修正注释：

```python
        except IntegrityError as exc:
            if isinstance(exc.orig, psycopg.errors.UniqueViolation):
                # 行为等价：旧实现把所有 UniqueViolation（email/主键）都映射为 DuplicateEmailError
                raise DuplicateEmailError(row.email) from exc
            raise
```

若刻意区分主键冲突，则至少把第 58 行注释改为"主键冲突透传 psycopg UniqueViolation（本轮有意收窄，与旧实现不同）"，避免描述失实。

## 可选（Nit，最多 3 条）

### N1 · `db.py:48-49`（及 `accounts/pg_stores.py:31` 等各 `__init__`）

现象：`make_session_factory` 每次调用都 `create_engine()`，即每个 store 实例各持一个 engine 与独立连接池，且无 `dispose()` 出口。

为什么重要：生产装配中 store 为启动期单例、无泄漏；但集成测试每个用例 new 多个 store 会建多个池（短生命周期，靠 GC 回收）。若将来改为 per-request 实例化 store，会快速耗尽连接。当前无实际影响。

改法：装配侧保持单例（现状即可），或在进程退出/测试 teardown 统一 `engine.dispose()`；如需彻底共享，可把 engine 提为模块级单例再派生多个 sessionmaker。

### N2 · `db.py:57-58` vs `docs/modules/M04-账号会话与编排域.md:152,190`

现象：设计文档 §2.1.1 与 §2.3 写明 API 为 `session_factory` 与 `get_session()`，实际代码导出的是 `make_session_factory()` 与 `session_scope()`。

为什么重要：文档也在本轮审查范围，命名漂移会让按文档接入的开发者找不到入口，属于很小的可维护性成本。

改法：统一命名——把文档 §2.1.1 表格与 §2.3 落位注释中的 `get_session()` / `session_factory` 改为 `session_scope()` / `make_session_factory()`；或在 `db.py` 增加兼容别名 `get_session = session_scope`（不推荐，徒增 API）。

### N3 · `services/orchestrator/adapters.py:8-14`

现象：模块 docstring 仍写"完整可运行的异步实现（psycopg3 / redis-py asyncio）""生产适配器用 psycopg 同步连接承载"，与本轮实际（PG 部分改 SQLAlchemy ORM + 同步 Session，redis 仍同步客户端）不符；顶部的 A3/A4/A11 未补跑说明也已与"集成测试已跑"现状脱节。

为什么重要：陈旧注释会让读者误判数据访问技术栈，与 §2.1.1"不用裸 psycopg 手写 SQL"的定稿结论矛盾。

改法：更新 docstring 首段为"PG 部分走 SQLAlchemy 2.x ORM（Checkpoint/Lease），Redis 部分走 redis-py 同步客户端"，并删除或改写"未补跑 A3/A4/A11"的过时说明。
