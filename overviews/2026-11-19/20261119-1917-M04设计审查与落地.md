### Blocker

**[B1] server.py:186,224,237,245 + service.py:63-153 — signal 端点全越权（实测复现）**
- 现象：post_message/interrupt/resume/cancel 端点收到 `user: UserRow = CurrentUser`，却只把 session_id 传给 SessionService；这些方法签名无 user_id，也不调 TenantGuard。唯 snapshot(L169)/clarifications(L209) 传了 user.id。
- 为什么重要：任何登录用户可用自己合法 token 操作他人会话。实测：用户 B cancel 用户 A 的会话 → HTTP 200、state 变 CANCELLED。直接违反设计 §4.1 权限"本人"、§7 "每个 REST 请求按 user_id 校验"、A1/A2 验收。
- 改法：SessionService 的 submit_message/interrupt/resume/cancel/complete/fail/mark_awaiting_input 全部增加 `user_id` 参数并在 `get()` 后 `TenantGuard.assert_owner(user_id, row.user_id)`；server.py 各端点传入 `user.id`。测试补 B 对 A 的 interrupt/resume/cancel/messages 各一条 → 403。

**[B2] adapters.py:93-98（save）+ 194-201（acquire）+ 213（heartbeat）— 租约随 checkpoint 丢失，双 worker 并发**
- 现象：PgCheckpointStore.save 插入新 rev 行不带 lease_owner/lease_until（新行两列为 NULL）；PgLeaseProvider.acquire 的抢锁 WHERE 锁在 `rev = MAX(rev)` 行；heartbeat 只更新 lease_owner=owner 的行，碰不到新插入的 NULL 行。
- 为什么重要：持锁 worker 每写一个 checkpoint（每个 super-step）后，新的 max rev 行租约为空，另一 worker 可再次抢到锁 → 两个 worker 同时推进同一 run，重复外部副作用/重复产物。违反 §11.4 "租约随 checkpoint"与 I3 单持锁者。集成测试 A3/A4 是手动改 lease_until，未覆盖"save 后再抢锁"路径，故漏检。
- 改法：租约列改为按 run 维度独立维护（单独 lease 表或 checkpoint 抢锁不绑定 MAX(rev)，改为 `WHERE run_id=%s AND (lease_until IS NULL OR lease_until<now() OR lease_owner='')` 且所有 rev 行同步，或新建 `run_lease(run_id PK, owner, until)` 表）；heartbeat 引用 HEARTBEAT_INTERVAL_S 常量而非硬编码 30。补集成测试：acquire→save_checkpoint→第二 worker acquire 应仍失败。

**[B3] accounts/service.py:110-112 + 169-176 — 用户删除/降权后仍凭旧 role 刷新令牌**
- 现象：refresh() 中 `find_by_id(...) or _claims_to_row(claims)`，用户查不到时用 token claims 里的旧 role 构造行继续签发 access token。
- 为什么重要：用户被删除或角色降级（curator→user）后，7 天 refresh token 有效期内仍可换发出带旧角色的 access token，越权访问管理员端点。违反 §7 权限裁剪在服务端、D-3 两角色。
- 改法：删除 _claims_to_row 兜底；`user = find_by_id(claims.user_id); if user is None: raise AuthError("invalid token")`；用 DB 中的 user.role 而非 claims.role 签发。补测试：删除用户后 refresh 应失败、降权后 refresh 新 token role 为最新值。
